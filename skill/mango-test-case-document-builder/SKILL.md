# 功能测试用例编写

## 职责边界

只作为测试人员，不改写、总结、重新解释、润色或编造产品需求/开发设计。

Skill 规则写明适用条件和对应动作。实际生成 Case 时，从本次需求、契约或测试目标获取项目、功能、字段和规则名称。

这是**功能测试用例设计** Skill。围绕可见业务行为及 API/UI/数据契约，通过可用测试环境的正常请求、账号、权限、业务数据、文件和产品支持操作触发。

不设计或保留须基础设施故障注入的功能 Case：停 Redis、数据库、MQ、应用、认证或下游，强制断网、超时、固定5xx、进程/Pod 崩溃、耗尽资源、切换、容灾或集群拓扑变化。可用性、中间件韧性、依赖容错和运维保障归开发组件测试、SRE/稳定性/混沌或另行授权可靠性计划，不属本功能集。

保留普通功能负例：非法参数、缺字段、认证/授权失败、租户隔离、状态冲突、重复提交、支持的功能开关及无需关服务就能确定触发的错误。

来源含基础设施故障场景时：

- 不创建为功能 Case，不算功能未覆盖/阻塞。
- 仅用户要求覆盖/风险说明时，在表外注明越界及适合归属。
- 已有行标为功能范围外并提出移出建议，不因无故障注入能力留作阻塞或暂不自动化。
- 用户未要求清理/更新范围，不静默删除原行。

## 功能覆盖与遗漏检查

让 AI 按实际业务自主推导，不规定方法名、固定方法清单、方法列、用例数量或穷举组合。完整性是约定范围内独立业务行为与重要风险有覆盖，不是行数越多越好。

写前从来源识别目标、角色、对象、入口、操作、前置、生命周期、限制及可观察结果，形成内部覆盖提纲，不将每句文档、每个控件或代码分支机械变用例。

设计顺序为：先形成约定范围的业务目标和规则 → 按独立验证入口、测试类型拆成可单独判定的 Case 行 → 关联自动化并补齐独立风险。页面与接口行在同一业务分组内相邻组织，不按执行方式分成两套台账；不先按接口列表机械生成用例，不设专项数量或比例指标。

- 标题、场景、预期优先表达用户目标、业务条件和可观察结果；URL、参数名、HTTP状态、内部标识仅在复现或精确判断确有需要时放相关数据/检查点，不以返回字段清单、路由或实现机制代替功能目标。描述不虚构页面操作，接口专项仍可明确写直接请求。
- 名称、日期、筛选、排序、重复保存等按独立业务规则和结果设计，适合 API 的直接覆盖原功能行；不同预期的边界分别设计，不因共用一个接口就打包成一条，也不按每个参数机械扩增。已有同目标时先复用，不为自动化另造同义行。
- API 专项只补已有功能目标未覆盖的协议、绕过页面校验、权限隔离、幂等或竞争等独立风险，说明业务影响及依据，不替代主流程和页面必测。整理旧接口化用例时先核对需求、重复与遗漏，再决定改写、关联或按授权拆分；不能仅换个业务标题就声称完成转换，也不擅自删除历史资产或执行证据。

按功能适用性检查，不要求所有功能强填每类：

- 主流程和有意义替代路径，动作前后、取消、重复、打断/重开及支持的允许/禁止状态变化。
- 成功与可控功能失败；会改变行为的缺失、空、非法、极值、冲突、重复输入/数据，具体限制有依据不编造。
- 谁能看/操作什么：用户角色、归属、租户边界和相关入口；页面限制不自动证明其他访问路径也受保护。
- 无数据、单条、多条、关联对象、生命周期差异及支持的组合筛选；只补会改变业务结果的组合，不盲目笛卡尔积，也不将一个代表当所有组合证明。
- 不只动作成功，还验证返回/显示内容、保存值、影响范围、关联及后续可见性；拒绝时禁止副作用不发生，异步区分接收与业务终态。
- 来源有依赖/变更风险时，考虑相邻功能、其他客户端、兼容和旧行为；不扩为停服务、可靠性或性能测试。

合理补场景不等于可编验收规则。AI 可自主发现遗漏，但不编预期、数值限制、权限规则、来源引用/编号。`验收标准来源` 规则不变。证据不足以确定预期时，在 `备注/探索性记录` 或独立问题表保留具体疑问，无依据验收/结果留空，不算可执行验收就绪 Case；继续独立项，穷尽现有证据后才问缺失业务决定。

交付前双向核对用例、内部提纲和来源业务路径。每条范围内的业务路径应能追溯到用例及具体检查点，或记录排除、未决原因。每条用例须有目标、有效触发和有依据的结果。检查遗漏、重复、不可能的组合、无依据的预期和过度合并，并补齐有证据支持的缺口。

检查保留工作证据，不把常规过程备注/新列塞用户文档。最终对话简述实际范围、未决业务和排除项。不超来源/审核证据声称“绝无遗漏”“全部覆盖”，不用数量证明完整。

## 仅接口输入与独立预期

仅提供接口时，先区分地址/curl与完整契约。路由、样例请求响应、历史成功或生成 schema 不证明全部业务规则。先读接口文档、确认目标、已有功能 Case 和业务上下文，记录已知与未决，不由名字编限制、错误语义、角色、状态或副作用。

独立于当前实现先拟业务覆盖和有据预期，按上节检查，不复制代码条件/实际响应作预期。代码已在上下文时，工作证据分开业务预期与实现观察，无需假装没读。

再查代码补触发、前置、校验、权限、持久化、异步、异常及清理风险，双向核对：

- 独立业务/契约要求但代码没有：保留测试目标/预期，记录可能实现遗漏及证据；无分支不代表无需测试。
- 仅代码有：补充 `代码现状回归候选`，不称已确认验收；遵守来源限制，不把源码位置/假需求编号填入验收来源。
- 代码/响应与独立需求不符：保留独立预期及差异，查版本/适用性，不为通过改预期；真权威冲突留未确认，继续其他 Case。

交付独立支持的契约/功能用例，代码候选和具体业务问题单列，不暗中升级候选。先用来源能解决的证据，只问决定重要预期所需最小问题；样例或本地通过不证明答案。只有地址/部分契约时不称全业务覆盖。

## 普通语言描述

面向普通测试，不面向读实现的开发。不了解源码、中间件、协议或架构也能看懂准备什么、做什么、看什么业务结果。

- `用例标题`、`前置条件`、`测试场景`、`期望结果` 简短自然，使用页面/用户认知词。
- 只描述谁在何条件做什么、用户/业务观察什么。
- 主描述不写成代码追踪，避免类/方法、表、缓存键、Redis、内部路由、JSONPath、注解、原始 header/cookie、枚举和内部异常。
- 功能用例的期望写可观察的业务结果。验证协议契约时，直接在期望中写明契约规定的 HTTP 状态、响应字段或错误结构。有业务结果要求时，同时说明应观察到的结果。
- 不改需求，将技术话转可观察含义，如 `同一访问范围内的多个用户连续访问同一功能，超过允许次数后限制后续访问`，不是共享缓存键/限流桶。
- 写前检查普通人是否须源码/基础设施知识；需要就改业务描述，不因设计写过就复制技术细节。

可在测试字段描述工厂前置，但不自行改平台。扩展到工厂可行性、模型/模板、编排、绑定、执行或清理前，读 [工厂 Skill](../mango-data-factory-builder/SKILL.md) 及其路由资料。

`需求`、`开发设计` 只放用户原文或原文档引用，不混入测试分析。粘贴来源尽量原样保留结构、代码、表和重要措辞；飞书 Doc/Wiki 默认放原链接、引用或预览卡，不内联抓取正文，除用户明确要求全文。抓取仅用于设计分析。测试补充只在测试场景/数据、数据库验证、测试记录、buglist、风险/假设或 Case 表。不写工具/映射/下拉/行数/操作过程，交付说明留最终对话，除非用户要求审计段。

## 飞书与本地工具

设计前按来源/输出选工具：

- 飞书 Docx/Wiki：用 `lark-doc`、文档 MCP 或 `lark-cli docs +fetch --doc "<url-or-token>" --doc-format markdown --detail simple`；抓取分析但需求/设计默认放链接。嵌入 `<sheet>`、`<bitable>`、`<cite file-type="sheets|bitable">` 时提 token 转对应表格 Skill。
- Sheet：用 `lark-sheets`、表格 MCP 或 CLI。未知工作表先 `lark-cli sheets +workbook-info --url "<url>"`；用 `+csv-get`、`+cells-get` 或最小范围读；按类型样式用 `+table-put`、`+csv-put`、`+cells-set` 写。下拉用 `+dropdown-set`，多选用 `--multiple` 并写 `multiple_values`。
- Drive/未知资源：用 `lark-drive`、CLI 或 MCP 定位、识别、复制、导入导出、上传下载，识别后转对应文档/表格/本地处理。
- Base：用 `lark-base`、`lark-cli bitable ...` 或 MCP，先查相关字段和记录。
- 授权：遵守 `lark-shared`，`lark-cli auth status --json --verify` 查身份；用户文档默认用户身份，除明确需机器人所有。
- 本地 Excel：用表格工具输出 `.xlsx`；只保留与规范字段不冲突的旧格式，设枚举验证/下拉，交付前裁剪使用范围。

## 流程

1. **读来源：** 识别粘贴/Doc/Wiki/Sheet/Excel/混合，提取产品、模块、流程、角色、环境、故事、API、数据和风险；原文与测试分析分开。先建内部覆盖提纲；仅接口/代码按独立预期流程，先业务依据再代码补漏。
2. **准备文档：** 需求/设计是粘贴则原文，是文档则引用；不总结、不写操作过程。
3. **准备表：**
   - 使用下文标准字段和顺序；`负责人` 后依次放置 `关联用户故事`、`验收标准来源`、`迭代/Sprint`，同属需求与测试负责人分组。`前置条件` 前连续放置 `一级分类`、`二级分类`、`三级分类`，填写与合并遵守下文“场景分类与合并”。已有 `场景分类1`、`场景分类2`、`场景分类3` 或 `分类一`、`分类二`、`分类三` 若确为这三级业务分组，保留内容并改为对应标准列名，不当作无用列删除；`column 1`、空名等占位表头仍应替换。
   - 场景不能独自说清可在其前加 `流程节点`、`流程路径`、`分支条件` 等支持列；先确认目标支持插列。Excel/Sheet支持；不支持时入允许的数据/备注。仅用于澄清设计，不写过程/工具或重复信息。
   - 交叉维度多时用两行表头：上层合并 `测试场景`，下层按实际来源设置页面标签、入口、流程节点、状态、角色等维度。组外编号、标题、优先级、预期、来源、结果、验证类型、数据等纵向合并两表头，不将组内维度零散平铺。
   - 按页面标签分隔流程时，首交叉字段使用来源中确切的标签名称。交叉值使用用户可见的名称，不直接展示后端枚举或内部状态码；代码映射仅在需要且用户要求时放允许的数据/备注，或隐藏参考。
   - 页面列表、筛选及状态字段只用来源确认的用户可见选项，不自行补充隐藏状态或内部终态。对象状态变化导致页面行消失时，预期写清不可见，不编造页面状态值。
   - 有业务流程图时，先识别范围内的业务路径和决策结果，再映射到用例检查点。图的连线数不决定用例行数。纯实现分支仅在产生独立的可观察结果或风险时纳入功能覆盖。用户明确要求交付指定数量时，核对覆盖并说明差异。
   - 一个独立可理解、可单独判定且测试类型唯一的 Case 一行。页面限制与接口防绕过分别设行，不能用一行同时承载手工页面检查和 API 自动化。单行内同一验证目标的必要检查点可分条，不为每个返回字段或内部实现机械拆行；真正的端到端目标按实际执行方式选择一种测试类型。
   - 需要独立判断的目标、触发条件、预期或风险分别设 Case。同一业务规则的页面行与接口行可用相同标题，公共字段按“按测试类型拆行与公共字段合并”展示；测试类型、场景、预期、编号、执行结果及自动化记录独立，合并展示不合并用例身份。
4. **写 Case：**
   - 标题表达本条 Case 的具体测试目标，短且独立可理解，可概括关键业务条件与预期行为。不统一写成 `××分类测试`，不靠读分类或前后行才能区分各条 Case。
   - 分类负责业务分组，标题负责本条目标，场景负责具体条件与操作；三者不互相照抄。标题不堆砌前置、完整步骤、数据清单或大段预期，具体输入值放测试数据。标题相似时核对是否遗漏区分目标的关键条件，或实际重复设计；不靠添加编号制造区别。不同输入、角色或操作路径可以验证同一具体目标并使用相同标题，其差异仍须在各条场景/数据中明确；标题相同不等于重复 Case，也不使标题承担分类职责。
   - 仅用户/来源明确或设计可有把握推导才填，不清楚留空。不写 `待补充`、`未知`、`TBD`、`Story1`、`Sprint1`、默认负责人、猜模块/链接。故事、Sprint、负责人、脚本、模块、客户端、接口/页面、环境及平台 ID 同样不猜。
   - 前置条件、测试数据、测试场景和期望结果按下文“四列分工”填写。
   - 简单场景用一句话写清操作。需要连续操作时，可在单元格内分行编号，保留复现所需的顺序。按上节规则拆分用例，写清各检查点的触发和结果，避免让执行人自行选择验证路径。预期按“预期原文与文案检查”核对。
   - `验收标准来源` 按下文“需求关联与验收原文”逐 Case 摘录可直接复制搜索的原文短句，不附编号、章节、说明或链接。
   - 交叉组合仅引用实际支持各条件及结果的条款，不用 `交叉矩阵`、`异常与边界` 等测试设计分类代替产品原话；依据不足留空，不硬套节点。
   - 补充、非目标、现状回归、权限/边界未走图节点时不套流程编号；有直接依据则摘录可搜索的原文短句，只有补充设计 ID 而未核实正文时不视为验收依据完备，无依据留空。
   - 不把代码/逻辑、类方法、表、评审结论、历史缺陷或测试推测当验收来源；代码可辅助补风险，仍须追需求设计，无依据留空，仅用户要求时记录风险。
   - 备注默认留空，主要给用户测试探索/跟进；仅明确要求或真实未决风险问题才填，不常规凑说明、覆盖笔记或显然断言。
5. **表格验证：**
   - 仅显式枚举列设下拉，自由文本不设。`验收标准来源` 为自由文本；逐行确认摘录是源文档中可直接搜索的连续原文，且与本行预期相关，不能仅有编号、章节名或模板化分类。
   - `前置条件`、`测试数据`、`测试场景`、`期望结果`、三级场景分类、`验收标准来源`、`备注/探索性记录` 均为自由文本，不设置状态下拉或选项限制。不得为了满足错误验证规则，把正文替换为选项、清空或改为通过/失败。
   - 按下文“四列执行性自查”逐条核对全部目标用例，发现通用前置、空泛步骤、套话预期、字段错放、对象不明或缺少顺序时先重写；不能只检查列是否填满，或为去重丢掉复现必需的信息。仅清理文案时，只改获授权的列和行，保留编号、数量、测试数据、来源、执行结果、自动化链接及格式；用户排除的 Sheet、冒烟集或其他用例不随同修改。
   - 更新旧表、套用模板、插入或移动列后，先读取实际表头和现有数据验证范围，按列名重新定位；不能沿用旧列字母/索引或连同模板的验证规则直接复制。只移除目标表内自由文本列的错误下拉/验证，保留正文、公式、链接和有效样式，再为正确的枚举列重建验证。无法读取或移除验证时明确报告限制，不声称格式已修复。
   - 下拉仅覆盖实际数据行，不包含表头或无关区域；交付前回读各验证范围、选项及单选/多选属性，确认与该列字段语义一致，并确认自由文本列无残留验证。`测试结果` 使用标准中文选项，不照搬旧模板的 `pass/fail/blocked`。正文与下拉不匹配的红色警告须定位并修正错误规则，不能只隐藏提示。
   - 新建表或获准更新测试层级列时，按平台 `api_case_scenario_layer` 设置单选下拉，选项仅为 `接口/组件级`、`模块级`、`端到端`，顺序一致。发现旧选项时，先按实际验证范围复核旧值，再在授权数据范围内重建下拉并同步写入核实值。交付前分别回读实际下拉规则和单元格值，核对选项、范围、单选属性及所有非空值。层级不明的行和未获准更新的旧规则单列说明。
   - `测试类型` 使用真实单选下拉：`手工验证`、`API 自动化`、`UI 自动化`，每行只选一项，不设置“组合验证”，不与 `验证类型` 混淆。出现手工与自动化混选时，先按独立场景和预期拆行；不能只删掉一个选项而丢失检查点。
   - 自动化状态按下文逐条判断。测试数据、测试层级、验证类型和执行场景按用例设计及实际用途填写。
   - 多选列使用真实多选，飞书通过 `+dropdown-set --multiple` 配置并用 `multiple_values` 写入。载体不支持时说明限制。
6. **清理验收：** 先对覆盖提纲/路径查漏，保留未决不编来源；去多余空行空列、旧模板列、占位表头、真实表外空验证范围。可见使用区截止最后标准列和真实末行。按下文四组规则设置表头配色，交付前回读内容、下拉/多选元数据、表结构及表头样式。

## 标准 Case 字段

除用户有更强团队标准外，按以下顺序：

| 字段 | 必填性 | 规则 |
| - | - | - |
| 用例编号 | 必填 | 统一 `FT-0001`、`FT-0002` 依次递增，至少四位数字；所有功能用例共用一个序列，不使用 FTAPI/FTMAN 等执行方式前缀，不按 API、手工或自动化状态分段、重置序号或另行排序。 |
| 用例标题 | 必填 | 具体业务目标，简短、独立可理解。同一规则的不同测试类型可同标题，连续同组时按公共字段规则纵向合并展示，仍是独立 Case。 |
| 优先级 | 必填 | 单选 `P0`、`P1`、`P2`、`P3`；按失败后果逐行定级，同组连续且定级相同可纵向合并展示，不为合并强行改级。 |
| 测试类型 | 必填列 | 真实单选 `手工验证`、`API 自动化`、`UI 自动化`，每行一种；证据不足留空并说明，不以是否已有脚本推断，不使用多选或拼接值。 |
| 一级分类 | 可选填写 | 被测页面或独立业务能力；有页面归属时优先使用已核实的实际页面名称。按下文“场景分类与合并”分组，不强行填写。 |
| 二级分类 | 可选填写 | 同一页面内可定位的区域/组件；无页面归属时为该业务能力下的接口能力、入口或子能力。无需细分则留空。 |
| 三级分类 | 可选填写 | 对应区域或能力中的具体字段、操作、状态或规则，如名称校验、删除确认；不只写“字段”“操作”等泛称，不代替具体场景。 |
| 前置条件 | 可选 | 仅写执行前需额外完成的特殊准备，按“四列分工”判断。 |
| 测试数据 | 条件必填 | 紧接前置条件。需要单独列出输入或对照值时填写。 |
| 测试场景 | 必填 | 写清谁对哪个对象做什么；需要时注明入口、先后顺序及检查动作，复杂场景可分行编号。不混实现或预期，不用概括性测试目标代替步骤。 |
| 期望结果 | 必填 | 有明确需求结果或提示文案时直接沿用原文；无可直接引用的原文时，才据已确认规则简述可观察结果。文案检查按下文处理，不只写“操作失败”或“结果正确”。 |
| 测试结果 | 必填 | 单选 `未执行`、`执行中`、`通过`、`失败`、`阻塞`、`跳过`，默认未执行。 |
| 负责人 | 建议 | Case 负责人。 |
| 关联用户故事 | 建议 | 紧接负责人；故事/需求/问题/PRD 章节 ID，未明确或无法可靠识别留空，不造 Story1。 |
| 验收标准来源 | 必填列 | 紧接关联用户故事；仅填直接支持本行预期、可复制到源文档搜索的原文短句。不要前缀、额外引号、章节和链接；无明确依据留空。 |
| 迭代/Sprint | 建议 | 紧接验收标准来源；首覆盖/主要维护版本，未提供或无法可靠识别留空，不放占位。 |
| 自动化状态 | 必填 | 单选 `待评估`、`待编写`、`已自动化`、`待修复`、`暂不自动化`；默认 `待评估`，按下文规则和真实证据填写。 |
| 自动化脚本链接 | 条件必填 | 已自动化、待修复时保留真实平台 ID/链接或仓库文件；没有真实资产则留空，不编造。 |
| 测试层级 | 条件必填 | `接口/组件级`、`模块级`、`端到端`，内部映射0/1/2。可确定实际验证范围时填写。 |
| 验证类型 | 条件必填 | `正常场景`、`异常场景`、`边界场景`、`权限场景`、`数据场景`、`流程场景`，内部0–5。按主验证目标填写，手工用例同样适用。 |
| 执行场景 | 条件必填 | 真实多选回归测试/发布验证/冒烟验证/稳定性监测/数据校验/效果评测/生产巡检/生产回归/临时验证/性能测试；内部依次 `routine_regression`、`release_verification`、`smoke_verification`、`stability_monitoring`、`data_verification`、`effectiveness_test`、`production_inspection`、`production_regression`、`temporary_validation`、`performance_test`。按已明确的执行用途及标签适用条件填写，用途未确定时留空。 |
| 备注/探索性记录 | 可选 | 用户测试维护，默认空，仅明确要求或真实未决问题/风险，不为填列写常规备注。 |

可按需增加：`模块`、`客户端`、`接口/页面`、`API Info ID`、`API Case ID`、`执行环境`、`最近执行状态`、`最近执行时间`、`维护人`。

### 功能用例编号

新建整表先按业务分类确定最终行序，再从 `FT-0001` 连续编号；API 用例与手工用例按同一功能分组顺序排列，执行方式仅写验证方式。向已有表追加时沿用现有最大 FT 序号继续，不按分类重新起号；从原表抽取手工必测或冒烟集时保留原 FT 编号，不为连续展示重新编号。

已有表明确获准统一编号时，按目标表当前或已授权重排后的顺序逐行替换，保留旧编号→新编号映射并核对结果、链接、备注及引用仍对应同一 Case；平台真实 Case ID 不变。仅排序或局部修改不自动重编号，也不把本规则当作修改其他表/历史记录的授权。

### 功能用例与自动化覆盖

功能用例是主账。页面显示、回显、按钮、输入交互及提示由页面行验证；接口防绕过、参数校验、权限、持久化及数据影响由接口行验证。API 返回正确不能代替页面观察，页面限制也不能证明直接请求无法绕过。只有独立且有依据的检查点才拆行，接口只是页面用例的造数或辅助查询时，不另造接口验收行。

`测试类型` 每行单选。人工操作/观察选 `手工验证`，接口自动化选 `API 自动化`，页面自动化选 `UI 自动化`；类型表达采用的方式，不表示脚本已实施。同一页面检查从手工迁移到 UI 自动化时按授权更新该行，不机械复制重复 Case。存在独立页面与接口检查时分别设行，不能混选以掩盖不同场景、预期或结果。

飞书 `测试类型` 下拉使用 `--multiple=false`，单元格写单个 `value`，不写 `multiple_values` 或逗号拼接值；回读验证规则及每行值。`执行场景` 等真实多选列仍按各自规则处理，不连带改成单选。目标平台的存储字段若为数组，仅在已核实契约下保存一个选项；不借此修改平台字段模型或声称平台页面已改成单选。

允许一个功能行关联多个自动化资产、一个资产覆盖多个接口行，但按唯一 FT 编号、测试类型和实际检查点映射，不按标题猜绑定。既有接口行已覆盖同一防绕过目标时复用，不因新增页面行而再复制接口行或重复计入覆盖。

### 按测试类型拆行与公共字段合并

- 同一规则需要页面限制与接口防绕过验证时，分别建立页面行、接口行。标题可相同，不强制加“前端/后端”后缀；测试类型、场景及预期说明差异。各行有独立 FT 编号；获准同步平台时分别关联真实 Case ID，不因展示合并而共用身份，也不为补 ID 擅自创建平台资产。
- 页面行写实际页面操作及可见限制、提示、输入保留或回显；接口行写直接请求、绕过页面的输入及服务端拒绝/保存和必要数据影响。页面未发出请求时不能拿接口响应代替按钮行为，也不向接口预期塞页面提示或焦点等检查。
- 同组相邻且内容、含义完全相同的公共字段可逐列纵向合并：标题、优先级、三级分类、特殊前置、测试数据、负责人、需求关联、验收来源、迭代及其他公共设计元数据。优先级须先独立定级；不同优先级、数据、来源、层级或验证类型保留各行值，不因同标题强行统一。空白不作为共同值合并，不跨组或跨不相邻行合并。
- `测试类型`、`测试场景`、`期望结果` 必须逐行保留；`用例编号`、平台 Case ID、`测试结果`、`自动化状态`、脚本链接及执行/探索记录也不合并，即使当前值相同。公共展示不传播通过、失败、阻塞、链接或自动化完成状态。
- 合并前保留逐行完整值和身份映射，合并后展开核对每行可独立还原；独立导出、筛选或同步时带回适用公共值。载体不支持合并则重复完整公共值，不用“同上”或清空重复值假装合并。
- 修改旧表须有相应拆分/整理授权；原行保留适用身份，新行沿现有编号序列追加唯一编号，保存旧行→新行及检查点映射。脚本、结果、来源只迁移至实际覆盖的行；原混合结果不能复制为两行均通过。仅获准改标记时报告需拆分，不静默新增/删除行。

通用示例（表中重复公共值在支持的载体中纵向合并，具体限制从本次来源取）：

| 编号 | 标题 | 优先级 | 测试类型 | 测试数据 | 测试场景 | 期望结果 |
| - | - | - | - | - | - | - |
| FT-0001 | 超过条目上限不可保存 | P1 | 手工验证 | 已达上限，拟再增加一项 | 在页面尝试增加超限条目 | 页面阻止超限操作；有明确提示要求时按需求核对 |
| FT-0002 | 超过条目上限不可保存 | P1 | API 自动化 | 已达上限，拟再增加一项 | 绕过页面，直接提交超限条目集合 | 接口按契约拒绝超限请求，原有效数据保持不变 |

统计分开报告：业务规则组数、独立功能 Case 行数（按 FT 编号去重）、自动化执行分支数。一个业务规则的两行是两条不同检查的 Case；参数化分支通过数不是功能 Case 通过数，同一接口分支不得重复计作多个独立测试点。

### 修改后二次复核

用户修改后再次要求读取、评估或重新标记时，以在线表/文件最新内容为准，重新读取授权范围的全部 Case 和真实表头/下拉，含新增行与表尾；展开合并分类还原归属，按稳定编号定位，不能只读标题、旧标签或聊天记忆。比较当前标题、特殊前置、数据、场景、全部期望与来源；有旧快照则列实际变化，无快照不声称已做历史差异比较。本规则在本次调用中执行，不承诺后台监听用户修改。

逐条重判唯一测试类型，核对关联资产的当前版本、实际覆盖及验证证据，再按下节判断状态。发现混选或新增跨类型检查点时，按授权范围拆分，不通过删选项或删预期收窄覆盖，保留仍有效的链接和证据。

获准重新标记时，只更新测试类型、相应单选下拉、自动化状态及必要覆盖备注，保留用户改写的正文、编号、行序、资产链接和历史结果；备注追加本次差异，不覆盖无关记录。标记变化不修改/执行/发布真实自动化，不因旧链接失配自动删除绑定；只读请求仅报告建议。写前核对目标行未被再次改写，写后按编号回读值及覆盖说明，汇报变更与未决项，不将旧执行通过当作修改后通过。

### 自动化状态使用规则

测试类型根据本行检查点选择一种验证方式。自动化状态只根据本行已确认方式、可行性、实现和验证证据判定；同组其他行的类型、未执行或阻塞不改变本行状态。选择 API 或 UI 自动化后仍有关键条件未核实时，保留 `待评估` 并写明入口、断言依据或数据准备等缺口。已明确采用手工且本行暂无自动化建设工作时标 `暂不自动化`，不让相邻接口行等待手工行完成。

| 状态 | 何时使用 |
| - | - |
| 待评估 | 默认值；尚未核实自动化可行性或证据不足，不能仅因验证方式是 API、手工执行或当前未写脚本就推断其他状态。 |
| 待编写 | 已确认采用 API 或 UI 自动化，关键条件已核实，仍有已确认的自动化检查点待编写或待完成首次验证。排期可另行安排。 |
| 已自动化 | 已关联与本条当前全部必要检查点一致的真实自动化 Case/脚本，且完成完整执行验证；只有计划、链接、部分覆盖或部分步骤通过不满足，必要手工点未自动化时也不满足。 |
| 待修复 | 已有自动化因脚本、数据、前置、配置或契约适配问题需要维护；保留资产链接，在备注写明具体问题。 |
| 暂不自动化 | 已明确当前不实施整条用例的剩余自动化，且无待编写或待修复工作。备注说明原因。仅手工且尚未评估的用例仍为待评估。 |

旧表混合用例在获准整理时先按类型拆行，再按各行检查点独立判断状态。接口行完整通过后可记录通过及已自动化，页面行仍按自身证据记录未执行、阻塞等结果；不能因共享标题或公共字段而互相污染状态。拆行前的部分覆盖证据保留，但不作为新行完整通过的证明。

状态表达自动化建设情况。产品缺陷导致严格断言失败且已证实脚本正确时，按实际覆盖和验证证据定状态，执行失败如实记录。已完整验证但待审核发布时，可标已自动化并注明待发布。

用例表下拉使用上述五项。同步平台前，核实目标部署的字段契约、合法存储值及页面选项映射。无法确认映射时，保留已核实的表格标记，报告平台字段未能同步。写后分别核验平台存储值及页面选项识别和展示，按实际说明未核验项。仅凭接口保存或回读成功，不能认定页面支持该状态。历史状态仅在获准范围内按证据逐条转换。

### 四列分工

**以简明、可执行为准。每条只写决定本条测试分支和结果的信息，不把完整表单、通用准备或检查方法逐条抄进用例。**

| 字段 | 写什么 |
| - | - |
| 前置条件 | 执行人开始本条操作前需额外完成的特殊准备。没有特殊准备时留空。 |
| 测试数据 | 单独列出更便于执行或核对的输入、取值条件或对照数据。可在操作中直接写清的简单输入随场景说明。 |
| 测试场景 | 写决定结果的权限、状态、对象关系等条件，以及实际操作和必要顺序。即使条件提前建立，也在场景中说明它如何决定本次验证。 |
| 期望结果 | 写明在哪看到什么、保存成什么值、允许或拒绝什么；需求有明确提示文案时沿用原文。 |

- 先确定本条测什么，再删无关细节。非验证字段不指定示例值，按页面要求填写即可；会影响结果或触发其他校验的字段仍须限定，不能让执行人猜。
- 共同准备在确有执行需要时集中说明。同一信息写在最便于复现的位置。若某条件既需额外准备又决定结果，前置写准备动作，场景写本次使用的条件和操作。
- 独立导出的用例须携带确有必要的共同说明，不依赖其他用例或历史备注补齐条件；没有额外准备时不新增通用说明凑内容。
- 动作相同可使用同一句短描述，不为区分用例加长措辞。不同条件、路径及预期分别保留，不因文字相似减少用例。
- 只验证本条目标相关的结果，不机械追加全字段核对、其他记录不变或日志检查；这些本身是目标或必要风险检查时才写。
- 简短不等于模糊。保留决定分支的权限、归属、匹配关系、边界和顺序；动态数据说明必要取值条件，不固化历史值或凭据。预期不得只写“正常”“正确”“符合规则”。
- 步骤不用“按需求操作”“填写合法数据”“进行验证”等概述代替关键动作。已有测试数据可直接引用本行具体字段和值，不必整段复制；与目标无关的必填项可简写“填写其他必填项”。例如长度边界须说明哪个字段输入多少字符，权限用例须说明用哪个权限的账号执行哪个操作，不能只写“提交测试数据”。
- 预期不用“按权限显示”“配置回显正确”“符合原规则”“数据保持一致”等套话代替判断。写成可核对的对象、范围或值。预期随执行数据变化时，说明应与哪个已知输入或状态对照。
- 写出本条目标需要核对的事实：操作是否生效、哪些值应变化或保持、哪些记录应命中或排除。不得为补具体性新增需求未规定的提示文案、操作入口、限制或跨模块检查。异步流程仍须区分已受理与已完成，不能删掉必要终态判断。
- 入口、提示和机制须有来源。需求明确而实现缺失时保留预期；依据不足则记录具体疑问，不编造触发方式。

已有用例清理时按含义逐条判断，不用批量替换删除“权限”“保存”“一致”等词。通用前置可清空；真正影响复现的特殊准备须保留。同组连续、非空且含义完全相同的必要特殊前置可纵向合并单列；不同条件不合并，不为合并隐去差异或调换用例。

### 四列执行性自查

1. 前置是否只有登录、环境、灰度、独立数据等通用准备？是则留空；不能把真正影响复现的特殊准备一并删掉。
2. 不读源码、不依赖前后用例，结合本行场景和测试数据能否直接完成操作？是否明确对象、关键输入及多账号/并发操作顺序？
3. 预期能否直接判断通过或失败？“按权限”“符合配置”“与提交一致”具体指哪个对象、范围或字段；需要猜测时先改写。
4. 是否重复通用说明、罗列非验证字段，或机械追加全字段、其他数据、日志检查？能删且不影响本条目标和必要风险判断的就删。
5. 是否保留了触发分支所需的数据、关系、边界及顺序，且没有把步骤放入数据列？精简不能改变原测试目标或有依据的预期。
6. 需求有明确提示时是否原样沿用？文案较多时是否引用了准确位置和语种，而非笼统写“参考需求”？改写是否编造了提示、入口或业务规则？

### 预期原文与文案检查

- 需求已明确结果、提示或确认文案，直接取与本条相关的原文，不自行改写成“操作失败”“禁止操作”等概述。只有需求未给可直接使用的文案时，才据已确认规则简述结果，不编造提示。
- 原文中的标点、语种和动态占位符保留；动态值按本次数据核对。不复制无关整段，也不额外堆叠失败、数据不变等描述；确有独立验收要求时再补。
- 翻译或固定文案少且位置清楚时，场景写“切换何种语言、查看哪个位置或触发什么提示”，预期直接列对应原文。
- 产品已列出大量完整文案时，可按页面、区域或触发场景分组，引用需求中的具体文案表、章节及语种，不必逐词拆成大量 Case。预期可写“该区域文案与需求×节×语种列一致”；需求链接放关联来源，不能只写“参考需求”而不说明范围。
- 分组检查只合并同一检查范围内的文案，不混合独立业务分支；不规定条数阈值，也不为搬运翻译表机械扩增用例。更新已有用例仍保留执行记录，数量调整遵循本次授权。

### 需求关联与验收原文

- `关联用户故事` 回答“属于哪个需求”，放真实故事/需求标识及可用链接，不放验收正文；仅开发设计来源时在此如实标明，不冒充产品需求。多个来源的必要链接也放此列，不堆入验收标准来源。
- `验收标准来源` 只保留与本行预期最相关、足以在源文档中定位的一段连续原文，优先一个短句或分句。不要添加 `原文：`、`定位：`、额外包裹引号、文档标题、章节、编号或 URL；用户应能直接复制单元格内容搜索，不需手动删掉附加文字。
- 先读来源，再逐字摘录；有产品原文优先产品原文。不改写、概括、拼接不相邻片段，不用省略号连接删节内容，不人为增删标点或空格。选择保留关键条件、否定、范围及例外的最短有辨识度片段，不以完整长段或全文充数，也不截成无法定位的 `灰度逻辑` 等泛词。
- 摘录应可在原文中连续匹配；如果同一句确实支持多条 Case，可重复，不为去重编造措辞。不同目标应分别选对应原文，不整批套用同一段。
- 一个 Case 确需多个独立条款时，仅分行放最少必要的原文短句，各行均须可独立搜索；不要拼成一段伪原文。优先拆分独立测试目标，避免单元格长篇堆叠。
- AI 自主补充、仅代码现状回归或产品未明确的规则，没有直接依据时本列留空；必要疑问按既有规则记录到备注/问题表，不用推测、当前响应或自造编号补齐。已有来源只有编号/章节时回查原文；无法读取就保留原有真实引用并说明未完成整理，不编造短句、不声称已验证可搜索。
- 更新已有表时移动整列，保留各行内容、链接、公式、合并关系及其他样式；核对后补充原文，不把多行来源合并成统一结论，也不改动测试结果。

### 场景分类与合并

- 分类帮助测试人员回答“在哪里测→测哪个区域或能力→测哪类行为”，应能对应到需求对象、实际页面或接口能力。有页面归属时优先采用“页面→区域/组件→字段、操作、状态或规则”；没有页面归属时采用“业务能力→接口能力/入口/子能力→具体行为”。不把后台能力虚构成页面组件，也不为凑三级拆分不存在的区域。
- 名称使用需求、原型、实际页面或接口契约中可核实的称谓；代码只辅助确认映射。依据是“能找到该对象”，分类单元格不堆章节号、源码路径或长篇说明。来源未明确组件名称时，可用准确的可见区域描述，不编产品控件名；仍无法定位则保留上级分类、下级留空。分类依据不等于验收依据，预期仍按来源规则独立核实。
- 分类按被测对象和业务目标归属，不按执行工具分类。API 用例有明确的页面映射时，归入该页面对应的功能分类；只有接口本身的契约、认证或其他独立能力是目标时，才按接口能力分类。页面权限可归入对应菜单、权限树或操作区域；跨页面的权限、租户隔离、访问控制可按独立业务能力分类，不硬塞进单一组件。
- 同一被测对象、相同含义的分类统一名称，不因执行方式或措辞差异重复建组。独立的接口能力可单独分类，不仅凭名称相似就合并不同业务对象。
- 分类、标题、场景各司其职：分类用于对象分组，标题说明本条目标，场景写具体条件与操作，不整句互抄。不以整条标题充当三级分类，也不只写“字段”“操作”“状态”等无法区分对象的泛称。
- 同一组内保持层级口径一致：不要把页面、测试方式和优先级混放在同一级；共用组件按当前业务页面归属，跨页面完整流程按流程或能力归属。三列保留在标准表结构中，但内容不是必填；可只填一级或一、二级，不跳级、不凑三级。简单 Case 无分组需要时均可留空；具体条件和动作仍须在本条 Case 中说清，不能靠前后行或合并分类补齐。

新建或获准整理/重建整表时，先统一分类名称，再按“一级→二级→三级分类”集中排序，最后合并；各层按实际业务/页面顺序，同组内稳定保留原用例顺序，不因验证方式交错而打散同类。用户要求保留原顺序、仅局部改列/行或仅改分类文字时不自动重排整表。

重排须先还原旧合并区域中每行的真实归属，再移动完整用例行；编号、数据、预期、来源、结果、链接、备注、公式和样式随行保留，不只排序分类列、不重新编号。交付前按原编号核对内容和执行记录不变、数量一致、同义分类无重复且同类未无故分散；不能安全保全则保留原表并说明限制。分类及顺序核对完成后再应用以下合并规则：

- 支持合并的 Excel/飞书表格必须按层级纵向合并连续相同的非空分类：一级在同一业务分组内合并；二级仅在相同一级分组内合并；三级仅在相同一、二级分组内合并。名称相同但父级不同、含义不同或不相邻的分类不得跨组合并；空白不作为共同分类合并。
- 每次仅合并单个分类列，不跨多列合并，不覆盖不同值；不因分类相同合并用例行、编号、测试场景、期望结果或执行记录。先写全每行分类，再合并；交付前按行展开检查每条 Case 的分类归属仍可还原，且行数、内容未丢失。
- 载体不支持单元格合并时逐行保留分类值，并说明展示限制，不以清空重复值假装合并。修改已有表格前先检查旧合并区域，保留各行内容、公式和格式，再调整列序与分类合并。

## 展示规则

### 表头分组配色

支持样式的 Excel/飞书表格必须使用四种不同的表头背景色区分字段用途，同组同色，不再将所有列标题统一为一种颜色：

| 分组 | 表头范围 | 默认配色 |
| - | - | - |
| 功能用例 | 从 `用例编号` 到 `测试结果` 的全部标准列，含三级场景分类、前置条件、测试数据、测试场景和期望结果，不含验收标准来源 | 浅蓝底、深色字 |
| 需求与测试负责人 | `负责人`、`关联用户故事`、`验收标准来源`、`迭代/Sprint` | 浅紫底、深色字 |
| 自动化信息 | `自动化状态`、`自动化脚本链接`、`测试层级`、`验证类型`、`执行场景` | 浅绿底、深色字 |
| 备注与探索记录 | `备注/探索性记录` | 浅橙底、深色字 |

- 已有团队配色时可沿用，但四组必须清晰区分，组内统一，文字易读；颜色只表达字段分组，不表达通过、失败或优先级。
- 配色仅应用于表头，不整列染色，不覆盖数据区、下拉选项和测试结果的既有状态颜色。两行表头时，各层标题和合并表头沿用所属分组色。
- 根据列名及用途定位分组，不硬编码列字母；调整列序、插入分类列或合并单元格后，重新核对各组范围。默认不额外增加一行分组标题。
- 交付前回读表头背景及文字样式，确认四组均已应用；载体不支持配色或工具无法验证时，明确说明限制，不声称已完成配色。

### 内容展示

- 主描述使用测试人员可理解的语言。复现所需技术输入按用途放在测试数据或自动化字段，协议契约的检查项写入期望结果。
- 用户表格/下拉不写 `0=`、`1=`、`10=` 等内部映射，不用后端枚举作场景显示；中文业务值，代码仅明确需时藏参考/调试。
- 页面字段下拉与实际页面可见选项一致，不自行添加内部状态或来源未支持的选项；无指定/不可见则空。
- 显示干净值如 `P0`、`接口/组件级`、`正常场景`、`回归测试`、`生产回归`。
- 飞书多选回读可逗号文本，但单元格必须真实存 `multiple_values`。

## 分类说明

### 优先级判定

| 优先级 | 判定标准 |
| - | - |
| P0 | 需求的最小完整主流程，以及失败会使需求目标失效或突破关键安全边界的必要场景。 |
| P1 | 支撑需求正常使用的核心功能、重要替代流程和主要异常分支；不属于最小主流程或关键风险例外的必要验证。 |
| P2 | 需求边缘功能、次要组合、低影响边界和兼容展示场景。 |
| P3 | 极低频且影响轻微、有替代路径，可延后验证的场景。 |

- 先明确本需求必须实现的目标和最小端到端路径，再逐条判断该 Case 失败的实际后果、影响范围、发生频率及替代路径；不将所有核心功能都视为主流程。
- 主流程之外的必要负例也可能为 P0，如关键越权绕过或合法用户失去核心操作能力；必须有与需求相关的具体严重后果，不能仅因含“权限”“安全”“异常”就设为 P0。
- 同一功能、不同终端、角色、输入或边界组合不默认同级；只有独立风险足以达到同等影响时才同级。不将主流程的全部组合展开都定为 P0，也不因属于边界、负例或低频就机械降级。
- 不规定各等级数量或比例，不为减少 P0 而降级必要场景；P0 集中在大量相似组合时，复核其独立风险与定级依据。无需在用户表格增加定级说明列，除非用户要求。
- 探索性是测试方式，不是优先级；依据探索目标的风险定级，不能统一归为 P3。手工、自动化、暂不自动化或历史用例身份也不能决定优先级。
- P0 不等于冒烟集。冒烟另按执行用途选择少量、稳定、快速、能判断基本可用或是否具备提测条件的代表用例；通常以 P0 主流程为主，也可包含必要 P1，不把全部 P0 直接复制为冒烟集。用户明确要求全部 P0 时仍按其范围筛选，不擅自缩减或更改源优先级。

### 测试层级、验证类型与执行场景

- 按实际验证范围选层级。接口/组件级验证单个接口或组件。模块级验证同一模块内多个接口或组件的协作。端到端验证跨模块的完整业务链路。执行方式、步骤数、前置工具和目标比例均不决定层级。
- 每条用例的测试层级单选，表格下拉和值均使用平台中文文案 `接口/组件级`、`模块级`、`端到端`。旧表迁移按每条用例的场景、步骤和预期重新判断，尤其不能仅凭旧标签推断协作范围或端到端覆盖。平台列表的多选用于筛选多条记录。
- 正常：主成功、标准输入；异常：正常输入/身份/权限/数据/支持操作能触发的非法/业务错误，不含停服务、中间件故障、超时、强制5xx等注入。
- 边界：长度、数量、空、极值、分页、时间；权限：角色、租户、越权、未授权、隔离；数据：前置、状态、一致性、工厂、SQL；流程：多步业务、审批、任务、完整迁移。
- 回归测试：非生产稳定持续版本回归；发布验证：发布前后必验能力；冒烟：少量核心 API/路径快速确认。
- 稳定性监测：目的是确认生产服务持续稳定可用，及时发现服务不可用或关键功能异常；通过高频只读巡检实现，例如每分钟检查一次关键功能。只选轻量、可连续重复执行且无业务副作用的 Case，断言须验证服务或关键功能实际可用，不仅检查请求已发出；频率由定时任务配置。与常规周期的“生产巡检”按执行用途区分，不因只读就默认添加本标签。Case/配置不得有 SQL、数据库连接、工厂/清理或自定义数据库访问。
- 数据校验：非生产准确一致性；效果评测：AI/算法/搜索/推荐/生成质量，仅 Case 自身标签，任务不可选，动态任务即使含其他标签也排除。
- 生产巡检：只读无副作用健康检查，平台 Case/配置不含 SQL、数据库连接、工厂或清理。
- 生产回归：仅正式产品 API 控制、隔离、可恢复写，平台 Case/配置不含 SQL、连接、工厂或清理。
- 临时验证：一次性排查、联调、复现，可手工，定时不可选，动态任务含此标签即排除；稳定后移除此标签改正式场景。
- 性能测试：仅性能模块的负载/压力/容量/并发/吞吐/响应指标 Case，不因普通 API/UI/Pytest/功能含并发或响应时间断言就标；定时不可选、动态任务排除。

层级、验证类型、执行场景仅上述现行值，不保留/生成/写入额外值。

## 模块资产管理与归属

功能用例按业务模块沉淀，每模块维护自己的集合，历史按模块可查，迭代只增改新变化。自动化用脚本链接或平台 ID 回指功能行，手工/自动可追溯。多模块文档或共享库宜加模块字段。

`负责人` 负责功能设计、执行跟进、失败分析及持续维护；`维护人` 负责自动化失败与维护，与负责人不同时可加该列。

## 环境执行边界

按环境选择 Case、标签、数据与状态：

| 环境 | 用途 | 适合 | 不适合 | 目标 |
| - | - | - | - | - |
| DEV / 联调环境 | 开发自测、快反馈 | 新接口调试、单 API、异常边界 | 正式质量结论 | 尽早发现问题 |
| TEST / 测试环境 | 主要自动化回归 | 多数 API/集成/数据/回归 | 无法清理或破坏共享数据 | 完整可重复可排查 |
| PRE / 预发环境 / 仿真环境 | 发布前确认 | P0/P1、冒烟、主流程关键链 | 大量边界/异常/调试、重造数 | 发布前确认核心 |
| PROD / 生产环境 | 线上巡检、稳定监测、受控回归 | 正式 API、安全稳定、合适生产标签 | 平台任何 SQL 查询/写/断言、数据库连接配置、工厂、清理或不可控影响 | 无数据库风险发现异常 |

生产约束仅对 PROD。平台里的稳定监测、巡检、回归均禁止 SQL 查询/前置/断言/变量、生产连接、工厂前后置和自定义生产数据库函数；平台 `SELECT` 也禁，因为平台不应配置生产连接/SQL。巡检只读，回归仅正式 API 的控制隔离可恢复操作。DEV/TEST/PRE SQL 按环境策略和 Case 规则。

不禁止本地合法诊断读。本地已有授权有效生产连接可任务相关只读，限 `SELECT`，禁止 insert/update/delete/merge/truncate/alter/create/drop、可写过程或其他数据/schema/权限变化，不复制连接/凭据/SQL 到平台/Case。

核心：DEV 调试、TEST 覆盖、PRE 发布确认、PROD 安全巡检。

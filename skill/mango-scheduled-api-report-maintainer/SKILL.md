# 定时任务 API 报告排查与修复

## 适用范围

只处理用户指定报告或项目产品中，**定时任务生成且已完成报告的失败 API Case**。即使是同 Case，也排除手工、临时及其他非定时报告；失败数量/结论不含UI/Pytest。

平台读写只经 mango-test-platform MCP，禁止平台SQL、ORM、shell、直接HTTP或service绕过；业务代码可读作契约，不在本 Skill 改后端。

已有/应迁入工厂，或工厂实体/模板/绑定/执行/清理异常导致失败时，工厂属于修复范围；尝试对应修复前不能仅说“数据工厂有问题”或无法修复。

必须通过 MCP 获工厂 Skill，不读本地同级目录：用 `list_mcp_skills`/目录，按当前 name/title/category/description 解析 `mango-data-factory-builder`，用 `get_mcp_skill`/资源完整读取；部署有别名用目录真实规范名。调用工厂写工具前，完整读 MCP 提供的 SKILL及本次路由引用。

任何修改前读 [修复流程](references/repair-workflow.md)；终态涉及标签或调度资格变更时还读 [资产治理](../mango-test-platform-asset-governance/SKILL.md)。

## 目标范围与项目产品核实

- **明确报告 ID：** 用户在本请求或活动上下文提供明确的报告 ID，或含明确报告 ID 的链接，即可通过 MCP 读取该报告，无需再提供项目产品名称或 ID。依据平台返回的正式关联核实所属项目产品、定时任务来源及报告状态，不把读取权当作修复/执行授权。
- **严格限定指定 ID：** 只排查用户明确指定的报告 ID；多个 ID 则仅处理这些 ID。可读取定位根因所需的关联任务、Case、原版本和历史证据，但不把其他报告纳入失败数量、修复或重试范围，不自动扩成同任务最近报告或整个产品。用户仅说“排查”时保持只读，不修改、上传、执行或重试。
- **未提供报告 ID：** 用户须明确给无歧义项目产品名/ID，才能按下文任务、名称或产品范围选报告。两者均缺失或目标类型有歧义时，只问缺失的报告 ID 或项目产品信息，不猜测 ID 是报告、任务还是 Case。

平台权限与项目产品数据范围仍须校验；报告不存在、无权访问、关联缺失或与用户明确给定的产品不符时，说明具体问题，不绕过、不擅自换报告或产品。未明确报告 ID 时，不从报告/任务名、平台当前选择、仓库名或同名资产猜测产品。

## 默认修复路由与确认

目标范围核实后按用户授权进入流程，不让用户例行选择诊断/修复：

- **明确直接修复：** `修复`、`直接修复`、`修复失败 Case`、`处理到终态` 或同等明确授权，立即进入连续修复，不预先/例行续批确认，不上传前置诊断；批次有至少一项 `是否修复成功=否` 才传结果文档，全成功不传。
- **确认后修复：** 写入授权不明确时，先只读诊断整个范围，在对话中给出确认表。诊断附件上传须另有明确授权。确认后连续处理授权范围，用户仅选子集或一批时按该范围执行。
- **明确只诊断：** `排查`、`只排查`、`说明原因` 或仅诊断文档要求保持只读，不变修复；用户要文档才上传。

修复授权覆盖确定范围的安全资产修改、验证、提交预发布，以及用户手动发布后原失败行的精确重试；不授权 AI 正式发布 Case，即使具有发布权限也不例外；必要 API Info 可按接口验证与发布规则直接发布。批次是检查点不是新批准点；未限制则自动处理完整范围。扩围、删除/取消发布、正式缺陷及其他破坏动作另走授权。

### 不反复询问继续

授权后不问 `是否继续修复/验证/下一批`。独立用安全能力修前置、工厂、可见性/索引、清理、请求变量及有据断言。模板停用、普通数据缺、方案未完、首次失败、耗时长都是待完成工作，不是结束/丢给用户理由；进度不等于要批准。

从名称、场景描述/名称、原请求断言、不可变失败版本、历史、需求文档和源码确定目标，记录资产错误、证据、安全修法及原业务错误仍能检出。不把旧断言当目标，不用空成功覆盖非空数据目标。

穷尽上下文/附件/历史/代码/MCP后，仅对不可替代标识、无法访问凭据权限、未决产品决定、扩围/破坏授权问具体问题，说明缺项及已查证据，继续独立项。缺权限或未明契约本身不证明Bug/外部条件。仅参考4.5已证外部专属前置可收敛为 `需要外部提供测试条件`，非成功。

### 异常前置先处理，不重新确认测试范围

用户已授权的有效场景默认继续测试。功能关闭、身份权限不足、任务占用、前置不完整或清理复杂，不构成重新询问“还测不测”“是否继续”“要不要删除/取消发布”的理由。按 [修复流程第 4.6 节](references/repair-workflow.md) 逐类完成取证、安全修复或具体外部条件交接；下游 Case/数据工厂 Skill 不得将原范围内、同一安全类别的常规修复重新变为方案选择门禁。

可通过已有合法身份、变量/请求/工厂配置、本轮隔离数据、失败安全清理及有界等待完成的，直接修复验证。普通测试配置仅指上述已授权测试资产配置；不包含开启共享功能/灰度、修改角色/租户权限、部署或服务运行配置，不得借“自动修复”扩大权限或操作范围。

确已证明必要条件只能由管理员/外部提供，且已有身份、允许的配置和安全替代都不可用时，可收敛为“需要外部提供测试条件”。一次集中交接具体提供方、条件、影响范围、证据、替代方案排除及恢复验收步骤，不要求用户重新证明场景是否值得测；不因未发送申请就永远拒绝此结论，也不擅自代发申请或改权限。真正冲突且现有证据无法决定的业务问题才请求具体决定。

同一缺项关联多个 Case 时合并交接并保留全部 ID/原失败行映射，继续独立修复。后续巡检复用已交接的条件记录，仅核实是否变化；未变化不反复提问、申请或重跑同一失败。条件到位后恢复原测试目标和原报告环境验证，不把换环境的一次通过当作原报告修复成功。仅发布审核仍走既有人工交接。

## 确定目标

- 精确报告 ID（含链接中的 ID）：直接读取并核实归属、定时来源及状态，只用指定报告；不要求补产品名，不自动选其他报告。非定时停止。
- 无歧义报告名：在已明确项目产品内定位，只用该报告；非定时停止。
- 任务ID/精确名加时间：选区间内已完成报告。
- 任务明确无时间：默认最近5份已完成，并说明。
- 名称歧义：列候选请选。
- 仅项目产品无报告/任务/时间限制：经MCP枚举该产品定时任务及已完成报告，分页取尽全部可用失败API记录，排非定时；说明实际保留与时间覆盖，不悄悄换最近一份/一个/五份或自定天数。

每报告先核定时关联，保留任务ID。MCP无法证明来源则不纳入，报告缺口。任务仅报告选择源，修报告不授权触发/改任务。环境以失败报告元数据为准用于验证重试，不用当前所选环境替代。

## 不可变失败基线

诊断/修改前记录：每报告任务ID/名、报告ID/名/时间；环境、Release/Revision、状态；失败 `test_suite_detail_id`、Case ID/名、步骤场景ID、错误；去重Case数与失败行/单元数。

基线前读尽全范围分页，Case按ID去重但保留每报告/失败行用于证据及精确重试；不以首页/首任务/首报告/一批当全清单。分开报告 `失败 API Case 数` 和 `失败执行单元数`（依平台粒度解释）。基线不被当前编辑态或后续版本替换。

## 强制处理模型

根因分类不是完成。有效场景需区别安全可修资产与已证产品/平台问题，修复阶段每个有效失败 Case收敛为一项：

| 处理结论 | 判定 | 必须动作 |
|---|---|---|
| `修复成功` | 测试资产已修正且没有削弱覆盖 | 完整验证编辑态并提交预发布，用户页面手动发布后核验版本，再精确重试所选原失败行 |
| `需要业务开发修改代码` | Case、数据、身份、目标环境和测试平台均正确，权威契约明确，实际行为违反契约，根因已定位到被测产品代码，必须由业务开发修改代码并重新部署 | 保留 Case 和断言，不重试未变化资产，并输出可直接交给业务开发处理的代码缺陷反馈 |
| `需要测试平台修复` | Case 和场景有效且产品行为不是根因，但已证明测试平台存在缺陷或缺少必要能力 | 保留 Case，输出平台缺陷或能力需求、复现步骤和验收标准，仅执行已明确授权的临时调度缓解 |
| `需要外部提供测试条件` | 场景有效，已穷尽安全查询、构造和受支持替代方案，必要数据、合法身份、管理员放行或外部状态只能由指定外部提供方提供，未证明产品或平台 Bug | 保留 Case 和严格断言，一次集中输出缺项、构造不可行证据、已尝试方案、提供方及精确恢复验证条件；继续处理其他 Case |

修复未成功仅三种：需要业务开发修改代码、需要测试平台修复、需要外部提供测试条件。第三种不是Bug/数据难找兜底，须参考4.5证据。普通数据、模型/模板、前置清理隔离账号配置及文字旧断言仍需修；不以方案待完/尚待验证结束，证据不足继续，不伪归责/成功。

已证正式废止场景单独交治理，保留待授权删除/取消发布建议；不是Bug，不混有效场景结论、不改简单查询伪修复。报数量和证据，未授权不删覆盖。

## 只读诊断

用于明确只诊断或两阶段首段。仅查询取证并汇报，平台附件仅在用户明确授权上传时写入。

### 全量门禁

诊断不截断数量：取尽每分页、每不同失败API Case。可内部只读分块，但最终表/文档全列，不受修改批次上限、不抽样、不隐瞒延期。最多50只限制授权后的每修改批，不限发现/取证/文档/确认表。

### 取证

逐Case：读失败行及原版本；完整当前编辑态/Release；同环境步骤场景历史；请求/头/变量/Info协议体类型/断言提取/前后置工厂；仅按需读controller/DTO/service/mapper/API文档建立契约；分开事实推断并脱敏；分类根因与可修性，不复述报错。

只用下节页面标准原因，不另建分类；证据缺口为待判定，不用其他原因凑齐。

## 报告原因类型与 MCP 回写

分类前读 `get_test_report_schema`，以 `enums.failure_reason` 的 `value/label` 为准，页面和MCP共用：

| value | 页面名称 | 适用证据 |
|---|---|---|
| `product_pending` | 产品缺陷待修复 | 已证明产品代码违反契约，等待开发修复 |
| `product_accepted` | 已接受产品缺陷 | 用户或业务方明确决定接受已确认缺陷，不因暂未修复自动使用 |
| `test_case` | 测试用例问题 | Case/API Info、断言、变量、前置数据或数据工厂配置错误 |
| `platform` | 测试平台问题 | 已定位平台、执行器缺陷或必要能力缺失 |
| `environment` | 环境／依赖问题 | 已确认目标环境、外部依赖、部署或环境身份条件异常 |
| `other` | 其他原因 | 已有明确根因但不属于上述类别；说明具体证据 |

`原因类型` 是原根因，`处理结论` 是修复结果/动作，不是第二原因枚举。普通配置/工厂准备和请求头错误属 `test_case`，非 `platform`；真实环境/身份条件属 `environment`；契约已变的旧断言属 test_case，不自动 product_pending。

已授权修复或明确授权记录诊断后：

1. 读 `get_test_report_case_detail(test_suite_detail_id=...)`，核报告产品环境及具体执行项，不能传Case/步骤/场景ID。多报告逐项。
2. 原因/说明冲突保留并问明确覆盖授权，相同则已记录；不以不完整证据覆盖有效结论。
3. 调 `update_test_report_case_diagnosis(test_suite_detail_id=..., failure_reason=<canonical value>, failure_description=...)`。说明非空且最多1000字符，含根因、最强证据、真实修复重试结果、后续，脱敏。修成功可保原类型，但说明须明确已验证成功，不暗示仍失败。
4. 回读核两字段，确认 `is_excluded` 和执行结果未变。逐执行项报回写成败，权限/迁移失败不算保存，不授权SQL/HTTP绕过。

精确重试清空字段，须在要求的重试**之后**写最终结论，不仅写前就宣称保留。新失败先核新证据，不套旧诊断。报告运行中不写，先完成/核验。

需 `report:exclude` 和项目范围。默认仅记原因/说明，不传 `is_excluded`，不自动排除、改执行结果、通知或调度。无回写授权只读保持只读；两阶段确认前不写，除非另明确授权诊断记录。普通准备仍修，不泛称需人工确认；只有真实授权/访问/业务决定才问。

### 排除统计开关（仅明确授权时修改）

同一个 `update_test_report_case_diagnosis` 支持可选 `is_excluded`。工具参数和页面开关的含义为：

| MCP 参数 | 页面开关 | 含义 |
|---|---|---|
| `true` | 开启排除统计 | 整条报告执行项不再参与有效总数、失败和成功率计算；仍显示已排除数量，原始结果、失败数、原因和说明保留 |
| `false` | 关闭排除统计 | 恢复该执行项参与统计；原本失败仍按失败统计，不代表已修复或已重试通过 |
| 不传或 `null` | 保持现状 | 只更新原因和说明，不改变现有开关；这是 MCP 的保留行为，不是页面的第三个开关选项 |

只有用户明确授权排除或恢复确定范围的历史报告记录，才传布尔值。取消发布、解绑或授权修复 Case 不自动包含历史记录排除授权，不为报告变绿自动排除。先核实项目产品、报告和 `test_suite_detail_id`，按报告执行项逐条操作；同 Case 的其他报告、未取消发布的 Case 及其他失败不扩围。原因分类按已查证根因选择，不把取消发布当成固定原因类型。

修改后读回 `is_excluded`、原因、说明与原始执行结果，确认没有删记录或把失败改成通过。排除作用于整条执行项，可能包含多个步骤/场景。已发送通知不会自动更新；重发须有对应授权。部署工具参数中没有 `is_excluded` 时报告版本缺口，不绕过 MCP 改库或调用私有 HTTP。

### 两阶段确认表

完整范围每个不同失败Case一行：

| 执行报告 ID | Case ID | 任务环境 | 执行场景 | 排查结论 | 证据 | 建议修复内容 | 建议处理结论 | 建议批次 |
|---|---|---|---|---|---|---|---|---|

证据/动作具体，不写接口异常/尝试修。建议为修复成功或三个未成功结论，证据不足写待判定及下一证据；建议不是已修完。全部分最多50个ID批，如已获准上传并完成回读，附上传目标和附件标识。问一次 `是否确认按表中范围和建议动作开始修复，并分批连续处理？`，范围未缩则含全部，不再批间确认。

### 文档上传

用户要求交付诊断文档时，读 [报告模板](references/report-template.md)，本地UTF-8文件名含产品/范围/时间。含来源、实际保留时间、计数口径、报告概况、全不同失败Case、证据根因、可修性、建议动作/批次/风险。

用户明确授权上传时，调用 `upload_scheduled_task_diagnostic_markdown` 写入已核实的任务；多任务附件各限定自己报告并报全部目标，不将全产品文档挂无关任务。回读元数据，完成需本地路径、成功、附件ID名、精确目标；失败不称完成。

## 修复执行

本 Skill 的 Case 也只允许提交预发布，不作为 AI 正式发布 Case 的例外。完整验证及清理合格的 Case 提交预发布，由用户或产品负责人到页面手动审核发布，不通过其他方式代替用户审核。API Info 不走 Case 的预发布审批：已授权修复范围内，完成自检、验证和修订后，有接口发布权限即可直接发布并回读版本，继续 Case 绑定/验证；无权限才交接。

待发布不阻其余修复：预发布无权限或不支持时保留已验证草稿/修订，记录拒绝和实际状态，不反复尝试或求提权。所有已验证但未由用户发布的资产，统一单列 `已验证，待用户手动发布` 交接，保留 ID、候选修订、状态、验证/清理证据及原报告精确重试行。它们不是产品/平台 Bug 或修复失败终态，也不能提前称“修复成功”。该交接阶段优先于后文仅终态的表格要求；清单非空不得称全部修复。

### 手动发布交接与恢复

- 每批及完整范围汇总时，列出待发布 Case 的 ID、名称、候选修订和实际状态，并在表格之外额外提供一行可复制 ID：只含真实 Case ID，以英文逗号连接、无空格，不混入名称、报告 ID 或修订 ID；按首次出现顺序去重。格式示例：`1,3,222,12`。没有待发布 Case 就不输出示例或空清单。
- 每次输出待审核/发布清单时，必须在可复制 Case ID 行后明确提醒：`请复制以上 Case ID 到用例页面查询并审核发布。审核发布通过后，请回到当前 Skill 对话框回复“已审核发布，请重试”，也可以附上已发布的 Case ID。我会核验发布版本，再逐个 Case 精确重试原报告中的失败记录；审核通过不代表报告已重试，重试完成后才算修复闭环。` 不得只给 ID 或只说“待发布”，避免用户忘记返回对话继续重试。API Info 有权限时验证后直接发布；仅因权限不足而待发布时，单独列出其 ID 和依赖顺序，不混入 Case ID 行。
- 待发布期间继续所有独立修复及后续批次，不反复问是否允许发布；无其他可推进工作时交还用户，等待手动发布。保留全部批次的待发布清单及报告行映射，不能只给最后一批。
- 用户确认已发布后，通过 MCP 回读每个 Case 的正式发布状态及精确 Revision/Release，确认对应已验证候选；只恢复已核实发布的 Case，未发布或版本不匹配项单列说明，不重新修复或重试旧版本。若候选内容发生变化，重新验证后再交接发布。
- 没有修改测试资产、只因用户已修复产品/环境而要求重试时，不强制新建修订或再次发布；核实当前正式版本和重试授权后直接精确重试。

修改前完整读 [参考流程](references/repair-workflow.md)。总数可超50，单批最多50去重Case；同Case多报告共一Case，保留全部失败行。

每Case先按名称/场景/描述/配置、历史契约核定前置→动作→结果。文字缺失矛盾先补证据，不立即问；只有不可替代业务决定才问。

必须流程：

1. 选本批最多50个Case。
2. 快照不可变失败与当前完整Case/Info。
3. 核测试意图。
4. 依报告、配置、历史、源码查根因。
5. 有据安全可修则实施含MCP工厂/精确清理；否则继续隔离真实产品/平台问题，前置清理难不授权退调度或归Bug。
6. 回读覆盖无减、报告环境完整通过后提交预发布，输出待手动发布的 Case ID；用户发布并核验候选版本后，仅精确失败 `test_suite_detail_id` 重试，全部通过才称修复成功。
7. 业务代码Bug保留Case/断言，不重试未变化资产，输出开发反馈；正式缺陷另授权。
8. 已废止单列治理证据影响，删除/取消发布另授权，不叫修复失败Bug。
9. 平台问题须穷尽支持流程并证明；外部条件须参考4.5证明专属提供方和恢复条件，继续独立项，不造签名凭据/外部结果。
10. 回读修复/重试/治理，更新历史与治理口径；精确重试后逐执行项写回最终原因。
11. 报检查点并自动下一批，只有用户范围限制、完成或真实例外才停，不泛问继续。

直接修复/确认表授权只覆盖具体 Case 的验证、修订及预发布交接、手动发布后精确重试与列明终态动作；结构调度变更仍预览/token。不授权 AI 正式发布 Case、弱化、删覆盖、整报告重试、触发任务、删 Case 或正式缺陷。

## 不可放宽的门禁

- 不为报告绿删/停/解绑/合并/跳过/替换Case步骤场景。
- 未确认测试点不改断言，不迎合错误响应。仅目标保留且controller/DTO/契约/更强历史证明旧错才改。
- 改前区分描述/契约目标与断言实际检错，对同一响应比较旧新判定，记录每差异、失去/新增检错，修改前披露依据，按参考决策表和提交门禁；不能凭文字不变或通过称覆盖不变。
- 记录旧新、依据、原目标与实际检错能力是否分别保留，最终逐Case说明。
- 业务开发结论须权威及具体源码路径证明必改重部署；资产/数据/账号权限/环境配置/部署漂移/第三方暂态/未定位异常不满足，继续证据。
- 过时资产有据修且不削安全；废止独立治理，冲突先调查，仅未决不可替代决定才问。
- 平台结论须已定位代码Bug或证明安全能力不存在；失败一次、不熟工具、停用配置或工厂不完整不够。
- 外部条件须证明专属来源并穷尽上下文、API、允许SQL、工厂、业务准备、忠实替代；一次空查、缺模板、未经检查的权限缺失、清理未完或契约不明不够。已证明只能由管理员提供的合法身份或功能放行按第4.5/4.6节交接，不要求先执行无权限的修改或发送申请；一次说明提供方/交付，不称Bug或通过。
- 工厂停用/无效/过时/失败是修复内容，按MCP Skill修实体模板绑定执行清理；仅证据证明平台才报平台，无权限/schema/业务证据继续获取，不造其他结论。
- 不写死环境业务ID、存量名码、身份或预期；请求/断言/SQL脚本/工厂覆盖/清理改为全局公共表达式、合格运行查询、提取缓存、本轮隔离造数，核租户/归属/状态/可见/原目标。不粘贴解析值、不回退历史；契约常量/故意非法边界允许；删除清理只本轮不删共享。
- `content[0]`、`LIMIT 1`、`TOP 1` 必须已证完整资格和排序。
- 完整编辑态未在报告环境通过不发。
- 不用整报告/任务重跑代替 `retry_test_report_case(test_suite_detail_id=...)`，不重试已成功行，不仅单步成功称修复。
- PROD平台无SQL、生产连接配置、工厂和不安全副作用；执行重试前读全树。本地已有授权生产连接可平台外只读 `SELECT`，不写数据/schema/权限，不复制连接凭据SQL到平台。

精确变更需预览/token则原授权下先预览原样传递，不因token另问；新增影响/破坏需真授权。无安全能力先核工具目录/替代，给有据平台反馈，不绕过、不停独立修复。

## 完成输出

### 只诊断

报范围、实际保留时间、报告ID、失败Case/单元、根因/可修分布、建议终态和缺证据。每不同Case一行用确认表，未规划批次可 `—`；如已生成本地文档或获准上传附件，分别报告实际路径或附件标识。建议不代表已修、退调度或建缺陷。

### 修复结果

每批紧凑表：

| 执行报告 ID | Case ID | 任务环境 | 执行场景 | 修复内容 | 是否修复成功 | 失败原因 | 处理结论 |
|---|---|---|---|---|---|---|---|

填真实ID、环境、具体场景动作或 `未修改资产`、`是`/`否`、唯一结论。成功失败原因 `—`，未成功原因是证明责任结论的证据；原失败根因表后单述。不用无法修复/已阻塞/已退出调度笼统结论。

再报历史原失败Case/行/单元；四种处理数量，调查未完不结束批（完成时为0）；仍可调度Case数；前后Case/步骤/场景及删停解绑数；仍调查项及下一证据（非终态）。

只有完整验证、发布、全部要求原行重试通过才 `是否修复成功=是`，描述变更/资产/执行/修订Release/重试。产品平台报证据、已试修、责任、验收重试；外部条件报缺项、专属证据、穷尽替代、提供方、交付、清理、恢复验证/重试，成功为否，诊断完成不等修复完成。真实写明动作，正式缺陷/破坏退役另授权，废止单列。

直接修复每批有任一 `是否修复成功=否` 才生UTF-8结果Markdown，含必需表、证据、实改、未修结论/责任/下一步/验收，按任务报告范围上传并回读；全成功不生/不传。两阶段修复的结果附件仅在用户明确要求上传时写入。

每批报结果与下一最多50候选/动作进度，自动继续授权范围；用户仅一批/指定ID则不扩。

无下一候选时跨全部批最终收口：

- 先单列跨全部批次的 `已验证，待用户手动发布` 清单及可复制 Case ID 行，并按“手动发布交接与恢复”的固定话术提醒用户审核发布后返回当前 Skill 对话框，以恢复逐个 Case 的精确重试。它们不混入三个修复失败责任结论，但属于尚未闭环项；即使没有其他失败项，也不能宣称全部修复成功。
- 任一未成功，列 `全部未修复成功项`，不得仅末批；沿用 `执行报告 ID`、`Case ID`、`任务环境`、`执行场景`、`修复内容`、`是否修复成功`、`失败原因`、`处理结论`，后逐项责任、动作、验收；结论仅三个未成功项。
- 全成功明确 `所有失败 Case 均已修复成功，无未修复成功项`，可不出空表。
- 说明所选范围无剩余批次，无候选不问继续。

不夹无关排除数据，不编用户未给过滤条件。

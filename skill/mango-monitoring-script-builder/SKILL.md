# 监控脚本编写与修复

平台资产操作只使用监控 MCP 工具，不通过 SQL、ORM、shell 或直接 HTTP 绕过工具权限。普通业务监控脚本不是通用数据库查询工具；不得用脚本、日志或通知绕过平台 SQL 工具限制或提取平台凭据。

开始编写或修改前：

1. 调用 `get_monitoring_script_context`，读取执行节点实际心跳中的依赖信息，以及本次部署返回的规则。不要用 MCP/Web、本机 Python 的包清单代替 monitoring 节点。
2. 读取 [编写与验证指南](references/writing-guide.md)。需要模板时从该文件选择普通脚本或平台 MonitorBase 模板。
3. 新增先明确项目产品、用途、目标环境和检查条件；编辑、排查必须先 `get_monitoring_task` 回读指定 ID 的原配置、完整代码，必要时读取 `get_monitoring_task_logs`。目标不明确或不可访问时，询问 ID/环境或让用户提供脱敏脚本，不猜测修改别人的同名任务。

依赖状态：`available_on_all_online_nodes=true` 才表示所有当前在线执行节点均报告该常用包可用；`false` 表示至少有节点报告不可用；`null` 是未确认。该工具不是完整包目录，未列出的包不能直接判定缺失或支持。无在线节点、旧节点未上报或节点清单不一致时，明确验证边界，优先选择标准库，不安装新依赖。

缺包时，先依据实际日志确认 `ModuleNotFoundError`，再选择已确认的替代包或标准库；保持输入格式、返回数据、空值、异常处理和业务判断语义。不能等价替换时说明影响并请求方向，不静默删功能，不以预装依赖为由安装或升级环境。

只提交用户要求的修改。`update_monitoring_task` 只传变更字段，保留项目归属、通知配置及其他未修改字段；保存后回读核对。保存不启动任务，运行中的代码不热更新。启动、停止、重启、重发通知均不能从“编辑/排查脚本”中推定授权；明确授权后才调用 `control_monitoring_task`，重启需先停止并确认状态后再启动。

结果说明区分：已保存、静态检查通过、启动请求已接受、实际运行成功。运行验证须确认目标脚本在授权环境的状态和日志；不能仅以接口成功或空日志认定成功。缺少真实执行环境时可完成静态修改，但明确尚未运行验证。

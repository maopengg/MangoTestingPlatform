# 根据代码创建 API 自动化用例

## 目标与边界

API Case 验证后最多提交 `预发布`，即使有负责人权限也不得代用户正式发布；无预发布能力/权限则保留验证草稿/修订并继续独立 Case。API Info 不走 Case 审批，在已授权创建/修改范围内，按 API Case Builder 自检、验证并生成修订后，有权限即可直接发布及回读；无接口发布权限才保留修订交接。仅扫描不授权创建或发布真实资产。

以已审核功能 Case、需求和验收标准为主要依据；代码用于发现遗漏边界、异常、状态、副作用和回归候选，不能单独证明产品正确。

每个业务相关分支必须且只能有一个归属：

- `HTTP API自动化`：单服务 API 契约或服务自身持久化；
- `单元测试`：HTTP 以下隔离的函数/类行为；
- `集成测试`：跨真实服务、消息、worker、第三方、分布式事务或最终一致性。

`Gap` 是来源、触发、判定、可达性、环境控制或清理尚未查清的分析缺口，不是第四种测试归属，也不直接代表不适合自动化。

本 Skill 记录单元/集成归属，除用户明确扩围外只实现 HTTP 自动化。静态映射不是运行分支覆盖；只有版本匹配的 JaCoCo、`coverage.py --branch` 或等效插桩才能证明运行命中。

以下维度独立：

- `依据分类` 仅 `功能用例已核验`、`设计已核验`、`代码现状回归候选`；集成不是依据来源。
- `test_ownership` 仅 `HTTP API自动化`、`单元测试`、`集成测试`。
- `scenario_layer`：`0` 接口/组件，`1` 真实集成，`2` 完整业务旅程。
- `scenario_type`：`0` 正常，`1` 异常，`2` 边界，`3` 授权/租户/范围，`4` 映射/一致性/质量，`5` 流程/状态/编排。
- `scenario_tags` 必须至少一个平台执行场景，表达整个 Case 适合的用途。逐 Case 审核全部支持标签，核对业务目的、关键性、完整请求链、身份、副作用、数据、隔离、清理、断言和调度，工作/交接证据保留逐标签依据。非生产按已证行为，生产须完整 Case 安全证据；当前所选环境可切换，不能单独决定可行性。
- `current_status`：`pending_create`、`completed`、`deferred`，不用 Gap 当流程状态。
- `execution_result`：`not_executed`、`passed`、`failed`、`partial`、`not_applicable`，遵循后文状态规则。

`ApiCase完成率 = completed / (pending_create + completed)`，排除 deferred，不能称代码或分支覆盖率。

### 链路未完成与暂不编写原因统一说明

以下六类用于普通语言汇报和现有备注，不新增平台枚举、状态或字段。原因、测试归属、链路解析状态及 Case 当前状态必须分开；接口内只有部分场景受影响时，只标记对应范围，不把整接口一概排除。

| 原因类别 | 适用证据 | 必须动作与恢复条件 |
|---|---|---|
| 链路未解析 | 动态分派、具体实现、路由映射、异常、异步或清理路径尚未查清；有前端但调用关系未确认也属待取证，不等于无调用 | 继续查代码和关联资料，记录缺失边界、已查范围和下一步；缺失路径/映射核实后恢复。不能凭未查清认定不适合自动化 |
| 测试依据未明确 | 对业务正确结果存在实际冲突，或缺少决定关键预期的依据 | 先补需求、已审功能用例及契约证据，穷尽后仅询问必要业务决定；依据明确后恢复。仅缺需求文档、但代码事实完整时可以保留“代码现状回归候选”，不能一律判为不可自动化或冒称验收已核验 |
| 无页面调用 | 项目有前端，已核实相关页面/客户端均未调用该接口 | 接口清单仍上传，暂不编写真实 ApiCase；页面接入并核实调用后重新评估。无前端项目不显示此项，调用关系未知不能使用 |
| 涉及禁止修改的配置或权限 | 代码证明会修改环境/服务配置、灰度、额度权益、角色或授权关系，包含前置及清理中的间接修改 | 按禁写边界排除写场景，保留安全只读查询和证据；可分离为不触及禁写的业务路径时再评估。不以测试环境、隔离或事后恢复豁免禁令 |
| 不属于当前 API 自动化职责 | 目标是 HTTP 以下的独立单元行为，或用户未扩围的独立集成测试职责 | 保留真实测试归属和推荐验证位置，不创建 ApiCase、不称该层测试已完成；用户明确扩围且满足对应条件后再实施。不得仅因有数据库或工厂前置就归为集成测试 |
| 缺少必要测试条件或平台能力 | 业务行为和预期已知，安全查询/构造、现有身份、合适环境和清理方案已评估，仍被已证实不可替代的外部条件或平台必要能力阻断 | 说明具体缺项、提供方/平台职责、已排除的方案及验收条件，条件或能力到位后恢复。区分只能外部提供与平台缺陷/能力缺失，不能只写“缺数据”或“平台不支持” |

前两类属于“待分析/待取证”，不是已证实的自动化排除结论；后四类只有证据充分才属于“已确认暂不编写”。本轮尚未分析、排队未轮到、工作未做完仅是进度，不得填写为排除原因或通过排除分母提高完成率。仅首次盘点未做链路分析时直接说明“尚未分析”，不伪造内部 Gap。

缺工厂实体/模板、变量或提取未配、普通前置/文件未准备、清理方案尚未设计，以及当前环境不合适，都属于继续实施工作；不能直接归为第六类。先使用现有安全能力修复，能切合适环境的按原规则处理，不修改禁写配置或权限。

每个受影响项至少记录 `原因类别；具体原因；证据及已查/已尝试范围；下一步动作；恢复/重新启用条件`，通过已有接口说明、Case 的 `payload.remark` 或事实台账承载，不造占位 Case 或额外原因枚举。多个原因选择直接阻断的主因，必要次因补充说明，不把其他未完成项全部改成同一理由。

实际状态仍遵守平台契约：链路缺口按已有 Gap 字段记录，未决证据不标链路完整；已有未绑定场景在平台仅支持三态时可暂存 `deferred/not_applicable`，但备注必须明确“待取证”而非“已确认不适合”，汇报分列两类数量，不用 Case 完成率替代项目接口分析完成率。待实施但可安全完成的保持 `pending_create`；已有绑定及历史不因分类而静默清空、降级或删停。更新状态、完成统计或交接前按本表复核。

### 代码扫描流程的执行场景限制

本限制仅适用于本 Skill 的模块覆盖场景及其创建、复用和交接的 API 自动化 Case，不修改平台全局标签，也不限制其他 Skill 的专用流程。

| 允许选择的标签 | 平台值 | 选择条件 |
|---|---|---|
| 回归测试 | `routine_regression` | 可在非生产环境稳定重复执行的功能回归 |
| 发布验证 | `release_verification` | 属于版本发布前后的必验能力或变更范围 |
| 冒烟验证 | `smoke_verification` | 精选的核心入口和主链路，不给全部 Case 默认添加 |
| 数据校验 | `data_verification` | 在非生产环境验证数据准确性或一致性 |
| 生产巡检 | `production_inspection` | 完整 Case 满足生产只读、无业务副作用及全部生产安全边界 |
| 生产回归 | `production_regression` | 完整 Case 通过正式业务 API 执行，数据隔离且可恢复，并满足全部生产安全边界 |

**禁止选择**：临时验证（`temporary_validation`）、性能测试（`performance_test`）、效果评测（`effectiveness_test`）、稳定性监测（`stability_monitoring`）。即使场景看似适用，也不得在本流程创建、上传或交接的标签集合中使用；不得以这些标签作为临时兜底，也不得为了通过审核换成无依据的允许标签。

“允许”不等于六项全部必打。每个 Case 至少选择一项有证据适用的允许标签；四项禁选标签审核时直接记录“本 Skill 禁选”，六项允许标签继续逐项核对真实用途和安全依据。没有适用项时停止该 Case 的实施并说明原因，不影响其他独立 Case。

交接给 API Case Builder 时必须携带六项允许、四项禁选的限制，后续创建、修改、预发布和绑定前再次回读标签，不能因下游通用 Skill 支持十类标签而重新添加禁选项。复用已有资产时先检查其标签；发现禁选项则先处理冲突，不得直接作为合格交付，也不得未经授权清除其历史标签或改变调度用途。

## 工作方式

### 首次对话默认先盘点整个项目产品的接口

用户提供项目/产品并要求开始代码扫描或创建自动化时，首次回复必须先说明：`建议先按该项目产品的模块盘点关联仓库中的全部 HTTP 接口，保留模块归属并上传清单，再按稳定接口身份去重汇总项目接口总量；这一阶段不分析业务链路、不编写用例。随后再按模块补充链路、场景和自动化。` 这是默认启动顺序，不要求用户再次选择是否先盘点。用户明确只处理某模块、目录或单接口时尊重范围，不借首次盘点扩大扫描或上传范围。

1. 从已有上下文和平台归属确认项目产品、关联后端仓库/服务、分支及已提交修订。按全部关联服务的路由清单盘点，覆盖没有页面调用的接口；不只扫描当前模块或某个 Controller。缺少仓库/服务范围时，只询问缺失标识，不无边界扫描本机，也不把单仓库结果冒称整个项目。
2. 使用相应索引器，仅识别真实接口名称、HTTP 方法、规范路径、版本、源码位置及所属仓库/修订，按稳定接口身份去重；记录动态路由等未确认项，不为了上传先追 Service、数据库、异步链或设计 Case。前端调用审核、业务链路和 Case 编写放在后续阶段，不能阻塞接口总量盘点。
3. 先分页读取产品模块树，根据现有归属、源码目录和接口职责核实模块映射。复用现有 MCP：`create_module_coverage_scan(scope_type="module", module_id=真实模块ID, inventory_only=true, expected_case_count=0)`，按模块、仓库、分支和修订建立盘点记录；`expected_interface_count` 为该范围准确接口数。用 `batch_upsert_module_coverage_interfaces` 分批上传 `source_key` 和 `payload.interface_name/method/url`，省略 `mermaid/node_ids/branch_ids`，不上传 Case。包含子模块时明确 `include_descendants=true`，每项在顶层填写真实子模块 `module_id`。不得为省去链路分析改为不传模块，也不创建虚假兜底模块、API Info 或占位 Case。归属未确认的接口保留在清单与缺口中，先查上下文和代码，不随便挂模块、不从项目总量核对中漏掉；只影响该部分上传。
4. 当前部署若不支持 `inventory_only`，或仍强制 Mermaid/完整链路才允许模块清单生效，明确报告“模块接口清单已盘点，纯清单上传待当前部署支持”，保留清单及精确恢复点。不得改用无模块上传、画假链路/占位图或用审计未生效记录声称已入库；不因能力缺失擅自改平台代码。旧 `scope_type=project` 仅兼容既有记录，不作为默认或绕过模块归属的替代流程。
5. 首阶段汇报项目产品、模块、仓库/修订覆盖范围、发现接口数、未确认路由数、已回读上传数和缺口。分别说明“接口盘点完成”“上传生效”“链路分析完成”“自动化完成”，不得互相替代；未分析接口不能因没有 Case 而算完成或排除。全部约定模块的清单生效并完成全集对账后，联合形成项目接口总量基线，不要求另建无模块记录；分母及排除口径须明确，不能用当前已分析的部分模块冒充全项目。

接口盘点与上传能力不替代下文完整链路/Case 上传契约。首阶段完成后，才按下述页面调用、独立业务依据和安全规则逐接口完善；纯盘点不授权执行被测业务接口或创建发布真实自动化资产。

盘点仍用 `get_module_coverage_scan_upload_status` 逐页核对接收集合与模块、`get_module_coverage_scan_validation` 检查数量，再用 `update_module_coverage_scan(status="completed")` 生效并回读 `summary.applied=true`、`summary.inventory_only=true`。模块纯盘点允许零链路生效，但不表示代码链路审计/自动化已完成，也不计为模块完整链路扫描完成；完整分析使用 `inventory_only=false`，保留原门禁。盘点不提交移除动作、不清空已有分析、不归档未上传的历史 Case；旧链路保持原分析修订，不因发现接口的新 Commit 就冒称已重新分析。后续按模块补全原接口身份，不另造重复接口；所有约定模块和关联仓库完成对账后，按稳定接口身份去重汇总项目总量，不简单相加跨模块复用接口，也不把部分模块当全项目。增量盘点与完整链路分析分别核对各自基线。老部署不识别该参数时执行第 4 条。

### 上传前必须校验是否已有完整接口清单

首次启动及每次恢复上传前，通过 MCP 查询平台基线和接收记录，不能根据聊天记忆、本地文件存在、模块扫描完成、ApiInfo 数量或平台已有部分接口判断“已经传全”。

- **核对同一范围：** 项目产品、全部关联仓库/服务、各分支及完整提交 SHA、扫描模式和包含/排除路径必须匹配；核对索引器/扫描规则变化是否会影响接口发现。多仓库使用各仓库修订清单，不能用一个仓库的 commit 代表全项目。模块仅为归属，不作为接口身份。
- **平台无完整基线：** 按模块完整盘点并上传。全部约定模块同版本的生效清单经全集对账可联合形成项目基线；只有部分模块、部分仓库、未生效记录，或未核对范围的历史链路扫描，都不能证明项目清单完整。核实并复用已有接口，不重复造无模块基线，也不跳过缺失范围。
- **完整基线与当前范围、修订和扫描规则一致：** 分页回读接口稳定标识、预期/实际数量及生效状态，核对无缺失、重复和冲突后直接复用，不重复创建扫描或上传；上传后的链路/Case 进度可以继续更新，不因复用盘点基线而重置。
- **完整基线存在但代码版本变化：** 先核旧基线与当前版本的可比较性，重新发现受影响路由并核对新增、变更及缺失项；平台支持对应清单增量协议时上传增量，否则使用受支持的全量方式。不能只看 Controller 文件名而漏掉路由前缀、注册和共享依赖变化。删除项仅由已核实的完整范围差异提出，按现有归档授权处理，不删除绑定的 API Info/Case。
- **同一范围/修订上传中断：** 查询本次上传 ID、已接收稳定键及内容校验信息，只续传缺失项；已接收同键同内容直接复用，同键不同内容先核冲突，不能盲目重复提交或另建全量记录。查询失败、分页未取尽不等于“未上传”。
- **完成后回读对账：** 本地完整路由集合与平台接收集合按稳定身份逐项相等，预期数与去重后实际数一致，并确认整份清单已成功生效，才可说“接口已全部上传”。数量相等本身不证明集合一致；未解析路由仍须说明，不能声称已知所有运行接口。接口身份遵平台稳定键契约，至少区分产品、仓库、分支、HTTP 方法、规范路径和 API 版本，不因模块或名称变更重复建接口。

汇报明确区分“首次上传”“已上传并复用”“增量更新”“中断续传”“已部分上传”及“尚无法验证”，给出基线/上传 ID、仓库修订、预期数、已核实数和剩余缺口。平台/MCP 若不能返回完整范围、接收集合或生效状态，必须报告精确能力缺口，不猜测已传或未传，不绕过平台读库；保留已核实进度，不用旧模块扫描冒充项目级基线。

### 先判定项目是否有前端，再核实页面调用

接口发现始终以所选后端代码范围为准，不因没有页面调用就漏扫接口；“上传扫描接口”和“编写 API 自动化 Case”是两个动作。

- **项目/产品有前端：** 根据用户上下文、仓库说明、产品关联及真实代码，定位对应前端仓库、客户端和修订。逐接口追踪页面/组件或页面操作，经请求封装、公共 API SDK、动态路径及网关前缀到后端 method + 规范路径的调用关系。不能只搜 URL 字符串；公共方法无人引用也不等于存在页面调用。
- **已核实无页面调用：** 首阶段仍上传接口清单，不以业务链路分析作为盘点前提；后续需完整链路审计时按真实证据补充。不为该接口创建、扩展、执行或交接真实 API 自动化 Case，也不为“接口录入率”额外创建 API Info。未编写原因显示为 `无页面调用`，附前端仓库/修订、核查范围及重新启用条件（页面接入并核实调用后重新评估）。这是当前代码驱动范围的排除理由，不证明接口废弃、无调用方或不存在测试价值。
- **项目/产品没有前端：** 不应用页面调用过滤，按原后端业务范围设计、上传和实施 Case；不显示 `无页面调用`、页面调用状态或相关空白占位列。不能因为本地只有后端仓库，就推定整个项目没有前端。
- **是否有前端或调用关系无法确认：** 前端源码缺失、修订不明、动态分派或代理路径未解析时，不能写“无页面调用”。记录 `页面调用关系未确认` 及具体缺失证据，先继续接口扫描上传和其他可确认接口；受影响接口暂不交接真实 Case。优先使用现有上下文和代码，仅确实缺少仓库/范围标识时再询问。

调用核查只决定自动化实施范围，不缩小后端接口扫描数量或把未调用当作链路解析 Gap；接口链路本身不完整仍按原规则记录 Gap。台账优先在现有说明/备注记录依据，不臆造 MCP 字段，不为写原因创建“无页面调用”的占位 Case。已有真实场景行可记暂不处理及启用条件，但不得据此静默清除已有 ApiCase 绑定、删除/停用 Case、改调度或伪造完成；已有绑定冲突单独交接治理。

增量扫描须同时考虑前端调用变化：新增页面接入时重新评估原排除项，调用移除时先核实全部相关页面/客户端再调整未实施项。用户以后明确扩大到服务间调用、开放 API 或无页面接口测试时，只调整明确范围，不自动沿用“无页面调用”排除。

### 先建立独立业务基线

将实现分支变 Case 前，依据需求、已审功能 Case、接口契约、已确认上下文建立业务覆盖与预期。遵循 [仅接口输入与独立预期](../mango-test-case-document-builder/SKILL.md#interface-only-input-and-independent-expected-results)。索引可先定位代码，但不能决定业务应该怎样；代码已在上下文时，工作证据明确区分独立预期与实现观察。

源码追踪补充并挑战基线，不替代基线：独立依据要求但代码缺失的行为保留覆盖项或有证据 Gap；仅代码行为标 `代码现状回归候选`；差异不得通过迎合实现改预期。schema、示例/实际响应、代码和历史通过可描述现状，不单独证明未文档化业务意图。无独立权威时交付候选与具体问题，不称验收已核验或全覆盖；继续有证据工作，未决业务只影响对应场景。交接带每个预期来源及候选/已确认区别。

### 默认就绪状态与下游交接

用户未明确仍开发时默认 `接口已完成，按严格断言执行`，简述假设但不让用户选择已完成/开发中。就绪只是执行假设，不证明契约、扫描、Case、执行、清理或发布通过，状态按证据。

交给 `mango-api-case-builder` 时保留默认就绪及原授权产品/模块/Case。用户已明确要求创建、执行或全模块完成时，方案作为进度，冻结范围并继续，不二次问就绪或是否开始。仅扫描、设计、总结不授权改真实资产。必要上下文、契约冲突、不安全清理、扩围和另行破坏性操作保留门禁，不得借默认放宽断言/权限。

AST 脚本是确定性接口索引器，仅枚举支持的路由、源码位置、请求契约入口、修订来源、解析警告和发现事实，不生成可信业务链、Mermaid、场景、断言、职责或分支覆盖结论。

AI 必须读源码，追踪影响行为的每条边：校验、认证租户、controller/handler、应用服务、领域状态、repository/事务、外部/异步、异常映射、响应、副作用和清理。FastAPI 脚本不解析 Pydantic 模型体/validator；Spring 注解仅入口线索。

模块扫描须运行索引器做全量清单与增删对比。已知单接口且固定已提交修订时可从平台身份和核验源码定位开始；路由身份/注册不明再跑索引。单接口未找到不证明删除。

## 硬性停止条件

- 不设计/交接依赖环境固定业务数据的可复用 Case。前置与业务预期带运行来源；允许全局/公共表达式，但不把解析值固化到请求、断言、前后置。遵循 [数据边界](references/automation-boundaries.md) 与下游运行数据门禁。
- 角色、权限、授权管理仅查询，不创建、修改、删除、授撤、分配角色或改授权关系，前置/清理也不例外；业务权限验证仅用已有身份。
- 直接实施须有可写唯一事实台账：优先 `/mcp/api` 的服务自动化模块覆盖，否则用户提供的精确可写飞书/Excel。
- 不扫描无边界机器范围，不泄密，不编字段、枚举、数据、依赖行为、断言、清理或预期。
- 影响行为的边未解析则停止受影响接口，只上传已证明部分链，带 `未解析边界：...`、`gap_reason`、`next_action`、`resumption_point`。
- 权威依据与代码冲突时停止对应场景，保留为 Gap。
- 不把路由 → Controller → 泛化占位当完整链。
- HTTP 成功/schema 不证明筛选、排序、授权、分页、修改、幂等、状态或副作用。
- 不建语义重复 Case，变更场景未下游验证不转移 ApiCase 绑定。
- 环境/服务运行配置、系统/租户管理控制、额度/权益、授权设置任何环境都禁写，含前后置。规则库规则、规则组、清单、业务模板允许有证据的隔离 CRUD，不能仅因“管理/配置”、复用或租户范围排除。按 [代码与影响边界](references/automation-boundaries.md) 判断；恢复、负断言、非生产标签不豁免真实运行/安全控制禁令。
- 查询可只读发现字段再精确查；创建可查合格共享前置但不改删；删除每轮先 API/获准工厂造专属目标，不从存量选。查询只确认本轮目标/删除结果，含任意 HTTP 的逻辑/批量删除；交接保留归属规则。
- 不因当前生产、不适合生产或需切测试就 `deferred`。可在可访问非生产安全构造/执行/观察/清理时保持 `pending_create`，打合适非生产标签，去掉无依据生产标签。

通常只停止受影响接口；共享路由、认证、租户、异常、事务、清单或清理不确定使更大范围失效时才扩大停止。

## 平台契约

模块覆盖 MCP 用整数 `schema_version=3`，扫描产物版本字符串 `"3.0"` 与上传契约独立。不提交旧 `automation_decision`、`case_no` 或合并的 `scenario_assertion`。

接口标准结构：

```json
{
  "source_key": "stable-interface-source-key",
  "payload": {
    "interface_name": "查询服务",
    "method": "GET",
    "url": "/service/path",
    "api_info_id": 123,
    "api_info_revision_id": 456,
    "mermaid": "flowchart TD\n    request[\"GET /service/path\"] --> handler[\"Controller.method\"]\n    handler --> decision{\"条件成立?\"}\n    decision condition_yes@-->|yes| success([\"成功响应\"])\n    decision condition_no@-->|no| rejected([\"拒绝响应\"])",
    "node_ids": ["request", "handler", "decision", "success", "rejected"],
    "branch_ids": ["condition_yes", "condition_no"]
  }
}
```

可实施但未绑定的 Case 结构：

```json
{
  "source_key": "stable-case-source-key",
  "payload": {
    "interface_source_key": "stable-interface-source-key",
    "interface_name": "查询服务",
    "method": "GET",
    "url": "/service/path",
    "case_title": "满足条件时返回目标记录",
    "evidence_category": "代码现状回归候选",
    "code_evidence": [{"path": "src/service.py", "symbol": "query", "start_line": 10, "end_line": 30}],
    "baseline_commits": [{"repository": "backend", "commit_sha": "0123456789abcdef0123456789abcdef01234567"}],
    "test_scenario": "查询同时包含目标记录和对照记录的数据集，并传入目标筛选条件",
    "core_assertion": "响应包含目标记录且不包含对照记录",
    "test_ownership": "HTTP API自动化",
    "scenario_layer": 0,
    "scenario_type": 0,
    "scenario_tags": ["routine_regression"],
    "current_status": "pending_create",
    "execution_result": "not_executed",
    "covered_node_ids": ["request", "handler", "decision", "success"],
    "covered_branch_ids": ["condition_yes"]
  }
}
```

语义未变且已有 ApiCase 时，保持载荷，设 `current_status=completed` 和已核实最近 `execution_result`，在与 `source_key`、`payload` 同级添加 `api_case_id`、`api_case_revision_id`。绑定 ID 不进 payload，不为重扫上传成功而降级已绑定 Case。

契约不变量：

- 接口身份 `project_product + repository + branch + source_key_hash`，`source_key` 来自方法、规范路径和 API 版本，模块 ID/路径不参与。
- 源路由与平台可执行 URL 是同接口两种表达。以 `/cooperation/{cooperation_id}` 等框架规范路由生成键/差异；上传接口/Case 或交接前，已由源码证明的 `{name}` 转 `${{name}}`，如 `/cooperation/${{cooperation_id}}`，保留已有 `${{...}}`，不改 query/body 或未证明大括号。Info 比对统一回 `{name}` 防重复；每个执行 Case 请求前产出同名缓存。
- Case 身份是接口身份加可控前置/状态、触发、可观察结果和实质副作用；职责/层级/类型/标签、状态/结果、文字、证据、模块、commit、图选择和平台 ID 不入键。
- 上传/交接前 `case_title` 自然准确，表达业务目标且与场景/判定一致。保留追溯编号或必要区别条件/结果，纯元数据的产品/模块/客户端/环境/执行标签前缀移除。原始枚举、字段、数码、ID、参数赋值、HTTP 状态、方法或维护说明不能本身当标题。
- `test_scenario` 必填，用普通业务语言说明条件/可控前置及用户动作，不依赖来源编号、分支 ID、自动化 ID、接口名、原参数、技术词、Mermaid、源码或 `core_assertion` 才理解。它们只能补充。空白、仅编号、仅实现、`正常场景`、`异常场景`、`参数校验`、`分支覆盖` 等不合格。独立可核验预期写 `core_assertion`，不混在一起；上传回读再查，违规阻止扫描完成、交接与绑定。
- 上传/交接逐 Case 按上文六项允许、四项禁选限制审核标签，证明已选适用及其他允许项为何不选，不全模块套标签。`production_inspection` 遇 `PUT/PATCH/DELETE`、SQL/工厂、数据库写或状态变化拒绝，`POST` 需只读正证。`production_regression` 含 SQL、生产连接或工厂拒绝。含禁选项、无审查、空集合或无依据已选标签禁止上传/交接。
- 每接口一张 Mermaid，不是每 Case 一张；节点全在图内，分支 ID 对应真实边，非根可达，所选 Case 节点/分支在接口快照存在。
- 菱形仅单次求值互斥结果；同请求能并行/循环命中的路径用矩形分发/循环，共享后续前显式汇合。
- 内部 Gap 必填三个恢复字段。已由源码证明的外部依赖可止于 `外部边界：服务/接口`；调用侧条件、组参、成功失败、事务、异常、响应均清楚才完整。
- `pending_create` 无 ApiCase且 `not_executed`；`completed` 有真实绑定，可 `not_executed/passed/failed/partial`；`deferred` 无绑定、`not_applicable`，具体原因和启用条件一起写 `payload.remark`。允许有证据的自动化/权威/平台缺口、职责越界，或有前端项目已核实的“无页面调用”范围排除；环境选择/不适生产不算。不编 `deferred_reason`、`enablement_condition`。单元归属为 `deferred/not_applicable`。

图拓扑、身份、职责、判定、碰撞和 Gap 详见 [分支到 Case](references/branch-to-case-rules.md)。

## 流程

默认先完成上文“首次对话默认先盘点整个项目产品的接口”，再进入以下链路分析与自动化流程；以下模块/单接口完整扫描契约只适用于后续完善阶段，不得反过来要求首阶段必须先完成链路或 Case。

1. 核定产品、模块、仓库、分支、已提交修订、框架、扫描范围/模式、包含排除路径、后代模块、可用验证环境及可写台账。先判定项目/产品是否有前端，有则核定关联前端仓库/客户端和修订，没有则不显示或应用页面调用分类。当前环境可切换，每 Case 独立判标签，不因当前非合适环境延期。工作区脏时仅扫描已提交树，或记录基线未解决 Gap。
2. 读取扫描、当前接口、全部分页 Case，全量时含已移除资产，读取权威功能/设计来源；无权威仅候选。
3. 模块扫描在 `.mango-test-scan/<service>/<revision>/` 跑对应索引；适用时与修订匹配 OpenAPI/运行映射核对。解析错误、动态路由、注册歧义、重复和清单不符记 Gap。接口级绑定/验证 `analysis_gaps` 不抹掉已证明路由，源码追踪解决。
4. 逐接口追源码，大范围保留路由清单作完成检查；有前端的项目按上文核实页面调用。无页面调用的接口保留扫描上传但不编写真实 API Case，原因写“无页面调用”；关系未确认不冒充无调用。无前端项目不做此过滤。不机械将 AST 事件转节点/Case。
5. 对比权威与代码，按边界先排禁止的配置写及其前后置；保留接口/证据，台账场景为 `deferred/not_applicable`、无新绑定并写理由，不为完成率造可执行 Case。合格行为推独立可控可观察场景，稳定键去重；`test_scenario` 普通语言测什么，`core_assertion` 可证伪结果，执行名称、标签和分支断言变更检查。
6. 先职责再可行性，遵循边界。工厂可表达前置仍 HTTP，缺实体/模板是工厂实施工作，不证明集成。
7. 最终数量已知才建扫描。`scope_type=module`，或单接口 `scope_type=interface`、当前 `target_interface_id`、`expected_interface_count=1`；增量基线须对应最近生效范围。
8. 中断恢复先读已接收接口/Case 键；先接口再引用本扫描快照的 Case，每批最多100。已有绑定保留在项级 `api_case_id`、`api_case_revision_id`；仅新实施在终结后用绑定工具。Info 精确唯一复用，模块覆盖上传不创建 Info。
9. 终态前验证数量、身份、路径、拓扑、普通语言必填场景、标签、占位。`valid=true` 且零 Gap 才 `update_module_coverage_scan(status=completed)`；`valid_with_gaps=true` 才 `status=completed_with_gaps`，仅关闭审计不生效。占位、仅编号、泛述或仅实现描述两种终态都不允许。
10. 回读扫描、当前接口、历史、结构差异、接口 Case、详情/历史/差异、高亮、绑定和范围指标。新增量/全量修不符；仅全量可移除缺失项，移除不删绑定 Info/Case。
11. 需真实自动化时，仅将已证且不含禁写的场景/逐标签依据交 API Case Skill，带六项允许、四项禁选标签限制、配置禁写和 Case 预发布上限，并明确 API Info 验证后有权限可直接发布。下游重审完整树并遵守本流程标签限制，负责获准修改、执行、诊断、清理、预发布；Case 无论正式权限均停预发布，无支持/权限保留验证草稿，记实际状态继续独立 Case，不重复确认。
12. 满足发布状态检查及平台绑定前提才回读绑定；权限不满足时保留未绑定台账，工作证据存真实候选 ID/修订，不造绑定或称覆盖完成，继续独立 Case。分别报功能覆盖、代码候选、Gap、职责、真实完成、结果、发布状态、匹配修订运行覆盖；最终汇总待负责人发布、依赖绑定/重验，请用户联系负责人，不等待发布才写其余。

## 扫描模式与终态

- 模块全量：可增改，经缩范围审核可移除缺失接口/Case。
- 模块接口盘点：`scope_type=module`、真实 `module_id`、`inventory_only=true`，Case 数为零，链路允许缺省；清单完整可生效，已有分析和绑定不变，缺失项不自动移除。项目接口总量按各模块稳定身份去重汇总；旧项目无模块盘点仅兼容历史记录。
- 模块增量：仅增改，未提交不代表删除。
- 单接口全量：更新已知接口，可移除其缺失 Case；目标缺失只审核不删。
- 单接口增量：更新目标与受影响 Case，未提交不删。
- `completed`：完整快照成为当前，可改生命周期/覆盖。
- `completed_with_gaps`：审计终结，Gap 可查，本扫描快照均不生效。
- `cancelled`：放弃上传，不成为当前。

## 完成声明

- `扫描审计完成`：范围清单全部覆盖或有明确 Gap，分支都有归属；用 completed/completed_with_gaps，占位不算。
- `功能设计完成`：预期有权威来源、代码核对、可区分错误的判定，无未决冲突。
- `自动化编写完成并已提交预发布`：可行 HTTP Case 已建/复用，请求的执行诊断、合法绑定、清理已回读，验证修订为预发布；正式发布交负责人，不能冒称。提交无权限/不支持是草稿交接，不是成功预发布；`current_status=completed` 只证明绑定。
- `分支覆盖闭环完成`：每个归属有修订匹配运行命中，清单与匹配 OpenAPI/运行证据核对。

只完成低层级不宣称高层级，用户未要求不提交扫描产物到 Git。

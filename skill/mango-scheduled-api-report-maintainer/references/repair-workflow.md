# API 报告失败 Case 修复流程

本文件是 `mango-scheduled-api-report-maintainer` 修复执行阶段的执行规范。开始修改任何资产前必须完整读取。

## 1. 修复对象与证据快照

以原失败报告行为修复对象。每一行至少保存：

- `test_suite_detail_id`、报告 ID、报告环境；
- API Case ID、失败发布/修订版本；
- 步骤和场景/参数行 ID、原始请求、响应、断言结果、错误；
- 当前编辑态和当前发布态的完整 Case 树；
- Case/步骤/场景数量、顺序、启停状态、API Info 绑定版本、断言、提取器、前置、清理和数据工厂绑定。

同一 Case 出现在多个选定报告时，共享一次资产修复，但保留每个原失败行，发布后逐行重试。

进入修改前必须已经完成所选项目产品与范围内、由定时任务生成的报告的全量失败清单：逐份核实定时任务来源，读取全部分页结果，排除非定时执行报告，按 API Case ID 去重统计 Case，同时保留任务、报告和失败执行行的对应关系。每批最多 50 个 Case 只限制修改，不得用于截断排查、诊断文档或待处理清单。

## 2. 批次边界与测试意图确认

- 每批最多修改 50 个去重后的 API Case ID。同一 Case 出现在多个报告行时算 1 个 Case，但其所有失败行都要保留。
- 第一批只能在用户已明确要求修复，或已确认只读排查阶段给出的 Markdown 表格及建议动作后开始。每批 50 个只是执行检查点，不是重新授权点；在用户授权的完整范围内自动续批，不问“是否继续”。用户明确限定一个批次或指定 Case 时不得扩大范围。
- 修改每个 Case 前，必须读取 Case 名称、场景名称、场景描述，以及当前请求和断言，形成明确的测试意图摘要：`前置条件 -> 被测动作 -> 预期业务结果`。
- Case 名称、场景名称和场景描述共同决定测试范围，不能只依据当前失败响应或某一条断言猜测测试点。
- 信息缺失或互相冲突时，先查原报告版本、历史通过记录、上下文/附件、需求/文档和实际代码链路，自行建立测试点与检错能力的对照。能够用权威证据消除歧义就直接修复；只有穷尽证据后仍缺少不可替代的业务决策才提出具体问题。
- 修改必须保留原测试意图和测试效果。若修复后无法证明同一业务结论，视为未修复。

## 3. 根因判断顺序

按证据从近到远检查：

1. 报告行的真实请求、响应、异常堆栈和断言明细；
2. 失败报告绑定的不可变版本；
3. 当前编辑态、当前发布态及历史通过/失败记录；
4. API Info 的 method、URL、protocol、body type、params/body/files；
5. Case 的公共头、变量、提取器、前置数据、清理和数据工厂；
6. controller、DTO、校验注解、service 分支、mapper/DDL 或权威接口文档；
7. 环境、鉴权、外部依赖和平台执行器状态。

不要把“接口返回失败”直接等同于后端缺陷。先排除请求构造、数据、版本绑定和断言错误。

每个 Case 必须形成 `实际测试目标 -> 当前资产错误/真实契约违例 -> 可以安全修改的资产 -> 验证及清理方法 -> 责任归属证据`。名称、描述、断言互相核对，不能只看一条断言或当前响应。动态合格数据、数据工厂实体/模板、文件/子记录、索引可见性、异步等待、身份前置、失败清理均属于授权修复工作；方案未完成就继续查证、实施和验证，不以“暂不发布”结束。

涉及索引或异步副作用时，追踪写入及删除/恢复链路并验证残留。产品代码违反契约地遗漏删除同步时，以具体代码和复现证明业务开发代码 Bug；平台无法执行产品已支持的安全清理且已排除配置问题时，证明测试平台缺陷/必要能力缺失。仅发现物理删除不清索引或尚未设计出清理方案，不足以判定任何一方 Bug；继续寻找符合真实业务契约的可清理路径。

## 4. 可自动修复边界

可以直接修复的典型问题：

- API Info body type/protocol 与后端 `@RequestBody`、表单或 multipart 契约不一致；
- Case 步骤仍固定绑定旧 API Info 发布版本；
- 参数位置、JSON 类型、变量引用或提取路径错误；
- 过期/删除的硬编码业务 ID，可改为合格的动态前置；
- 前置查询缺少租户、用户、权限、状态、有效标记、关联数据或稳定排序；
- 断言与已确认的 HTTP/业务错误封装契约不一致；
- 缓存键、场景级清理、允许环境中的数据工厂配置存在可验证错误。

不得自动“修复”的问题：

- 需要改后端业务逻辑、部署、生产配置、租户权限或第三方系统；
- 契约证据冲突，无法判断代码还是 Case 正确；
- 缺少合法测试数据且无法用安全 MCP 能力创建/发现；
- 需要删除覆盖、放宽业务结论或制造假数据才能通过；
- MCP 缺少安全的读取、预览、修改、执行、发布或精确重试能力。

这类问题不得伪造通过。修复成功使用 `修复成功`；修复未成功只允许下表三种结论：

| 处理结论 | 判定 | 必须动作 |
|---|---|---|
| `修复成功` | Case/API Info/前置/断言等测试资产已安全修复 | 完整编辑态验证、提交预发布，用户页面手动发布并核验版本后精确回放原失败行 |
| `需要业务开发修改代码` | Case、数据、身份、目标环境和测试平台均正确，权威契约明确，实际行为违反契约，根因已定位到被测产品代码，必须由业务开发修改代码并重新部署 | 保留 Case/断言，不重试未变化资产，输出完整代码缺陷反馈 |
| `需要测试平台修复` | Case/场景有效且产品不是根因，已证明测试平台存在 Bug 或缺少完成测试所必需的平台能力 | 输出平台缺陷/能力需求、复现步骤、已穷尽方案和验收标准 |
| `需要外部提供测试条件` | 场景有效，必要条件只能由指定外部主体提供，安全构造及忠实替代方案已证实不可行 | 按第 4.5 节输出缺项、来源证据、尝试方案、提供方及恢复验证条件，保留严格覆盖并继续其他 Case |

修复未成功统一使用上述三个结论，外部条件不足不是 Bug。不允许用 `无法修复`、`已阻塞`、`可测试性缺口`、`前置与清理方案待完成`作为结束结论。普通数据、前置、清理、隔离、账号、配置和未尝试的受支持流程继续解决，不能直接归为外部条件不足。证据不足继续查证，不假称完成或强行归为 Bug；真正不可替代的缺项只问具体问题，同时继续独立 Case。已废止场景按第 4.3 节单独治理。

### 4.1 权威契约判定

测试点与当前行为不一致时分两类：

- **权威契约已明确**：controller/service 分支明确，权威接口文档或维护中的自动化测试与代码一致，目标环境响应也一致，且修正 Case 不会删除或弱化安全、权限和业务边界覆盖。直接修复旧 Case，验证并提交 Revision 预发布；交用户页面手动发布，核验版本并精确回放全部原失败行通过后，处理结论才为 `修复成功`。
- **权威契约不明确**：代码、文档、需求、前端行为或环境响应冲突，修改断言会改变安全边界，或无法判断当前行为是否为回归缺陷。保持 Case 不变并继续取证；必须请求用户决策时只提出决定结论所需的具体问题，不得用其他终态结束。

不得仅凭一次当前响应改写预期，也不得在多方权威证据一致时笼统标记“测试点失效待确认”。

### 4.2 需要业务开发修改代码

只有同时满足以下条件，才能确认 `需要业务开发修改代码`：

1. Case 的请求、前置、数据、身份、断言和清理均正确；
2. 目标环境配置正确，实际部署版本与排查依据一致；
3. 测试平台请求构造和执行无误，问题不是平台 Bug 或能力不足；
4. 权威接口文档、明确需求或维护中的测试与代码共同证明预期契约；
5. 已定位到具体 Controller、Service、参数校验、异常处理或等价产品代码路径，修复必须修改代码并重新部署。

测试环境配置错误、部署漂移、账号或租户权限缺失、第三方临时异常、只有异常响应但尚未定位代码，以及产品契约冲突或不明确，都不能使用该结论，必须继续修复对应问题或补充证据。

确认后：

1. 保留 Case、原请求、关键断言和失败证据，不接受错误结果、不重试未变化资产。
2. 输出一份可直接交给开发处理的缺陷反馈：

| 字段 | 必填内容 |
|---|---|
| Case ID | 平台 Case ID |
| 报告 ID | 所有相关失败报告 |
| 环境 | 实际失败环境 |
| 接口 | method + URL |
| 场景 | 失败参数场景 |
| 预期结果 | 权威业务契约 |
| 实际结果 | HTTP、业务码、响应或副作用 |
| 复现稳定性 | 单次、连续多次、多日或多场景 |
| 代码证据 | Controller、Service、配置、枚举或测试证据 |
| 缺陷类型 | 代码、配置、下游、权限、安全或数据一致性 |
| 业务影响 | 用户影响和数据风险 |
| 清理结果 | 写场景的清理及残留验证 |
| 建议负责人 | 对应业务服务或模块 |
| 修复后验收 | 需要精确重试的报告行和场景 |

3. 安全、越权、数据污染问题标记高优先级。
4. 默认只向用户输出缺陷反馈；只有用户明确要求创建正式缺陷记录时，才调用对应缺陷系统能力。
5. 业务开发修改代码并重新部署后，只精确回放原失败行/场景。

### 4.3 已废止场景的单独资产治理

只有权威契约证明场景已不存在或正式废止，才记录单独资产治理建议；它不是修复失败结论，也不是任何一方 Bug。数据难找、环境暂不可用、清理复杂或自动化实现困难都不是退役证据。未经授权不得删除或取消发布，单独记录待治理数量，不能称整个范围已全部修复。

1. 输出场景退役的代码、文档、需求或用户决策证据，以及受影响报告、任务和覆盖。
2. 查询平台是否支持真正取消发布；支持时先预览影响，再在取得所需明确确认后执行。需要删除 Case 时同样必须预览并单独确认。
3. 平台暂不支持取消发布或尚未获得破坏性操作授权时，可按明确授权暂时移除正式执行标签和任务绑定，但必须记录为“历史发布版本保留，已退出正式调度”或“仅限人工临时执行”，不得声称已经取消发布或完成退役。
4. 反查显式任务和动态规则任务，记录当前是否仍会被调度；保留历史 Revision、Release 和失败报告审计证据。

### 4.4 测试平台缺陷或能力不足处理

只有同时满足以下条件才可使用 `需要测试平台修复`：

- 场景和 Case 预期有效，被测产品不是根因；
- 已完整执行相应平台 Skill 和现有 MCP/数据工厂/前后置/清理能力；
- 证据能够复现测试平台代码错误，或平台目录确认缺少完成该测试所必需的安全能力；
- 问题不是测试数据不足、配置未完成、权限尚未申请、环境未修复或工具使用错误。

必须输出：平台操作/工具、最小复现步骤、预期与实际、错误证据、受影响 Case/环境、已尝试方案、缺失能力、建议平台模块/负责人和修复后验收步骤。正式创建平台缺陷记录仍需用户明确要求；在平台修复前如需临时退出调度，必须按资产治理流程单独预览并报告调度状态，不得把退出调度当作问题结论。

### 4.5 需要外部提供测试条件

只有同时满足以下条件才能使用该结论：

1. 用例名称、场景、断言和权威契约证明场景真实有效，该条件不可省略，否则原业务检错目标会消失。
2. 已检查上下文、附件、可用身份、历史记录、文档及代码中的数据产生/获取链路，证明条件只能由指定外部主体签发、完成或提供。
3. 对只读业务接口、允许环境的只读 SQL、数据工厂、正常业务 API 前置及受支持测试桩等逐项记录尝试结果或有证据的不适用理由。替代方案必须保留真实验证目标；不能伪造签名、身份、外部结果，也不能插入数据库记录就声称外部业务已发生。
4. 未定位产品或平台 Bug，问题也不是已授权且现有能力可完成的配置/模板/身份解析尚未修复、查询遗漏或清理未设计。仅看到权限错误而未检查已有合法身份，不满足条件；但已查明只有管理员能提供的授权身份或必要功能放行，且替代方案已排除时，即使尚未发出申请，也可进入本结论，不要求越权尝试或先申请再无限等待。确属平台应提供而缺少的安全构造能力，归为 `需要测试平台修复`，不能用外部条件掩盖平台缺口。
5. 能指出具体提供方、所需交付物、目标环境/身份/状态、验收及恢复条件，而不是泛泛要求用户造数。

第三方才能签发的特定合法凭证，或只能由外部真实参与者完成且不存在忠实替代的状态，可能符合条件；不能仅因名称出现“Token/签署”就认定无法构造，应先检查获取、等待、业务流程和安全测试支持。

输出缺失条件、必要性和外部来源证据、尝试/排除方案、提供方、精确交付要求、已有修改/清理结果、条件到位后的完整验证与原失败行重试步骤。凭证只描述安全交付方式，不输出秘密。`是否修复成功=否`，保留 Case、断言和历史失败，不删除、不自动退出调度、不重复执行未变化资产。调查可以收敛为该结论，但不能声称已修复或通过；一次说明提供要求后继续其他 Case，条件到位后恢复验证。

### 4.6 常见异常的强制处置与一次性交接

以下是处理流程，不新增结果分类。授权范围内的测试目标不重复请求确认，只有真实业务证据冲突、扩围或额外危险操作才提出具体问题。不得以“尚未证明是产品/平台 Bug”作最终交付；先完成可行的取证与修复，或按第 4.5 节证明并交接外部条件。

| 异常 | AI 必须先完成的工作 | 无法自行完成时的处理 |
|---|---|---|
| 功能开关/灰度关闭、能力未开放 | 从原 Case/需求确定开启前提，沿代码追开关、租户/身份/环境及部署适用性；只读核实当前条件，检查已有获准且功能已开放的身份或上下文。不能把未开启等同于功能废止，也不能把错误身份下的关闭响应改为正确期望 | 证明目标环境必须由管理员放行且无安全等价条件后，按“需要外部提供测试条件”交接具体功能、目标环境/租户、来源和生效验证方式。不自行改共享开关、灰度或部署，不改问“是否还测/是否删除” |
| 登录、角色、租户或数据权限不足 | 先核实际身份、Token 有效性、公共变量/请求头、目标租户、权限要求和现有合法测试身份；资产误配直接修，已有合适身份可在原授权和原场景意图内使用。原目标若是拒绝/越权校验，不得换成高权限身份绕过 | 确无可用合法身份且只能由管理员提供时，集中列出最小业务权限、目标租户/环境和安全交付方式，使用“需要外部提供测试条件”；不修改角色/授权关系，不把预期成功改为接受无权限 |
| 异步任务占用、处理中或短暂互斥 | 查任务类型、租户/用户作用域、状态、创建时间、归属及完成/释放机制；在任务契约和总耗时预算内有界轮询，必要时在本 Case 内等待前一任务终态再提交，避免重复提交。只清理已确认本轮专属任务及产物，保留本场景业务断言 | 不取消/删改他人任务、不清锁、不重启服务、不无限等待或无变化重试。超过有据等待预算后，查是否违反完成/释放契约；证实产品/平台缺陷按对应结论。若只能由外部运维恢复或提供独占条件，按第 4.5 节证明并交接；不能仅凭一次“占用”就要求用户处理 |
| 请求缺字段、正文/文件/子记录/编辑器前置缺失 | 根据名称、场景和契约核对前置输出是否真实传入请求，核验所需文件/标识/状态；修正提取、变量、工厂实体/模板/绑定和执行顺序。前置确需真实业务 API 时补齐流程，不能编状态或回退共享存量 | 缺模型、缺模板或还没设计好不是外部条件；继续构造并验证。只有已穷尽方案且确需指定外部主体提供时才按第 4.5 节交接 |
| 清理不完整、可能修改共享对象 | 改用本轮隔离目标，按响应 ID/唯一键追踪直接和异步副作用，配置失败也执行的 Case 级清理及依赖顺序，验证残留/恢复。只停不安全动作，不停止其他取证和独立 Case | 不清理共享对象、不先执行后赌能恢复。继续查安全替代；证据证明产品清理违约或平台缺少必要能力才归 Bug，不能以“清理方案待完成”收口或建议删 Case |

**统一交接要求：** 同一功能、身份或共享依赖造成多个失败时，只保留一份条件交接记录，列出全部受影响 Case/原报告行。对用户用普通语言说明“需要谁，在什么环境/范围，提供什么，提供后如何验证”，附必要证据与已排除方案。负责人姓名未知时写已核实的职责角色，不编姓名，不把查不到具体人作为停止调查的原因。保留规定八列结果表，外部条件的细节放表后；不要让用户在“继续测试/删除/取消发布”之间重新选择。

记录本次已做动作、未做动作及原因、具体外部交付物、下一条可执行步骤和恢复条件。该记录是调查收敛与责任交接，不等于功能已通过；Case、断言、调度状态保持不变。未经明确授权不创建正式缺陷/申请、不发消息、不修改任务调度或灰度权限。恢复测试所需的业务条件不等同于“用户是否还想测”。

**连续处理与重复检查：** 交接后继续其余可修复 Case，不等外部回复才进入下一批。当前检查仍有安全可推进工作时不得只给“尚未证明”的清单就结束；确因本次运行时限中断时，明确标为未完成调查检查点并保存精确恢复点，不能伪称范围已处理到终态。所有可推进工作完成后，才交付待发布、三类未成功及未决证据各自清单；未决证据不冒充终态。

已有周期检查流程再次遇到相同缺项时，先读取历史交接，做必要的轻量只读核实；条件、影响和责任未变化则沿用记录，不重复申请确认、不重跑注定失败的 Case、不重复上传相同附件。条件已变化或用户提供新材料时，再核实并恢复受影响 Case；原报告环境和测试目标不变，其他环境验证只作补充证据，不替代原环境完整验证与精确重试。

## 5. 前置数据规范

从失败场景反推候选数据必须满足的完整资格条件：租户、当前用户/角色、所有权或协作关系、业务类型、状态、删除/有效标记、流程节点、必需子记录/文件及其他校验条件。

优先顺序：

1. 前置只读产品 API，能返回并证明全部资格条件；
2. 非 PROD 且环境允许时，使用测试平台支持的只读 SQL 发现；生产环境不得在测试平台配置 SQL 或数据库连接，但本地电脑已有合法、可用的生产连接时，可在平台外使用只读 `SELECT` 补充诊断证据，严禁任何增删改、DDL、权限变更或其他写操作，也不得把连接、凭据或 SQL 回填到平台资产；
3. 数据库可表达的受控状态，使用数据工厂；
4. 数据工厂无法表达的真实流程/外部效果，使用正常业务 API 构造并配置可靠清理；
5. 都不可行时继续确认责任边界：产品代码问题按第 4.2 节，平台缺陷/必要能力缺失按第 4.4 节；条件只能由外部提供且满足第 4.5 节门禁时进入 `需要外部提供测试条件`。证据不足继续排查，不虚构 Bug 或外部责任；场景废止时单独治理。

查询场景可以通过只读接口获取真实字段值再精确查询；创建场景可以查询合格的共享前置，但不得修改或清理它们。删除场景（含逻辑删除、批量删除及任意 HTTP 方法）必须每次通过业务 API 或允许环境的数据工厂创建本轮专属目标并捕获精确 ID，禁止查询存量数据作为删除目标；查询只确认本轮创建的数据或删除结果。目标缺失、造数失败不得改删共享/历史数据；批量作用范围无法限定时不执行，继续寻找安全设计或取得真实责任证据。

选择必须确定性排序。`content[0]`、数组下标 `0`、`LIMIT 1` 或 `TOP 1` 只有在查询已经证明全部资格条件时才可使用。

禁止复制另一个环境的业务 ID。长整型 ID 在日志、脚本或只读 SQL 证据中按字符串处理，避免 JavaScript 数值精度损失。

### 数据工厂修复升级

出现以下任一情况时，数据工厂属于当前 Case 修复的一部分，不能仅记录为阻塞后跳过：

- Case/场景已经绑定数据工厂，但实体、模板、依赖、输出、绑定、执行或清理处于停用、缺失、失效或失败状态；
- 当前前置依赖硬编码业务 ID、复制历史数据、任取第一行或直接 SQL 夹具，需要迁移为可复用、可清理的数据工厂；
- 接口没有进入目标业务分支，证据表明缺少订单、权限、协作关系、文件、子记录或其他数据库可表达的业务状态；
- 编辑态执行的数据工厂预览、落库、缓存输出、用例消费或清理失败。

必须通过 mango-test-platform MCP 获取数据工厂 Skill，不得直接读取本地 `mango-data-factory-builder` 目录作为执行依据：

1. 调用 `list_mcp_skills` 或读取 MCP Skill catalog；
2. 按当前目录返回的 name/title/category/description 解析 `mango-data-factory-builder`。若部署返回不同的 canonical name，使用 MCP 返回的实际名称；
3. 调用 `get_mcp_skill` 或读取 catalog 返回的 Skill resource，完整读取 MCP 提供的 `SKILL.md`；
4. 按该 Skill 的路由继续通过 MCP 读取当前修复所需 references；
5. 按其流程修复实体字段、模板、多表依赖、输出、Case/场景绑定、执行与清理，并完成规定的预览、启用、编辑态执行和残留校验。

`预览失败`、`绑定停用`、`模板不完整` 或 `清理失败` 是需要继续修复数据工厂的症状，不是自动终止理由。只有完整遵循数据工厂 Skill 后，证据明确证明平台实现错误或缺少必要的安全能力，才能进入 `需要测试平台修复`；缺少环境权限、实时 schema 或业务证据时继续获取，不得把它包装成平台能力不足。最终结论必须列明已修复或仍在处理的数据工厂实体、模板、绑定和验证证据。

不要在本流程内臆造模板字段、外键关系或业务状态，也不要绕过 MCP 直接修改平台数据库。

## 6. API Info 协议与固定版本修复

当源码/文档证明 API Info 的请求协议或 body type 错误时：

1. 保存旧 API Info 和所有引用步骤的绑定基线；
2. 通过 MCP 修改 API Info 编辑态并读回 method、URL、protocol/body type、params/body；
3. 执行 API Info 编辑态，确认请求构造和响应契约正确；
4. 完成接口契约、精确差异及引用影响自检，创建 API Info 新修订，有接口发布权限时直接发布并回读 Revision/Release，不走 Case 预发布审批、不再请求用户审批；无权限才保留修订交接；
5. 检查 Case 步骤是否固定绑定旧 API Info 发布版本。

如果步骤绑定的是不可变旧版本，不能只刷新或重跑。API Info 发布后先核实对应已验证修订，再使用 MCP 的影响预览，完整快照该步骤全部场景，然后将步骤重新绑定到新 API Info 发布版本。未发布时仅使用平台明确支持的编辑态验证方式，否则保留依赖交接并继续其他 Case，缺接口发布权限时不得为解锁绑定绕过权限；有权限则按上述 API Info 流程直接发布。若平台只能通过“预览删除步骤 -> 删除 -> 重新添加”完成重绑，必须：

- 精确预览单个步骤影响并使用确认 token；
- 保存并逐项恢复原步骤顺序、全部场景/参数、断言、提取器、前置、清理和数据工厂绑定；
- 修改后读回并证明步骤/场景数量和语义覆盖均未减少；
- 任一配置无法完整恢复时停止，不发布 Case。

## 7. 断言修复规范

修改断言前先引用本 Case 的测试意图摘要，说明该断言在证明哪个业务结论。将“名称/描述及权威契约定义的测试目标”与“当前断言实际接受或拒绝的响应”分别记录；不能把旧断言的期望值直接当成原测试目标。不得为了消除失败而随意修改断言。

在保存修改前，对旧断言和拟修改断言做同输入判定对照。至少覆盖原失败响应、原本应通过的响应，以及与被测业务结论有关的相反值、缺失值或异常值；只选择该场景相关的输入，不要求穷举所有 JSON。逐项记录：

| 响应条件 | 旧断言通过/失败 | 新断言通过/失败 | 判定变化及失去/新增的缺陷检出能力 | 权威依据 |
|---|---|---|---|---|

只要旧/新断言对同一输入的判定不同，修改前就以进度说明披露差异、影响的业务检查和权威依据，不等发布后才说。证据充分且原业务检错能力保留时，披露不构成再次确认门禁，直接修复并验证。证据不足或来源冲突时先继续取证；不得让原场景要求检出的业务错误变成通过。只有证据穷尽后仍缺不可替代业务决策才请求具体问题。不能凭名称不变、编辑态通过或断言数量不变声称覆盖未降低。

先区分两种失败：

- Spring/网关在请求绑定阶段返回 HTTP 4xx 的统一错误封装；
- 接口以 HTTP 200 返回业务 `code/msg/success/data` 错误封装。

依据 controller、DTO 校验、全局异常处理或权威文档修正预期。固定 JSON 片段可用 `ass_json_all`；嵌套、动态或需与缓存比较的字段用 JSONPath。保持数字、布尔、字符串类型准确。

每个场景至少有一个能证明场景业务结论的断言。做反事实检查：如果接口忽略被测条件但随便返回一个成功响应，现有断言是否仍会通过？如果会，断言不合格。

禁止：

- 仅为匹配本次错误而把精确断言改成宽泛 contains/regex；
- 用 HTTP 200、`success=true`、非空 data 或 schema-only 代替业务结论；
- 删除失败断言、设置 allow-failure、改成警告；
- 在契约证据不足时以当前响应反推“正确预期”。

只有满足以下条件才可修改断言：

1. 原测试点已经从 Case 名称、场景名称、场景描述和配置中确认；
2. controller/DTO/全局异常处理、权威接口文档、已确认需求或更强历史证据证明原断言错误或过时；
3. 新断言仍验证同一测试点，而不是换成更容易通过的结论；
4. 修改记录包含旧断言、新断言、同输入判定对照、权威依据，以及原测试目标和实际缺陷检出能力各自是否保留的结论。

最终结论必须逐 Case 说明断言是否修改。修改过的必须分别回答“文字描述的测试目标是否改变”和“断言的实际缺陷检出能力如何变化”，给出关键判定差异、依据及保留或丧失的检查；未修改的也不能用笼统的“调整断言”描述修复内容。

## 8. 覆盖保留门禁

修改前后逐项比较：

- Case 数、步骤 ID/数量/顺序；
- 场景/参数 ID、名称、数量、启停状态；
- API Info 绑定及版本；
- 请求分支、断言、提取器、前置、清理、数据工厂；
- 原失败报告版本的执行单元数。

`修复成功` 只有在 Case 内 `删除=0、停用=0、解绑=0` 且语义覆盖未收窄时才能进入发布。涉及断言变更时必须完成第 7 节同输入判定对照，证明原业务错误仍会失败；不能仅凭名称、数量不变声称覆盖保持。已废止场景的单独治理及临时调度缓解必须预览、授权、计数和报告，不能伪装为 Case 修复，也不进入修复结论分类。

除非用户在看到具体对象 ID、原因、影响和恢复方案后明确授权，否则不得删除或减少覆盖。

## 9. 编辑态执行与发布

使用报告环境运行完整 Case 编辑态，优先 `run_api_case` 的明确 editing selector。若只有批量工具支持编辑态，可只对目标 Case、并发 1 执行；不得扩大到整份报告或任务。

查询执行结果并审核：

- 所有保留场景均执行并通过；
- 断言仍能证明业务结论；
- 提取变量正确；
- 副作用和清理正确；
- 使用数据工厂时，执行级和 item 级清理均成功，并在允许环境以受支持只读能力证明残留为 0。

失败则回到根因分析，不得提交预发布。完整编辑态通过后，再做一次覆盖 diff，随后创建 API Case 修订并提交预发布；即使具备正式发布权限，也不得由 AI 发布该版本。

所有已验证 Case 均交用户页面手动发布，不因 AI 权限充足而跳过。修订创建或预发布提交被拒绝时，保留已验证编辑态及已有修订，记录被拒操作，不重复尝试、不绕过权限。单独输出“已验证，待用户手动发布”清单，记录产品、Case/API Info ID、候选修订、实际状态、验证与清理证据及原报告精确重试行；表外额外给出可复制 Case ID 行，格式为英文逗号连接的真实 ID，无空格、不含其他标识，例如 `1,3,222,12`。跨全部批次去重汇总，前置 API Info 另列。

每次交接清单后，必须使用入口 Skill 的固定提醒，告诉用户复制 ID 到用例页面审核发布，并在通过后返回当前 Skill 对话框回复“已审核发布，请重试”（可附已发布 Case ID）。明确下一步由 Skill 核验版本后逐个 Case 精确重试原报告失败记录，审核通过本身不表示已重试或修复闭环；不能只给 ID 而省略此提醒。等待期间继续其他独立 Case，不中断批次，不反复申请发布；无其他工作才暂停交还用户。待发布是交接阶段，不是产品/平台 Bug 或修复失败终态，也不得提前写“修复成功”；该交接例外优先于后续仅终态的批次表要求，清单非空不得声称全部修复完成。

## 10. 原报告精确重试

修改过的 Case 必须先完整验证并提交预发布；用户确认页面手动发布后，MCP 回读正式状态及精确 Revision/Release，核实其对应已验证候选，才对所选范围仍失败的原始行逐个调用。未发布、版本不匹配或候选发生变化时，不重试旧版本；候选变化须重验后重新交接。没有修改资产、用户已修复产品/环境并明确要求重试的 Case，不要求新建修订或重新发布，核实当前正式版本后即可精确重试。

`retry_test_report_case(test_suite_detail_id=...)`

全部要求的原失败行重试通过后，才记“修复成功”，不得先以该结论作为重试前提。

禁止调用整报告重试、重新触发定时任务、重试已成功行。每个重试完成后读回：使用环境、新 Case 版本、执行单元数量、状态、失败详情，以及报告汇总变化。

若重试失败，停止对该行的无变化重复重试并回到诊断，取得新证据并完成必要修复后再验证。三个修复未成功结论都不重试未变化资产；单独治理退役后，不重试会再次执行旧快照的报告。其他独立 Case 继续处理。

## 11. 每批汇报与自动续批

每个执行项完成调查及必要的精确重试后，执行入口 Skill 的“报告原因类型与 MCP 回写”。原因分类使用报告页面枚举，通过 `update_test_report_case_diagnosis` 写入该 `test_suite_detail_id` 的 `failure_reason` 和 `failure_description`，再读回验证；默认不传 `is_excluded`，保持原开关。只有另有明确历史排除/恢复授权时，按入口“排除统计开关”传 `true`/`false` 并验证原始失败保留。批次汇报列出回写成功/失败的执行项 ID，禁止把回写失败称为保存成功。处理结论与原因分类各司其职，不把 `修复成功` 等处理结论当成原因类型。

每批先输出以下固定汇总表，列名和信息不得省略或用笼统状态代替：

| 执行报告 ID | Case ID | 任务环境 | 执行场景 | 修复内容 | 是否修复成功 | 失败原因 | 处理结论 |
|---|---|---|---|---|---|---|---|

每行必须填写实际执行报告 ID、API Case ID、失败报告记录的任务环境、具体执行场景、实际动作（未修改时写 `未修改资产`）、明确的 `是`/`否` 修复结论，以及唯一处理结论。`处理结论` 填写为 `修复成功`、`需要业务开发修改代码`、`需要测试平台修复`、`需要外部提供测试条件` 之一。`修复成功` 的 `失败原因` 统一填写 `—`；修复失败只能填写证明其对应处理结论的原因。Case 原始失败根因放在表后的“根因证据”中。

汇总表后还必须说明：

- Case ID/名称及所属报告、`test_suite_detail_id`；
- 根因证据；
- 修改的 API Info/步骤/场景/断言/数据来源；
- 修改过断言时，分别说明原测试目标是否改变、旧/新断言对相同响应的关键判定差异、缺陷检出能力失去或新增了什么及权威依据；
- 编辑态执行结果和时间；
- 新 Case 修订/发布版本；
- 原报告行重试结果；
- 修改前后 Case/步骤/场景数量，删除/停用/解绑数量；
- 历史报告口径：原失败 Case 数、原失败行数、原失败执行单元数；
- 当前治理口径：`修复成功`、`需要业务开发修改代码`、`需要测试平台修复`、`需要外部提供测试条件`数量，当前仍会进入定时任务的 Case 数，以及未完成调查数（批次完成时必须为 0）；
- 非`修复成功`项的结论证据、责任方、下一步动作和验收条件。

只有完整编辑态验证通过、发布成功且要求精确重试的所有原报告行均通过时，`是否修复成功` 才能写 `是` 且处理结论为 `修复成功`。三个修复未成功结论的 `是否修复成功` 均写 `否`；不得用笼统状态替代责任和动作。

每批完成后，列出最多 50 个下一批候选：

| 候选 Case | 所属报告 | 推断测试点 | 初步根因 | 建议处理结论 | 建议动作 |
|---|---|---|---|---|---|

建议处理结论填写为 `修复成功`、`需要业务开发修改代码`、`需要测试平台修复`、`需要外部提供测试条件` 之一；证据不足只是内部待取证工作，不是终态。该表是进度说明，不请求确认；按已授权范围自动续批。只有用户限定本批/指定 Case、范围已完成或真正缺少授权/访问/业务决策时才停止。

如果已经没有下一批候选，必须执行一次覆盖本次用户所选完整范围的最终收口，不能只写“没有下一批”，也不能只重复最后一批：

先按第 9 节单列全部“已验证，待用户手动发布”项及英文逗号连接的可复制 Case ID 行；它们是待发布/回放的交接项，不混入下方三类修复失败结论。清单非空时不得宣称所有 Case 已修复成功，用户发布后继续第 10 节精确重试。

1. 汇总所有批次中 `是否修复成功=否` 的 Case，不得遗漏已经在前序批次给出终态的项目。
2. 只要存在未修复成功项，输出标题 `全部未修复成功项`，并使用完整固定列再次列出：

| 执行报告 ID | Case ID | 任务环境 | 执行场景 | 修复内容 | 是否修复成功 | 失败原因 | 处理结论 |
|---|---|---|---|---|---|---|---|

3. 表后逐项给出责任方、下一步可执行动作和修复后的验收条件。处理结论填写为 `需要业务开发修改代码`、`需要测试平台修复`、`需要外部提供测试条件` 之一，不得使用笼统的“无法修复”。
4. 如果完整范围内所有 Case 的处理结论都是 `修复成功`，明确写出“所有失败 Case 均已修复成功，无未修复成功项”，此时不需要输出空表。
5. 最后明确写出“本次所选范围已无下一批”。没有候选时不得再请求用户确认是否继续。

文档上传按入口流程区分：明确直接修复时不上传前置诊断文档，每批仅在存在 `是否修复成功=否` 的 Case 时上传该批修复结果 Markdown；全部修复成功则不上传。两阶段确认修复必须在用户确认前先上传诊断 Markdown，并在对话中发送 Markdown 确认表；修复后不重复上传结果文档，除非用户另行要求。

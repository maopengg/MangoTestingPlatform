# 数据源使用与 ES 资源恢复

## 先确定创建方

| 类型 | 正确使用 | 不可推断 |
| --- | --- | --- |
| MySQL／其他 SQL | 实体、模板构造 SQL 数据；自增/数据库生成列跳过，输出插入后真实值 | SQL 行删除不等于 ES、Redis 或文件已清理 |
| ES 派生文档 | 业务异步同步产生；工厂用 cleanup_resources，API 创建用 Case resource_cleanup | 平台不会自动创建索引、模拟业务同步，也没有独立 ES 工厂模板 |
| Redis | 按当前工具 Schema 做获准查询，或正式 Case 已保存的受支持操作 | 数据源有执行审计不等于已有工厂 Redis 自动清理；不能猜键、清空库或扫描前缀批删 |

查询能力不构成写入授权；不使用脚本、临时 Case 或 Redis/ES 工具绕过 MCP SQL 直查禁令。资源由 API 创建时，读取 API Case Skill 的资源清理教程，不伪造工厂执行记录。

## 三种身份、两种语法

分别核实 SQL 物理主键、业务 ID、ES 文档 ID。例如 `_id`、`id`、`group_id` 可能不同；以实际同步代码为准，不按表名统一套用。显式 document_id_field 缺值不能回退主键。业务 group_id 需要调用方生成时，可使用合法生成器，但不能给数据库自增主键生成雪花 ID。

- index_template 的 `{tenant}` 是索引模板占位符，支持单独使用及末尾带前缀；固定精确索引也允许。
- Case/字段值的 `${{变量名}}` 是运行时表达式，不放进 index_template 冒充占位符。
- 查看预览的 resource_cleanup_preview：物理主键字段、文档 ID 来源及示例值、最终索引、租户路径、模式、pending_fields。deferred_until_execution 表示尚待真实运行解析，environment_checked=false 不是环境资格通过。
- ES 404 先区分 index_not_found 与精确 found=false。前者需核对环境、模板及索引初始化，不能创建空索引绕过。

## 选择模式与证明归属

verify 只等待并验证业务同步删除，不会主动 DELETE。只有获准精确清理/补偿时选 delete_and_verify；既有授权是否覆盖见下文，观察失败本身不构成升级模式的授权。

根租户字段缺失的局部聚合文档，可在未来模板中使用已有 tenant_lineage。核对实际父子字段、同执行/同数据库绑定及完整子记录集合；需要配置的结构为：

```json
{
  "entity_id": 52,
  "parent_field": "parent_id",
  "tenant_field": "tenant_id",
  "id_field": "id",
  "collection_path": "rounds",
  "document_id_path": "roundId"
}
```

数字和字段均是示例，必须换成已核实的真实配置。根字段存在但为 NULL/错误租户，不能回退关联证明；子 ID 缺失、多出、重复、跨租户或不属于本执行同绑定，必须拒绝。只有原冻结的本轮已创建子记录可作为事实来源，不能把存量行或调用方传入的 ID 填成证明。

## 补偿授权范围

- 区分用户授权与工具确认协议。用户已要求“处理本轮残留”“修复这些执行的清理并确认零残留”，且已明确非生产环境及 Case、执行或批次范围时，对范围内已证明属于本轮的 SQL/ES 资源，直接走正式预览和精确清理，不逐条重复请示。历史记录中的“本轮”按用户指定执行归属判断，不因记录发生在过去就一律要求再次授权，也不把它扩大到全部历史数据。
- 操作前核对并简要告知精确目标、归属证据与清理方式；已有授权覆盖时这是进度说明，不是新的阻塞确认。每次仍须调用正式影响预览，回传相同参数及有效 token/确认文本。预览、授权保存、任务创建均不等于清理成功。
- token 过期或文档版本变化时旧确认不可复用。先停止当前删除，重新核查归属与目标并取得新预览凭据；仍属原授权范围且安全条件满足时无需再问用户。归属不确定、版本持续变化或工具校验不通过时停止该项并报告，不盲目重试、强删或扩大条件；用户批准不能替代技术证明。
- 原授权仅为查询/分析、仅 verify、仅配置或没有包含真实删除时，以及发现其他执行/租户/环境、共享/存量资源或需扩大清理范围时，先说明差异再请求明确授权。对本轮残留的补偿授权不自动授权修改公共模板、未来执行清理模式、业务资产或重新造数/重跑 Case。
- 不变的安全门禁：原执行已结束、原快照及基线事实可用、索引 UUID 与精确文档 ID 一致、租户/完整子记录归属证明合格、当前版本条件删除、完整观察及连续缺失回查。禁止通配删除、跳过校验、改原快照或直接改平台数据库。

## 历史失败处理，不重跑业务创建

先读原执行、原快照及 SQL／ES 分资源状态，确认原创建执行已结束。模板更新只影响以后执行，不修改旧 snapshots。

1. 原规则已有充分证据：先调用 preview_cleanup_data_factory_execution_impact，核对影响后使用原参数、token 和确认文本调用 cleanup_data_factory_execution。
2. 原 SQL 已清理，ES 仍存在，且需要补充子记录映射或将原 verify 显式授权为精确补偿：先确认实际工具签名支持 compensation，再使用同一个预览/执行入口。不要新增工厂执行接管旧文档。
3. compensation 只允许原 item_id、snapshot_index、reason、可选 tenant_lineage。平台读取原执行证据并冻结当前文档版本，不能提交租户、索引、文档 ID 或跳过校验开关。
4. 核对上述授权范围：已授权处理本轮残留的，告知精确目标与证据后直接继续；未覆盖或扩围才向用户确认。回传相同 compensation 与正式预览确认凭据。确认绑定用户、原快照、参数和文档版本，变化后必须重新核查并预览，不反复执行已失效的 token。
5. 查清理与恢复历史及完整观察结果；失败只重试原资源清理，不发送业务创建，不重跑整例。原执行缺索引 UUID、有效所有权事实或结束证据时停止自动补偿，报告缺口；用户批准不能替代技术证明。

部署尚无该参数时报告版本差异，不绕过 MCP 操作平台库。不要宣称可以补偿任意历史资源。

## 解释结果

- SQL 已验证、ES 未确认：不是整体零残留，未知残留数不能当成 0。
- 业务全部通过、清理失败：保留业务结果，整体不能算通过；优先清理恢复，不重新造数。
- DELETE 超时：原审计保留超时；先按冻结目标回查，完整观察通过才解决对应异常。单次当前 404 不证明历史验证合格。
- 查看 get_data_factory_execution_detail 的 cleanup_history，可分页读取每次开始、失败、成功及补偿授权；API 台账查询以 resource_id 定位后可分页读取历史。当前错误清空不表示旧失败被删除。
- 历史复用原工厂明细 cleanup_resources / API 资源 proof 的追加记录，不需要另建表或伪造 SQL/ES 操作审计。读取分页历史即可，不直接改 JSON、原快照或授权证据；没有历史字段的旧记录只表示未登记，不能推定从未失败。历史随原台账生命周期保留，不能当作永久档案。
- 不按“15 秒规则”直接推断整个任务必须 15 秒完成；区分 SQL 阶段、ES 阶段的实际处理时间、轮询、调度和连接等待。长请求不应被误当调度中断，但真正恢复后的空白时间不能算完成观察。

最终记录创建方、Case/Trace、工厂执行与明细、原模式、补偿授权、精确索引与文档、失败及恢复过程、SQL/ES 验证范围和未确认项。不因单个成功样本或历史错误码推断全部执行当前状态。

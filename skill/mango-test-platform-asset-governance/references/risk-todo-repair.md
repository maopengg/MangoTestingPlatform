# 风险待办修复流程

仅在用户要求排查或修复首页风险待办时读取本文件。目标是解除真实风险并验证待办状态，不是清空待办数量。

## 当前支持范围

当前平台已落地以下风险：

| 来源模块 | 待办类型 | 正确处理方式 | 是否允许人工确认 |
|---|---|---|---|
| 前端自动化 / 授权管理 | 授权即将到期、授权已过期、授权刷新失败 | 更新或刷新授权，验证有效期和刷新结果后由系统关闭 | 否 |
| 服务自动化 / 授权管理 | 授权即将到期、授权已过期、授权刷新失败 | 更新或刷新授权，验证有效期和刷新结果后由系统关闭 | 否 |
| 数据工厂 / 数据模型 | 数据模型无效 | 按目标环境真实表结构修复模型并重新扫描，恢复有效后由系统关闭 | 否 |
| 数据工厂 / 数据模型 | 数据模型结构待确认 | 核对结构差异，确认风险消失、停用/删除模型，或在人工完成确认后逐条处理 | 是 |
| 数据工厂 / 执行记录 | 数据工厂清理失败 | 修复清理配置并重试清理；执行成功或记录删除后系统关闭。已在线下清理且证据完整时可逐条确认 | 是 |

未在平台事件枚举和查询结果中出现的规划中待办，不得声称已经支持或已经修复。

## 通用流程

1. 解析用户有权限的项目产品和待办范围。调用 `list_workbench_todos` 分页查询待办，并按项目产品、来源、事件类型或严重程度缩小范围；需要完整上下文时调用 `get_workbench_todo_detail`。部署版本未暴露这些工具时，要求使用用户提供的待办 ID、类型、底层资产 ID 和详情，不得访问数据库补查。
2. 保存处理基线：待办 ID/类型/严重程度、项目产品、负责人、底层资产 ID、异常摘要、发生时间、`can_mark_handled` 和当前状态。
3. 查询底层资产的当前状态，确认待办仍然有效。待办已被系统关闭时不重复修改资产。
4. 根据待办类型执行最小修复。修改前读取完整配置及影响范围；涉及删除、解绑、停用或覆盖时必须执行 MCP 影响预览并取得用户确认。
5. 验证真实异常已经解除，调用 `refresh_workbench_todos` 触发同步，再使用列表或详情工具确认自动关闭；不能只根据修复接口返回成功就宣称完成。
6. 若部署版本没有待办复查能力，报告“底层资产已验证，待办关闭状态无法通过 MCP 复核”，不要假报已关闭。
7. 输出修复清单、验证证据、关闭方式和仍存在的风险。失败项保留原状态，不进行批量已处理。

## 授权待办

- 核对授权类型、项目产品、环境、刷新方式、到期时间、最近刷新时间和刷新错误。
- 仅通过正式 MCP 授权能力更新凭据或触发刷新；不得读取、回显或记录完整 Token、Cookie、APIKey、密码等敏感值。
- 修复后验证授权状态、有效期和最近刷新结果。授权配置停用或删除属于独立业务动作，不能为了关闭待办擅自执行。
- 授权风险可由系统客观检测，禁止人工标记已处理。

## 数据模型待办

- 必须按待办对应的具体环境调用表结构查询，核对主键、自增、字段类型、长度、默认值、可空性及关系。
- 修复模型时保留现有模板和依赖关系；不得通过删除字段、模板或关联来规避结构异常。
- 自增主键、随机值 `AUTO` 前缀、实体字段合并、递归模板修复和启用验收统一遵循 `../../mango-data-factory-builder/SKILL.md` 及其实体修复流程；自增主键不得配置非零生成器或覆盖值。
- “数据模型无效”必须在重新扫描并恢复有效后由系统关闭，不能人工确认。
- “结构待确认”只有在差异已核对、风险已由人工接受或已线下处理，且详情返回 `can_mark_handled=true` 时，才能通过 `update_workbench_todo_handled` 逐条确认并填写处理依据。新结构差异应产生新事件，不能沿用旧确认掩盖。

## 数据工厂清理失败待办

1. 读取执行编号、模板、环境、数据源、失败项、成功/失败/跳过数量、表名和错误摘要。
2. 区分 SQL/表达式错误、数据源连接失败、事务回滚、依赖顺序错误、超时和部分清理失败；不能只重试而不处理原因。
3. 修复清理配置后重新执行清理，逐项核对执行级与明细级清理状态。
4. 在非生产环境，通过 MCP 支持的残留检查确认自动化生成的数据为零；生产环境禁止在测试平台配置或执行 SQL、数据工厂清理和直接数据库修复。本地电脑已有合法生产连接时，仅可在平台外执行只读 `SELECT` 诊断，严禁任何增删改或其他写操作，也不得把连接、凭据或 SQL 写入平台。
5. 只有清理状态全部成功且残留为零，才能报告风险已修复。部分成功仍视为失败。
6. 用户已在线下完成清理时，必须获得执行编号、处理对象和残留验证证据；仅当 `can_mark_handled=true` 时通过 `update_workbench_todo_handled` 逐条人工确认并记录证据。
7. 同一次失败人工确认后不得要求系统立即重新打开；后续重试产生的新失败按新的事件处理。

## 验收条件

- 底层资产状态符合预期，且未削弱 Case、模板、数据模型或任务覆盖。
- 可自动检测的风险已由系统关闭；允许人工确认的风险记录了处理人、处理时间和处理依据。
- 数据工厂清理失败的执行级和所有明细级状态均成功，残留检查为零；否则明确列出失败项。
- 没有通过 SQL、ORM、内部接口或直接修改待办表绕过 MCP。
- MCP 能力不足时明确列出缺失的查询、修复、同步或人工处理能力。

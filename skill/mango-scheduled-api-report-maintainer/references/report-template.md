# 测试报告排查文档模板

本模板仅用于已核实由所选项目/产品的定时任务生成的报告。排查必须覆盖确定范围内的所有失败 API Case；每批 50 个 Case 的限制只适用于修复批次。

根据当前模式选择一级标题：

```markdown
# {项目}/{产品}｜{定时任务名称}｜测试报告 {报告ID}｜排查时间 {YYYY-MM-DD HH:mm:ss}
```

```markdown
# {项目}/{产品}｜{定时任务名称}｜测试报告 {最早报告ID} 至 {最新报告ID}｜排查范围 {开始时间}～{结束时间}｜排查时间 {YYYY-MM-DD HH:mm:ss}
```

项目/产品范围包含多个定时任务时，使用产品级一级标题，在报告概况中标明各任务及其报告；按任务拆分文档，分别上传到对应定时任务。

## 编写约束

- 第 1 节汇总指定报告或所选定时任务报告的完整范围，不阅读后续章节也应能理解结论。
- 每个 Case 只保留一个主要根因；次要影响写入“失败现状”。
- 有对应记录时，使用准确的报告、Case、步骤、场景、修订版本和发布版本 ID。
- 定时任务模式列出扫描到的所有已完成报告，但只排查至少在一份报告中失败的 Case。
- 每个失败 Case 只写一次，将全部失败记录合并在该 Case 下。
- 优先使用简短对照表，避免冗长时间线叙述。
- 不在报告结论和 Case 详情中重复同一段响应 JSON。
- 可选字段没有内容时省略，不得编造。
- 每个诊断小节通常使用一句话或紧凑的键值列表；每个 Case 只保留最有力的 1～3 项证据。
- 从 `1. 失败现状` 开始编号。只有存在历史成功执行时才保留“为什么以前成功”；否则删除该标题和内容，“明确根因”“直接修复方案”从 `2.` 起连续编号。
- 编号诊断项使用 `####` 标题，不将“失败现状”或诊断顺序写成表格。
- 根因明确时，在“明确根因”下使用 `##### 测试平台问题` 和 `##### 断言问题`，分别填写“是/否 + 原因”；其他原因只有核实后才增加标题。判定“测试平台问题=是”必须有已验证的平台 Bug 或必要能力缺失证据，并明确区分二者。修复前排查可以保留待补证据，但不能将其作为已完成的修复失败结论。
- 不罗列所有正常的平台子系统，只说明选定的问题分类和直接原因。
- 直接原因是 Case、API Info 或数据工厂资产配置错误时，归为“测试用例问题”（`test_case`），不得归为“测试平台问题”。
- 同一根因不要在第 1、3、4 节重复叙述：第 1 节分类汇总，第 3 节提供证据，第 4 节给出动作。
- “修复建议与结论”下必须有“建议处理结论与可执行动作”表，每个去重后的失败 Case 一行，列固定为 `Case ID`、`Case 名称`、`原因`、`是否能直接修复`、`建议处理结论`、`建议动作 / 待补证据`。已完成结论只能是“修复成功”“需要业务开发修改代码”“需要测试平台修复”“需要外部提供测试条件”之一；证据不足的保持“待判定”，不得计为完成。
- 用户要求修复时，使用 `../mango-api-case-builder/SKILL.md`：修改编辑态，在原失败报告环境完整验证后提交预发布，输出“已验证，待用户手动发布”清单，并单独给出英文逗号连接、无空格的真实 Case ID 行，如 `1,3,222,12`。用户页面手动发布并确认后，回读正式版本与已验证候选一致，再逐条重试受影响的原报告失败 Case 行；AI 不正式发布。待发布单列为交接阶段，不强行归为修复失败，也不提前称修复成功。不得重跑整份报告或定时任务制造通过结果。
- 修复已授权后，常规前置、数据、清理和配置工作持续推进，不再询问是否继续或开始下一批。未成功场景必须按 repair-workflow 第 4.5 节给出业务代码、测试平台或只能由外部提供条件的证据，不以“尚待验证/前置方案待完成”作最终结果。外部条件必须写明具体缺项、必要性及来源证据、已穷尽的安全替代方案、提供方、交付物和恢复/验收条件；“是否修复成功”填“否”，不得称为 Bug。保留要求的八列结果，详细证据补在表后；外部条件项必须纳入最终全部未修复清单及失败结果上传。失效场景另行治理，证据未完成不算结论完成。

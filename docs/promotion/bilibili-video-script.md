## 视频定位

用一条可理解的业务链路展示芒果测试平台，而不是逐个朗读菜单。观众看完后应该知道平台解决什么问题、与普通脚本执行器有什么不同，以及如何开始体验。

**建议时长：** 10～12 分钟

**目标观众：** 测试工程师、测试开发、质量平台负责人、正在建设自动化体系的研发团队

## 视频简介

芒果测试平台是一套可私有部署的开源低代码质量工程平台，支持 API、UI、Pytest、测试数据工厂、任务调度、远程执行、测试报告和 MCP/AI。

本视频通过一条完整链路演示：配置测试环境、准备测试数据、执行自动化用例、查看报告，以及 AI 如何通过 MCP 读取平台资产并辅助分析问题。

## 分镜与口播

### 00:00—00:25 开场：先展示结果

**画面：** 快速切换数据工厂执行记录、API 用例运行、测试报告和 AI 对话页面。每个画面停留 3～4 秒。

**口播：**

> 这是我持续维护的开源项目——芒果测试平台。它可以统一管理 API、UI 和 Pytest 自动化，也可以在执行前自动准备测试数据、执行后生成报告，再通过 MCP 让 AI 读取测试资产和分析结果。这条视频不逐个介绍菜单，我会直接跑一条完整链路。

### 00:25—01:15 为什么做这个平台

**画面：** 简洁流程图，展示脚本、环境、测试数据、定时任务和报告原本分散的状态。

**口播：**

> 很多自动化都是从个人脚本开始的。脚本少的时候没有问题，但数量增加后，环境配置、账号、测试数据、执行机器和报告会散落在不同地方。真正消耗时间的，往往不是写出第一条脚本，而是长期维护、稳定执行和失败排查。
>
> 芒果测试平台想做的，是把这些环节放进同一个可追踪的执行链路，而不只是提供另一个脚本启动按钮。

### 01:15—02:05 平台结构

**画面：** 首页或项目配置页，随后展示简化架构图。

**屏幕文字：**

```text
项目与环境
→ 测试资产
→ 测试数据
→ 调度与执行
→ 报告与分析
```

**口播：**

> 平台按照项目、产品、模块和测试环境组织资产。Web 控制台负责配置和查看结果，后端负责任务与权限，API Worker 执行接口任务，独立执行器承接 UI 和 Pytest，Scheduler 处理定时触发，MCP Service 则把平台能力提供给 AI 客户端。

### 02:05—03:20 配置 API 用例

**画面：**

1. 进入接口定义列表。
2. 打开一条演示接口。
3. 展示请求方法、路径、参数和请求体。
4. 进入 API Case，展示步骤、场景、响应提取和断言。

**口播：**

> 这里是一条 API 自动化用例。接口定义只保存可复用的请求信息，用例再通过步骤和场景组织具体业务流程。不同输入组合可以放在同一步骤的多个场景中，响应中的 ID 或状态可以提取成变量，供后续请求、断言和清理使用。

**提示：** 演示数据统一使用 `example.com` 或本地演示服务，不展示真实业务域名、Token 和数据库信息。

### 03:20—05:20 数据工厂：自动准备数据

**画面：**

1. 打开逻辑数据源与环境绑定。
2. 展示一个演示实体及字段规则。
3. 打开状态模板。
4. 预览即将生成的数据。
5. 展示用例与数据模板的绑定。

**口播：**

> 这条用例执行前需要一条满足特定状态的数据。传统做法通常是在用例里写一段前置 SQL，但 SQL 很容易和环境、表结构以及清理逻辑耦合。
>
> 数据工厂把它拆成逻辑数据源、环境绑定、业务实体、字段规则和状态模板。同一个模板在不同环境执行时，会自动找到对应的真实数据库。用例可以直接引用工厂输出的字段，执行记录也会保留创建和清理状态。

**屏幕文字：**

```text
环境解析 → 自动造数 → 变量引用 → 执行验证 → 数据清理
```

### 05:20—06:45 执行用例

**画面：**

1. 选择测试环境。
2. 点击执行，并展示按钮 loading。
3. 展示任务进入执行队列。
4. 查看步骤状态逐步更新。

**口播：**

> 选择环境后执行用例。平台会先处理绑定的数据工厂配置，再把 API 任务交给 Worker。UI 和 Pytest 等需要特定运行环境的任务，则可以交给远程执行器。
>
> 对团队来说，任务是谁触发的、在哪个环境运行、当前处于什么状态，以及失败发生在哪一步，都应该能够被追踪。

### 06:45—07:55 查看测试报告

**画面：**

1. 打开本次执行报告。
2. 展示汇总状态和耗时。
3. 展开请求、响应、断言和提取结果。
4. 展示失败信息或一条预先准备的失败演示记录。

**口播：**

> 执行结束后，报告不仅显示通过或失败，还会保留每个步骤的请求、响应、断言、变量和错误信息。UI 自动化失败时还可以回传截图和日志。报告应该是问题排查入口，而不是一张只能看的结果表。

### 07:55—09:35 MCP 与 AI 演示

**画面：**

1. 打开 MCP 服务和工具列表。
2. 在 AI 助手中输入一个明确任务。
3. 展示 AI 查询项目、用例或报告。
4. 展示工具调用结果和最终总结。

**推荐演示问题：**

```text
查询演示项目最近一次失败的 API 自动化报告，汇总失败步骤，
并判断问题更可能来自请求构造、断言还是测试数据。
```

**口播：**

> AI 部分不是让模型绕过平台直接操作数据库，而是通过 MCP 使用平台明确提供的工具。AI 可以先读取项目上下文和已有资产，再查询执行报告、汇总失败信息。
>
> 对创建、修改、执行或清理这类操作，平台仍然需要结合权限、风险分级和审计进行约束。我的目标不是让 AI 完全接管测试，而是让它成为了解团队测试资产的工程助手。

### 09:35—10:25 适用场景与边界

**画面：** 使用清单展示适合与不适合的场景。

**口播：**

> 如果你只需要临时调试几个接口，轻量接口工具会更方便；如果只有少量稳定脚本，Pytest 加 CI 也完全够用。
>
> 芒果测试平台更适合已经有一定自动化规模，需要统一管理环境、用例、测试数据、执行任务和报告，并且希望私有部署的团队。平台化能够解决协作和治理问题，同时也会带来部署维护成本，这一点需要根据团队实际情况选择。

### 10:25—11:00 结尾与行动引导

**画面：** 展示 Gitee 仓库、帮助文档和 Issue 页面，不连续展示多个二维码。

**口播：**

> 芒果测试平台已经在 Gitee 和 GitHub 开源，演示环境和部署文档也可以直接访问。如果你正在建设自动化平台、测试数据体系，或者探索 AI 在测试中的应用，欢迎体验并提交 Issue。

## 正文

芒果测试平台最初主要解决 API 和 UI 自动化的配置、执行与报告问题。随着测试资产和团队协作规模增长，我们发现真正需要连接的不只是“用例和执行器”，而是从需求进入、测试设计、数据准备，到自动执行、失败诊断、缺陷反馈和质量复盘的完整过程。

7.1.1 围绕这条主线补充了一批能力。以下内容可以提前公开交流，相关代码、演示环境和帮助文档会按版本逐步开放。

### 1. 研发协同：从需求到缺陷的测试闭环

新增和完善迭代、需求、开发设计、功能用例、测试计划与缺陷管理。功能用例支持表格式连续编辑、版本历史和自动化绑定，测试计划可以进入执行并汇总结果。

这部分关注的不是替代专业项目管理工具，而是让测试团队能够在同一处回答：

- 一个需求设计了哪些测试；
- 哪些用例已经绑定自动化；
- 本轮计划执行了什么；
- 失败和缺陷如何回到需求上下文；
- 当前迭代还存在哪些质量风险。

### 2. API 自动化：模块覆盖、版本管理与 Mock 服务

API 自动化新增或增强以下方向：

- 接口与用例版本管理，执行步骤可以固定需要的接口版本；
- 模块覆盖扫描与接口级覆盖流程，用于观察模块、接口与用例之间的覆盖关系；
- 执行链路与结果诊断，帮助定位请求构造、提取、断言和环境问题；
- Mock 服务，可配置请求匹配条件、响应内容和断言，并查看请求记录；
- 多环境变量、认证配置和调试体验持续完善。

模块覆盖强调的是“当前资产覆盖了哪些接口和流程”，不是用一个百分比代替人工判断；Mock 则用于依赖未就绪、异常分支和稳定回归等场景。

### 3. UI 自动化：实时工作台与智能定位、自愈

UI 自动化继续完善元素检测、录制、运行画面和结果同步，并引入智能定位与自愈流程。

当页面结构发生变化时，系统可以结合元素信息、页面快照和运行上下文生成候选定位方案，并把验证结果保留在可审查的流程中。目标是减少常见页面变更带来的维护成本，而不是让 AI 在没有验证的情况下静默修改用例。

最新版还加强了页面步骤流程的 AI 修复与执行器诊断，便于从失败画面、元素变化和运行状态继续排查。

### 4. 性能测试：场景、计划、运行历史与执行容量

性能测试从单次运行扩展为场景配置、测试计划、运行历史和执行器容量管理，并支持分阶段负载、实时指标、调度和结果收敛。

性能执行仍然需要明确的目标、容量边界和测试环境。平台提供的是配置、调度、观测和记录能力，不建议在没有授权与限流方案的情况下直接对生产环境压测。

### 5. 数据工厂：更可靠的环境映射与执行审计

数据工厂继续完善多类型数据源、环境绑定、字段规则、关系展示、结构变更检测和用例回写，并把 SQL 执行纳入统一审计上下文。

用例仍然只描述需要的业务状态，平台负责解析当前环境、创建数据、回写变量并按策略清理。对于可能修改业务数据的 SQL，最新版加强了服务端执行和审计链路。

### 6. 质量报告：从执行记录到效能与风险

报告中心在统一 API、UI、Pytest 等执行结果的基础上，增加质量效能和风险视角，用于汇总执行趋势、失败原因、需求测试进展和待处理事项。

指标只应作为定位问题的入口。每个汇总结果都需要能够回到原始任务、步骤、断言或缺陷，避免形成无法解释的“漂亮数字”。

### 7. 调度与执行：多场景、多环境和更清晰的运行状态

定时任务支持更灵活的场景与环境配置，执行通知和任务状态进一步统一。执行器侧完善了仪表盘、实时结果同步和多端兼容，Pytest 仓库与执行管理也得到增强。

调度目标是让一次执行的触发来源、环境、版本、运行节点、结果和通知都能被追踪，而不只是定时启动一个脚本。

### 8. 工程治理：灰度、SQL 审计与统一异常中心

最新版补充灰度仓库、配置文件、灰度开关和执行记录等管理能力，并持续完善 SQL 执行审计、用户操作日志、系统任务、自动化执行结果和异常中心。

前端、服务端和执行器的系统异常可以进入统一记录并按来源筛选，减少故障信息分散在不同机器和日志文件中的情况。

### 9. MCP 与 AI：技能、工具和执行过程可管理

平台继续完善技能管理、MCP 服务、工具选择和 AI 执行记录。AI 可以在明确上下文中查询和维护测试资产、辅助生成测试设计、分析报告或参与 UI 修复流程。

所有能力仍遵循同一原则：读写边界清晰、危险操作可约束、执行过程可追踪、结果能够由测试人员复核。

# 统一测试平台资产治理

## 目标

把测试平台资产整理到业务语义清晰、名称与实际内容一致、生产标签和定时任务绑定正确、可长期维护的状态。

支持三个互不混用的模式：

1. **名称清洗模式**：审计和修改 API Info、API Case 名称，默认只改名称。
2. **执行场景与调度治理模式**：在测试、预发、生产等目标环境审计和修改 Case 执行场景、显式任务绑定、动态规则匹配及发布/调度状态；生产环境额外应用生产安全规则。
3. **风险待办修复模式**：定位首页风险待办对应的真实资产，修复授权或数据工厂异常，验证风险解除及待办自动关闭；只有产品规则明确允许的待办才能人工确认已处理。

## 硬性边界

- 所有测试平台资产查询和修改必须通过 `mango-test-platform` MCP。
- 禁止通过 SQL、数据库连接、Django ORM、Django shell、管理命令、后端 service 或绕过 MCP 的 HTTP 请求查询或修改平台元数据。
- MCP 没有暴露所需能力时停止并报告缺失能力，不得绕过。
- 名称清洗模式只更新名称字段。不得顺带修改模块、负责人、步骤、绑定接口、场景、参数、请求头、变量、断言、数据工厂、清理逻辑、标签或执行配置。
- 执行场景与调度治理模式只处理用户授权范围内的 Case、标签、任务绑定和任务配置；不得借机改名或删除 Case。需要修复请求、场景或断言时，必须获得相应授权并同时遵循 API Case Builder 的环境、安全和验证规则。
- 风险待办修复模式必须修复待办指向的底层资产，不能直接修改待办状态来掩盖仍存在的异常。不得通过数据库、ORM、后端 Service 或内部 HTTP 接口查询、关闭或删除待办。
- 部署版本没有暴露待办查询或人工处理能力时，只能根据用户提供的待办信息修复 MCP 已暴露的底层资产，并报告待办查询/处理能力缺口；不得绕过 MCP 补做操作。
- 只有接口返回 `can_mark_handled=true` 且已取得真实人工处理证据时，才允许调用 MCP 的人工处理能力。不得批量标记已处理，也不得用人工确认代替可客观检测的修复结果。
- 删除、合并、移动、解绑等结构性操作必须单独说明影响，并遵循对应 MCP 的预览和二次确认要求。
- 解绑 Case、停用任务、删除任务是三类不同操作。清空绑定后不得自动停用或删除任务；必须分别审计、预览并取得相应授权。
- 测试平台禁止配置或使用生产 SQL、生产数据库连接、数据工厂准备/清理，以及任何通过平台绕过正式产品 API 的数据修复。本地电脑已有合法、可用的生产连接时，可在平台外执行与任务直接相关的只读 `SELECT` 诊断；严禁增删改、DDL、权限变更及其他写操作，也不得把连接、凭据或 SQL 配置到测试平台。

## 模式选择

- 用户只说“整理名称、清洗资产名称、名实不符”时，使用名称清洗模式。
- 用户提到无法持续完成测试、退出正式调度、稳定性监测、生产巡检、生产回归、执行场景、定时任务绑定、任务清理、生产安全或批量解绑时，使用执行场景与调度治理模式；该模式适用于所有环境，不以生产环境为前提。
- 用户提到首页风险待办、授权到期/刷新失败、数据模型失效/结构待确认、数据工厂清理失败或“修复代办异常”时，使用风险待办修复模式，并读取 [风险待办修复流程](references/risk-todo-repair.md)。
- 风险待办涉及数据模型、场景模板、数据工厂执行或清理时，还必须完整读取并遵循 [`../mango-data-factory-builder/SKILL.md`](../mango-data-factory-builder/SKILL.md) 及其按当前操作路由的参考流程。数据工厂 Skill 负责底层资产修复和验收，本 Skill 负责待办范围、关闭方式与治理审计；冲突时采用更严格的安全边界。
- 同时要求多类治理时，分开清单、修改批次和验证结果，不得把名称更新、调度变更与风险待办处理混在同一确认中。

## 事实来源

按以下优先级判断资产的真实业务含义：

1. Case 实际绑定的 API Info、步骤和场景参数。
2. Case flow、场景名称、断言、描述和执行结果。
3. API Info 的 method、规范化 URL、请求结构和描述。
4. 用户提供的接口文档、飞书文档、测试用例、curl、代码仓库中的 controller/service/DTO。
5. 资产现有名称。

名称与实际步骤、断言或代码冲突时，以更接近真实执行路径的证据为准。证据不足时标为“需人工确认”，不要猜测后修改。

## 全量扫描流程

1. 解析用户指定的项目产品；用户要求“全部”时，使用 MCP 列出有权限的全部项目产品。
2. 分页拉取完整资产，直到每个项目产品没有下一页。不得只扫描第一页。
3. 记录总数和各项目产品数量，并保存已处理 ID，避免重复建议或重复修改。
4. 首轮用名称、描述和 case flow 做低成本筛选。
5. 对疑似名实不符的 Case 调用完整详情，核对绑定 API、步骤、场景和断言。
6. 必要时扫描代码或读取用户提供的文档，确认真实业务动作。
7. 把问题分为：确定需要修改、需人工确认、仅结构问题、无需处理。
8. 只向用户展示“确定需要修改”的名称；除非用户要求，不展示正常资产。

## API Info 名称规则

API Info 名称只保留接口执行的业务动作或能力名称，标准比 API Case 严格。

### 应保留

- 动词加业务对象，例如 `查询付款记录`、`上传订单文件`、`移除角色成员`。
- 必要的业务限定，例如 `查询开放平台管理员列表`、`重置 Verification Token`。
- 区分真实业务能力所必需的版本含义；能用业务词表达时不用 `v1/v2`。

### 必须移除

- 测试场景、固定数据、文件编号、成功/失败结果、正向/负向、边界、巡检等 Case 信息。
- 产品、项目、模块、菜单、页面、服务、客户端和环境前后缀。
- HTTP 方法、协议、域名、URL、路由、路径片段。
- 测试编号和来源编号，例如 `FHSDK-DOC-033`、`TC_API_001`。
- `@人名`、`@codex`、负责人姓名和无业务意义的 bot 标记。
- `本地完整迁移`、`调试接口`、`基础覆盖`、`测试接口`、问题定位记录等维护备注。
- 原始代码方法名、脚本名或类名；将其转换为业务动作。

示例：

- `上传文件-订单二docx` -> `上传文件`
- `FHSDK-DOC-033 更新字段` -> `更新字段`
- `系统管理-后台配置-订单列表导出` -> `订单列表导出`

## API Case 名称规则

API Case 名称以准确、自然、不误导为目标，不套用 API Info 的“只留接口作用”规则。

### 允许保留

- 只写业务功能，例如 `查询模板自定义字段`。
- 测试场景、条件、数据、结果或场景组，例如 `无效字段ID`、`跨租户场景`、`正向负向覆盖`。
- 有追溯价值的测试编号，例如 `FTAPI-0001`、`TC_API_002_014`、`CT05-007`。
- 有意义的字段名、枚举值、文件名和固定测试数据。
- `成功`、`失败`、`异常`等结果词，但必须与实际断言和执行意图一致。

Case 名称不要求一定包含测试场景。名称没有写场景，不构成修改理由。

### 确定需要修改

- 包含 `@人名`、`@codex`，或把负责人/创建人当作维护备注写进名称。
- 名称只是原始方法名、脚本名、代码标识或无法理解的缩写，例如 `async`、`testCacheRateLimiter`。
- 包含产品、模块、页面、服务、客户端、环境、HTTP 方法或路径前后缀，且这些信息不属于业务场景。
- 包含迁移来源、调试过程、问题排查说明或修改原因，例如“因为后台日志报错去掉了某用例”。
- 名称动作与绑定 API/步骤不同，例如名称写“开通”，实际执行“修改”；名称写“下载协商文件”，实际执行“查询付款记录”。
- 名称结果与断言或描述相反，例如名称写“成功”，实际保留为未通过；名称写“校验不通过”，断言要求通过。
- 明显错别字、词语重复或缩写错误，例如 `orc` 应为 `OCR`、`订单订单`、`反馈反馈`。
- 重复写同一个 Case 编号，或尾部只有“原始文件”等无区分度占位词。
- `相关接口`、`的接口`等模糊冗余词；完整详情能确定业务动作时改为具体名称。
- 不自然的占位英文可以转换为稳定中文，例如 `negative case` -> `负向场景`。

### 通常不要修改

- 仅仅缺少测试场景。
- 仅仅想在中文和英文之间增加空格。
- 仅调整大小写、标点、连字符或分隔符，且不改善语义。
- 仅因为名称包含英文参数、枚举、文件名或测试编号。
- 同名资产位于不同项目产品或模块，且上下文足以区分。
- `临时`、`废弃`等词准确表达资产当前用途，并非随手备注；这类资产可另列为治理建议，不要只靠改名掩盖生命周期问题。

不要为了凑满批次数量强行修改。高置信问题不足一批时，按实际数量提交。

## Case 分类字段

Case 使用“测试层级、验证类型、执行场景”三个互相独立的维度。只接受本节列出的现行值；不在列表中的值视为无效，不保留、不生成、不写入。

### 测试层级

`scenario_layer` 是单选整数，描述 Case 覆盖的技术范围：

| 值 | 文案 | 判定标准 |
|---:|---|---|
| `0` | 接口/组件级 | 单个接口或单个组件，包含其参数、协议、契约等局部能力 |
| `1` | 模块级 | 同一模块内多个接口、组件协作 |
| `2` | 端到端 | 跨多个模块验证完整业务链路 |

展示名称不插空格，值仍为0/1/2；按业务覆盖范围而非步骤数量、工厂或SQL判断，与测试归属独立。名称调整不自动重分类历史Case。

### 验证类型

`scenario_type` 是单选整数，描述 Case 最主要的验证目标：

| 值 | 文案 | 判定标准 |
|---:|---|---|
| `0` | 正常场景 | 标准输入、成功路径和正常业务结果 |
| `1` | 异常场景 | 非法输入、失败响应、异常分支和容错 |
| `2` | 边界场景 | 空值、极值、长度、数量、分页和时间边界 |
| `3` | 权限场景 | 登录、角色、越权、租户及数据权限隔离 |
| `4` | 数据场景 | 数据状态、准确性、一致性和数据变化 |
| `5` | 流程场景 | 审批、多步骤处理、任务流和完整状态流转 |

一条 Case 只选择一个主要验证类型；存在多个独立验证目标时应拆分 Case。

### 执行场景

`scenario_tags` 是字符串数组，可多选，描述 Case 适合在哪类任务或环境中执行：

| 值 | 文案 | 规则 |
|---|---|---|
| `routine_regression` | 回归测试 | 非生产环境常规功能回归 |
| `release_verification` | 发布验证 | 发布前后必须确认的能力 |
| `smoke_verification` | 冒烟验证 | 快速确认关键入口和基本功能可用 |
| `stability_monitoring` | 稳定性监测 | 确认生产服务持续稳定可用；通过高频只读巡检（如每分钟一次）及时发现异常；轻量、无业务副作用；测试平台内强制禁止 SQL 和数据库连接/操作 |
| `data_verification` | 数据校验 | 非生产环境的数据准确性和一致性验证 |
| `effectiveness_test` | 效果评测 | Case 专用；用于 AI、算法、搜索、推荐或生成内容的效果评价；定时任务不可选，规则任务不动态匹配 |
| `production_inspection` | 生产巡检 | 仅生产环境；安全、只读、无业务副作用；测试平台内强制禁止 SQL 和数据库连接/操作 |
| `production_regression` | 生产回归 | 仅生产环境；允许通过正式产品 API 完成可控、可恢复的业务验证；测试平台内强制禁止 SQL 和数据库连接/操作 |
| `temporary_validation` | 临时验证 | 用于临时排查、联调、问题复现或一次性验证的 Case；允许用户手动执行，但定时任务不可选，规则任务不动态匹配 |
| `performance_test` | 性能测试 | 仅供性能测试模块中的性能 Case 使用，用于负载、压力、容量、并发、吞吐量和响应时间等性能指标验证；定时任务不可选，规则任务不动态匹配 |

稳定性监测、生产巡检、生产回归的测试平台资产全部禁止前置 SQL、后置 SQL、SQL 断言、SQL 公共变量、生产数据库查询或写入、生产数据库连接配置、数据工厂准备/清理，以及自定义函数通过平台访问生产数据库。测试平台内即使是 `SELECT` 也不允许。本地电脑已有合法、可用的生产连接时，可以在平台外执行与当前任务直接相关的只读 `SELECT` 诊断；严禁增删改、DDL、权限变更及其他写操作，也不得把本地连接、凭据或 SQL 写回测试平台。

产品全量和模块全量任务按执行场景任意交集匹配；但 Case 只要包含 `effectiveness_test`、`temporary_validation` 或 `performance_test`，无论同时还有什么场景，都必须从规则任务动态匹配结果中排除。

`effectiveness_test` 只用于效果评测资产，由用户在效果评测流程中按需执行和分析，不属于自动化定时回归任务。

`temporary_validation` 只表示资产当前用于临时验证，不作为稳定回归资产的长期分类。临时验证完成并确认 Case 可持续复用后，应移除该场景，再根据真实用途设置回归测试、发布验证、冒烟验证等正式执行场景。

`performance_test` 不用于普通 API、UI、Pytest 或功能 Case 的接口耗时检查，也不能仅因 Case 配置了并发或响应时间断言而设置。只有归属于性能测试模块、按性能模型执行并产出性能指标的 Case 才能使用该场景。

## 结构性审计

所有模式均可只读检查以下问题：

- API Info 是否在同一项目产品、客户端、HTTP 方法和规范化 URL 下重复。
- API Case 名称、描述、case flow 与绑定 API/步骤是否一致。
- 是否存在长期停用、废弃、历史定位或仅用于一次性清理的资产。
- 是否存在空描述、含糊名称、错误归属或大量同名资产，导致搜索困难。
- API Case 的测试层级、验证类型、执行场景是否与真实接口和完整执行链路一致。
- 生产定时任务的项目产品、模块、环境、负责人、状态、通知策略和绑定 Case 是否一致。
- 同一 Case 是否被重复或错误绑定到稳定性监测、生产巡检、生产回归、临时验证等互斥用途。

结构问题与名称问题分开报告。不得通过改名掩盖重复绑定、错误步骤或生命周期问题；也不得未经授权合并或删除。

## 生产执行场景规则

按 Case 完整执行树判断标签，不得只根据名称、HTTP 方法或单个步骤判断。

- `stability_monitoring`：目的是确认生产服务持续稳定可用，及时发现服务不可用或关键功能异常；通过高频只读巡检实现，例如每分钟检查一次关键功能。具体频率由定时任务配置，不由标签自动设置。Case 必须轻量、可连续重复执行、负载有界且无业务副作用，断言须验证服务或关键功能实际可用，不仅检查请求已发出；测试平台资产内必须无 SQL、数据库连接或数据库操作。与常规周期的 `production_inspection` 按实际执行用途区分，不把所有只读 Case 默认标为稳定性监测。
- `production_inspection`：只允许 GET，或明确不提交/修改数据的只读 POST。不得包含正式 API 写操作、通知、文件生成或异步任务创建。
- `production_regression`：可覆盖正式 API 写操作，但写操作必须幂等、隔离，或能通过正式产品 API 可靠恢复原状态。
- 上述三个生产执行场景全部强制禁止 SQL、直接数据库访问和数据工厂操作。
- 回归测试、冒烟验证以及异常场景、边界场景等分类不能替代生产执行场景。
- 同一 Case 可有多个不冲突的执行场景；生产执行场景必须与任务用途、执行环境和真实副作用一致。

标签审计至少检查：

1. method、URL、API Info 请求体类型和场景实际请求。
2. 全部步骤、前后置、提取器、SQL、数据工厂、文件和自定义函数。
3. 固定生产业务 ID、跨步骤缓存变量和生产存量数据依赖。
4. 写入、状态推进、通知、邀请、催办、导出、文件生成、异步任务和第三方调用。
5. 断言是否验证真实业务语义，而非只验证 HTTP 200。

## 生产安全判定

### 可以保留

- 不存在 ID、空集合、无权限等稳定负向场景，在写入前终止，并断言明确业务码、success=false、错误语义和空数据。
- 使用哨兵值的只读查询，断言成功契约及空列表、分页、布尔值等业务结果。
- 生产写操作有完整的创建/修改/校验/恢复闭环，且失败时也能执行清理。

### 必须修复或移出生产任务

- 正向场景依赖会失效的固定订单、模板、协商、主体、交易方或文件 ID。
- 写操作没有恢复，或仅把删除放在顺序末尾；前序失败会跳过清理时，不算恢复闭环。
- 异步导出、文件生成或任务创建缺少轮询、产物验证和清理。
- 邀请、通知、催办、流程推进、配置修改等会影响真实用户或生产状态。
- 外部 AI、签章、企业信息、OFAC 等调用存在费用、敏感数据、限流或非确定结果，且未证明适合定时执行。
- 请求返回 HTTP 500、FATAL_ALARM、SYSTEM_ALARM、系统错误或空指针；禁止把这些返回写成预期结果来刷绿。
- Case 使用生产 SQL、数据工厂、数据库清理或绕过正式 API 的数据操作。

能修复请求模型、API Info body_type、必填参数或稳定业务断言时，先修复并单 Case 验证；无法证明生产安全时，移除对应生产标签并从生产任务解绑，保留 Case 本身供非生产环境使用。

## 定时任务绑定审计

1. 分页读取完整任务清单和每个任务的完整 Case 绑定，不得只取第一页。
2. 明确任务是生产巡检、生产回归、普通回归还是临时任务；核对项目产品、模块和测试环境。
3. 对规范定义为“全量标签任务”的任务，比较任务绑定集合与对应标签集合：
   - tag_not_bound = 标签集合 - 绑定集合
   - bound_without_tag = 绑定集合 - 标签集合
4. 任务若明确只运行标签子集，不强求集合相等；记录筛选依据，避免擅自扩容。
5. 检查同一 Case 的其他任务绑定。移除标签前确认该标签是否仍被其他合法生产任务使用。
6. 分开输出：应补绑、应解绑、应改标签、需人工确认、任务配置问题。

推荐一致性：

- canonical 稳定性监测任务绑定集合与 `stability_monitoring` 集合双向一致。
- canonical 生产巡检任务绑定集合与 `production_inspection` 集合双向一致。
- canonical 生产回归任务绑定集合与 `production_regression` 集合双向一致。
- Case 从唯一对应的生产任务解绑时，同步移除对应生产标签，避免留下“有标签未绑定”。
- 仅修正错误标签但仍属于其他合法生产任务时，保留其必要标签和绑定。

## Case 退出正式调度

本流程适用于所有环境，用于执行已经明确批准的 Case 退役，或在产品/测试平台修复期间实施临时风险缓解。

退出调度是平台执行状态，不是报告修复失败的处理结论。报告维护流程只能在以下情况下调用本流程：权威证据已经形成“需要删除或取消发布 Case”的结论，或者“需要业务开发修改代码”“需要测试平台修复”的 Case 在责任方修复前需要用户明确授权的临时风险缓解。数据、前置、清理、隔离或普通环境问题仍应继续修复，不得借退出调度规避处理。

执行顺序：

1. 建立 Case 当前发布版本、全部执行场景标签、显式任务绑定和可能命中的动态规则任务基线。
2. 保留 Case、步骤、场景、断言、历史 Revision/Release 和失败报告；不得通过删除覆盖或放宽断言代替下线。
3. 查询 MCP 是否提供真正的取消发布能力。若提供，先调用影响预览，再按工具确认令牌和授权执行；若未提供，不得声称取消发布成功。
4. 在不能取消发布或只需停止自动执行时，移除所有会进入正式调度的执行场景；平台规则允许时设置 `temporary_validation`，明确仅供人工临时执行。
5. 分页查全并预览解绑所有显式定时任务。使用确认令牌执行后重新读取，确保绑定为零。
6. 反查产品全量、模块全量、标签全量及其他动态规则任务，按平台真实匹配规则证明 Case 不再入选；不能只检查显式绑定。
7. 输出原标签、原任务、实际变更、退出原因、恢复测试条件，以及当前仍会选中该 Case 的任务数。

取消发布与退出调度必须分别说明实际情况：

| 当前情况 | 必须说明的含义 |
|---|---|
| 当前无正式发布版本 | 已真正取消发布，当前不存在正式发布版本 |
| 已发布但已退出调度 | 历史发布版本保留，但已移除全部正式执行标签和任务绑定 |
| 已发布且仍参与调度 | 当前仍可能进入正式任务 |
| 仅限临时执行 | 只允许人工临时执行，不参与显式或动态定时任务 |

MCP 没有取消发布能力时，将缺少“预览取消发布影响”和“执行取消发布”能力作为平台能力缺口报告；不得用临时验证标签冒充已取消发布。如果某类动态规则无法反查或证明不匹配，退出调度尚未验收完成，应报告精确能力缺口。

## 定时任务清理流程

“清理定时任务”按以下层级执行，不得把不同动作合并成一次隐式操作：

### 1. 清理错误绑定

1. 形成待解绑 Case 清单和逐条理由。
2. 先更新 Case 标签，使标签表达真实用途；保留普通回归等仍有效标签。
3. 调用解绑影响预览，核对任务 ID、实际将解绑、跳过和缺失的 Case。
4. 使用预览 token 和确认文案执行解绑。
5. 重新分页读取任务绑定与标签集合，确认双向差集符合预期。

### 2. 清理缺失绑定

仅当任务定义明确要求覆盖完整标签集合时补绑。先检查 Case 生产安全和其他任务关系，再预览、确认、绑定并复核；不得仅因 Case 有生产标签就盲目加入任意任务。

### 3. 清理重复、空或过期任务

- 重复任务：比较任务用途、项目产品、模块、环境、策略和完整绑定；证据不足时只报告。
- 空任务：先确认是清理结果还是配置异常。不得因绑定为空自动停用或删除。
- 过期/临时任务：检查名称、状态、最近报告和业务用途；用户明确授权后再停用或删除。
- 环境错误、负责人失效、通知配置不合理：单独列为任务配置整改，不与 Case 解绑混合执行。
- 停用和删除必须分别使用对应 MCP 的影响预览与二次确认。MCP 无能力时停止并报告。

### 4. 报告与执行验收

- 报告是历史快照。解绑后直接重试旧报告可能重新执行已移出的不安全 Case。
- 先预览旧报告重试影响；若仍包含旧 Case 快照，不得执行。
- 触发整改后的当前定时任务生成新报告，且生产并发使用保守值。
- 修复后的 Case 先单 Case/小批验证，再执行完整任务。
- 最终至少确认：报告通过、失败 0、警告 0、等待 0、执行中 0；分别报告 Case 数和场景数。
- 新报告仍失败时，按请求构造、业务码、响应结构、固定数据、权限、外部依赖和副作用重新分类，不能弱化关键断言。

### 历史失败记录的排除统计

取消发布或解绑 Case 不会自动排除它的历史失败。只有用户明确授权确定项目产品和历史报告范围的排除/恢复操作时，才通过 `update_test_report_case_diagnosis` 更新报告执行项；不能用 Case ID 代替 `test_suite_detail_id`，也不能绕过 MCP 改数据库。

- `is_excluded=true`：开启排除，整条执行项退出有效总数、失败和成功率统计；已排除数量与原始报告、失败结果、原因说明仍保留。
- `is_excluded=false`：关闭排除，恢复参与统计；原失败仍是失败，不表示修复或重试通过。
- 不传或 `null`：不改变开关，只记录原因和说明；页面开关只有开启/关闭两项。

先从 `get_test_report_schema` 获取原因类型并核实工具参数，再按真实执行项逐条传原因、说明和已授权的开关值，操作后读回验证。普通修复、取消发布或全量清理授权不自动扩展为历史排除授权；明确排除的 Case/报告之外不扩围，不因名称、灰度失败或未取消发布就自行处理。部署工具缺少参数时报告需要更新服务，不改库兜底；已有通知需另行授权重发。

## 生产治理修改顺序

1. 建立基线：任务、标签、绑定、报告、Case 和场景总数。
2. 分页扫描并保存已审计 ID，按名称、标签、生产安全和任务配置分类。
3. 对疑似问题读取完整 Case 树；必要时以 controller/service/DTO 或正式文档确认契约。
4. 优先修复无副作用的 API Info 请求模型、Case 参数和业务断言。
5. 单 Case 或小批在目标环境验证，记录报告 ID。
6. 对无法安全修复的 Case，先纠正标签，再预览并解绑。
7. 复核标签集合与绑定集合。
8. 处理空、重复、过期或错误配置的任务；停用/删除单独确认。
9. 触发整改后的任务生成新报告并验收。
10. 输出所有修改 ID、未处理风险、报告 ID 和最终统计。

非生产环境的退出调度同样执行“基线、修复优先、影响预览、标签变更、显式解绑、动态任务反查、结果复核”的闭环，但不套用生产专属的 SQL、数据工厂和业务副作用限制；仍须遵守目标环境自身的安全与清理规则。

## 提议与确认

名称清洗默认先提议、后修改：

1. 只列需要变更的资产。
2. 默认每组最多 50 个；用户指定其他数量时服从用户。
3. 使用固定格式：`ID | 当前名称 | 建议名称 | 处理理由`。
4. 理由写具体证据，例如“实际绑定接口为修改开放平台”，不要只写“命名不规范”。
5. 同一组未确认前不得更新。
6. 用户确认后，只更新该组已确认的 ID 和名称。
7. 用户明确授权自动连续处理时，可跳过逐组确认，但仍需保存修改清单和失败项。

建议名称应做最小必要修改。能删掉错误前缀解决时，不额外改写用户原有场景表达。

执行场景与调度治理使用独立清单：

- Case 标签：ID | 当前标签 | 建议标签 | 调度/环境安全结论 | 证据。
- 任务绑定：任务 ID | Case ID | 当前关系 | 建议动作 | 影响理由。
- 任务配置：任务 ID | 当前配置 | 问题 | 建议动作 | 风险。
- 任务生命周期：任务 ID | 重复/空/过期证据 | 建议停用或删除 | 是否已单独授权。

风险待办修复使用独立清单：

- `待办 ID | 待办类型 | 项目/产品 | 底层资产 | 当前异常 | 修复动作 | 关闭方式 | 验证结果`。
- “关闭方式”只能写“系统自动检测”或“允许人工确认”，不能把点击“已处理”描述为异常已经修复。
- 同一待办涉及多条数据工厂清理明细时，逐项记录失败原因、修复和残留校验，不用汇总成功掩盖部分失败。

用户明确授权“自动连续清理全部”时，可连续处理高置信项，但每次危险写操作仍必须调用 MCP 影响预览、核对实际影响并传回预览 token；需人工确认项不得混入。

## 名称修改与验证

1. 调用对应 MCP 的名称更新工具；API Info 和 API Case 使用各自的更新能力。
2. 分小批执行，收集每个 ID 的成功或失败结果。
3. 失败项不得假报成功；记录错误并仅重试可安全重试的请求。
4. 更新后重新查询修改项或抽样核对，确认名称已落库且未改变其他字段。
5. 报告本组总数、成功数、失败 ID 和失败原因。
6. 继续扫描时排除已成功处理的 ID。

名称清洗不要求执行 API Case；只有用户同时要求验证用例行为时，才按 API Case Builder 的环境和执行规则运行。

## 输出要求

全量审计完成时至少说明：

- 扫描的 API Info、API Case、测试层级、验证类型、执行场景、定时任务和绑定总数及项目产品范围。
- 已处理数量、剩余高置信问题数量和需人工确认数量。
- @人名/@codex、名实不符、代码化名称、调试备注、错别字/重复词等关键类别是否仍有残留。
- API Info 名称和 API Case 名称分别修改多少条、失败多少条。
- 稳定性监测、生产巡检与生产回归场景分别新增、移除、保留多少条。
- 每个 canonical 生产任务的绑定数、标签数、tag_not_bound 和 bound_without_tag。
- 补绑、解绑、停用、删除、配置整改分别处理多少项；空任务和重复任务是否仍有残留。
- 单 Case/小批验证报告和最终新报告 ID，以及成功、失败、警告、等待、执行中场景数。
- 本轮哪些操作只审计未修改，以及仍存在的结构性或生产风险。
- 风险待办修复时，补充待办 ID、底层资产 ID、修复前后状态、自动关闭/人工确认结果，以及仍未关闭的原因。

不要把纯格式美化包装成资产治理成果。

# MangoServer AGENTS.md

MangoServer 是芒果测试平台 Django 后端。本文件约定后端开发规范，重点覆盖 Django/DRF、数据工厂、MCP 和迁移边界。

## 基本原则

1. 修改前先读已有模型、视图、service、enum，不要凭接口名猜逻辑。
2. 优先沿用现有目录风格：`models.py`、`views/`、`service/`、`urls.py`、`enums/`。
3. 业务逻辑尽量放在 `service/`，ViewSet 只负责入参、权限、序列化和响应。
4. 返回结构使用项目已有 `ResponseData.success/error` 风格。
5. 业务异常必须使用对应 app 的异常类抛出，例如 API 使用 `ApiError`，UI 使用 `UiError`，Pytest 使用 `PytestError`，通用工具使用 `ToolsError`；新增 app 异常必须继承 `MangoServerError`，确保 `error_response` 能直接返回业务文案。
6. 通过 `ResponseData.fail` 返回给前端的错误响应文案，必须先定义在 `src/common/tools/view/response_msg.py`，代码中引用常量，不直接写散落字符串。
7. 通过 `ToolsError` 或异常抛出的业务错误文案，必须先定义在 `src/common/exceptions/error_msg.py`，代码中引用常量，不直接写散落字符串。
8. 不允许用 `serializers.ValidationError`、`ValueError`、裸 `Exception` 等承载可预期业务错误文案；DRF 字段校验只用于字段格式错误，业务规则冲突必须转换为对应 app 异常。
9. 不要修改无关模块，不要顺手重构老代码。
10. 遇到用户已有改动，先兼容，不要回滚。

## 命令边界

11. 后端目录是 `MangoServer/`。
12. 常用启动命令：`python manage.py runserver --env=dev 0.0.0.0:8000`；多服务本地启动使用 `sh scripts/start_dev_services.sh`。
13. 本地虚拟环境通常是 `.venv/`，Windows 下可用 `.\.venv\Scripts\python.exe`。
14. 开发过程中不允许执行生成迁移脚本命令。
15. 开发过程中不允许执行迁移命令。
16. 迁移脚本由用户自己生成和执行。
17. 如模型发生变化，只说明需要迁移，不要运行 `makemigrations` 或 `migrate`。

## 模型与迁移

17. 修改模型前先确认历史迁移和线上表结构。
18. 新增字段要考虑默认值、历史数据、空值和序列化兼容。
19. 删除字段时同步检查 serializer、service、MCP、前端返回字段。
20. `JSONField` 必须有明确结构约定，不能随意存任意 JSON。
21. JSON 配置建议配合 Pydantic、校验函数或枚举常量定义结构。
22. 外键删除策略优先参考相邻模型，核心数据通常使用 `PROTECT`。
23. 表名沿用 `db_table` 显式命名风格。

## 序列化与查询

24. 列表接口注意 `select_related`、`prefetch_related`，避免 N+1。
25. 详情接口如果返回嵌套对象，应统一 serializer 输出。
26. 搜索字段要和前端查询组件一致。
27. 每个数据库模型原则上对应一个独立 `views/<model_or_table>.py` 文件，serializer、CRUD 和该模型强相关 ViewSet 放在同一个文件内。
28. 参考 API Case 的 serializer 分层：无 `C` serializer 用于写入和轻量基础字段，`C` serializer 用于需要嵌套对象的读取展示。
29. 表相关的自定义接口必须放在该表对应的 ViewSet 下，例如 `ApiCaseViews` 这类写法；ViewSet 必须显式声明 `model` 和 `serializer_class`。
30. 如果一个接口最终创建、查询、更新或展示某张表的数据，应归到那张表的 view 文件里，不新建游离的聚合 views 文件承载业务方法。
31. 聚合文件只能作为兼容导出索引，不继续堆业务类；新增/调整接口时优先从真实模型 view 文件导入。
32. 列表接口不要随意增加冗余 `*_name`、`*_id` 展示字段；优先返回真实外键字段或必要的嵌套对象。
33. 当列表项包含父对象且只需父对象基础字段时，父对象使用无 `C` serializer，避免父对象内部的项目产品、模块、用户等再次展开成大对象。
34. 项目产品、模块字段如果页面需要展示层级路径，可在当前列表项上返回必要嵌套对象；不要让嵌套父对象继续展开无关外键。
35. 大列表接口谨慎返回重字段、大 JSON、长文本、上下文资料正文和多层嵌套对象。
36. 按模块过滤时考虑跨模块依赖，不能阻断合法关联实体。

## AI 与功能测试约定

37. `functional_test` 只负责需求、用例、资料、绑定、统计和落库；AI、Skill、MCP、Agent、上下文历史、任务阶段和对话展示统一放在 `ai` app。
38. 功能测试用例由 AI 生成时，不要求 AI 输出 `project_product_id`、`module_id`，后端落库必须使用当前需求的项目产品和模块。
39. 用户手动新增或编辑功能测试用例时，可以单独修改用例自己的项目产品和模块；读取、筛选、模块导航和 API 自动化生成以用例自身字段为准。
40. 功能测试用例编号统一使用 `FT-{四位序号}`，AI 生成和后端兜底都遵守同一规则。
41. 生成 API 自动化时，Skill 决定执行规范，MCP 提供真实工具能力；后端只做基础结果校验和业务落库校验。

## 枚举规范

42. 枚举统一放在 `src/common/enums/` 或模块既有枚举位置。
43. 枚举值变更要同步前端枚举接口、展示文案和测试。
44. Service 中尽量引用枚举，不要散落数字魔法值。
45. 数据工厂执行状态语义：`0 失败，1 通过，2 待开始，3 进行中`。

## 数据工厂核心约定

46. 工厂实体只描述单表字段规则，不直接绑定具体业务场景。
47. 场景模板是业务入口，可以包含一个主模板和多个关联模板。
48. 后端模型可继续叫 `DataFactoryTemplate`，产品语义是“场景模板”。
49. `DataFactoryTemplateItem` 表示场景里的关联模板。
50. 关联模板默认启用，不再设计 `enabled` 字段。
51. 关联模板清理策略继承场景模板，不再单独维护 `cleanup_strategy`。
52. 关联模板顺序使用 `sort`，后端按 `sort,id` 执行。
53. 执行场景模板时，主模板和关联模板共享同一个运行上下文。
54. 子模板依赖主模板时，应复用上下文，不应重复创建主表。
55. 工厂实体字段规则中的“依赖实体字段”只保存依赖实体和字段。
56. 状态/场景/API 覆盖层才选择具体依赖模板。
57. 依赖字段执行仍以 `template_id` 创建依赖数据。
58. 多表场景必须通过关联模板表达，不要让主表反向自动创建所有子表。

## MCP 规范

59. MCP 工具描述要面向调用者，不要只写后端字段名。
60. 创建/更新场景模板时要支持 `items`。
61. MCP 返回场景模板详情要包含主模板字段和关联模板列表。
62. MCP 应明确工厂实体是单表规则，场景模板是完整业务对象。
63. MCP 入参示例必须和后端校验结构一致。
64. 前端能力变更时，MCP 文案和参数也要同步。
65. 拆分 views 后，MCP tools/resource/service 引用 serializer 时优先从对应模型 view 文件导入，兼容聚合文件只作为过渡入口。
66. 功能测试 MCP 写操作必须复用现有 serializer/service 规则，不能绕过功能测试用例必填、枚举、绑定和统计刷新校验。
67. AI 查询 MCP 只提供任务、阶段、工具调用、上下文、Skill、MCP 服务和工具快照等只读能力，不提供绕过页面的 AI 配置写入。
68. 新增 MCP 写操作工具时，必须走 `src/services/mcp_server/app.py` 统一演示环境写操作校验；工具名优先使用既有写操作前缀：`create_`、`add_`、`copy_`、`upload_`、`bind_`、`batch_`、`batch_generate_`、`execute_`、`debug_run_`、`update_`、`set_`、`sort_`、`refresh_`、`auto_generate_`、`delete_`、`cleanup_`、`clear_`。
69. 如果新增 MCP 工具会写库、改配置、上传文件、绑定关系、清理数据或真实执行落库，但工具名无法使用上述前缀，必须同步更新 `_mcp_tool_write_operation`；如果是查询、预览、分析或允许演示环境执行的测试任务，确认不需要加入写操作分类。

## API 与兼容

70. 已存在接口路径尽量保持兼容，例如 `/data-factory/template`。
71. 产品文案可从“状态模板”改为“场景模板”，内部路径可暂不改。
72. 接口新增字段要兼容老客户端缺省值。
73. 接口移除字段前可在 serializer 入参处忽略旧字段，避免老请求失败。
74. 不要让前端必须一次性加载所有实体、模板、字段。
75. 大数据量场景应按模块、实体懒加载。

## 测试与验证

76. 数据工厂改动至少跑相关 compile/test 或最小测试集。
77. 场景模板测试要覆盖无关联模板、有关联模板、子模板缺字段。
78. 跨模块依赖要作为重要验证场景。
79. 复用上下文要验证不会重复创建主表。
80. 修改枚举后要验证前端展示和后端状态流转。

## 代码风格

81. Python 代码保持项目既有格式，不引入不必要的新框架。
82. 注释只写复杂业务原因，不写显而易见的代码翻译。
83. 查询条件、JSON key、枚举 key 尽量集中定义。
84. Service 方法要命名清楚，避免一个方法同时做预览、执行、清理。
85. 事务边界要明确，执行造数和执行记录更新需考虑失败状态。
86. 记录日志时避免输出敏感 token、Authorization、密码。
87. 最终交付时说明改了哪些文件、是否需要迁移、跑了哪些验证。

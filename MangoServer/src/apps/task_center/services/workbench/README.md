# 风险待办开发清单

## 测试执行平台受阻

- 复用 `WorkbenchTodo`，来源为测试报告，事件为“测试执行平台受阻”；报告和明细使用独立结果值 `6`，旧版失败记录中的 `infrastructure_blocked` 标记按受阻读取。
- 按项目产品、执行环境、任务聚合；手动执行按报告聚合。多个 Case 和连续调度只更新同一待办，首次或恢复后再次发生才通知产品负责人；无产品负责人时兜底任务负责人或手动执行人。
- 受阻且无业务失败时不发送常规报告通知；同时存在业务失败时仍按任务设置发送业务失败报告。任务组同样遵守。
- 受阻可手动重试，不再要求逐条填写排查记录；不确定原请求是否执行时必须确认重复写入风险。已知清理未完成仍需先处理，确认只针对当前重试，不永久解除保护。
- 待办快照结构见 `ReportInfrastructureTodoDetails`，不复制请求响应。有效的同范围完整执行恢复后自动关闭；人工核验关闭须保存处理说明，不修改报告或 Case 结论。
- 实时同步为事务提交后的旁路操作，异常不得回滚报告；非授权待办定时对账补偿漏写和通知失败。

本文档与风险待办业务 Service 放在同一目录，用于开发接口、补充事件枚举和验收自动关闭逻辑。

## 当前实现范围

当前代码已实现 4 种来源、6 种事件：前端授权、服务授权、数据工厂模型和数据工厂执行记录；对应授权即将到期、授权已过期、授权刷新失败、数据模型无效、数据模型结构待确认、数据工厂清理失败。

当前提供待办查询、系统自动关闭能力，以及“数据模型结构待确认”和“数据工厂清理失败”的人工“已处理”能力。其他待办仍只提供“去处理”入口。模型使用
`handled_by`、`handled_at` 和 `handle_note` 记录人工或系统处理结果。

表格中的“是否允许直接处理成功”是产品规则，不表示该按钮已经开发完成；是否已经落地以最后一列“是否已完成”为准。

## 待办同步架构

风险待办采用“业务事件实时写入 + 定时任务兜底扫描”的混合方式，不是单纯依赖页面查询或全量定时扫描。

| 待办类型         | 业务事件实时写入              | 定时扫描职责                   |
|--------------|-----------------------|--------------------------|
| 前端、服务授权刷新失败  | 授权刷新失败后立即生成待办         | 补偿漏写，并在刷新成功、配置停用或删除后自动关闭 |
| 授权即将到期、授权已过期 | 不单独实时生成               | 扫描授权有效期并生成、更新或关闭待办       |
| 数据模型无效、结构待确认 | 数据模型结构扫描产生结论时立即生成     | 检查模型恢复、停用或删除，并自动关闭已解除风险  |
| 数据工厂清理失败     | 清理事务提交后立即生成；清理成功后立即关闭 | 补偿历史失败，并关闭清理成功或执行记录删除的待办 |

“授权风险代办同步”每 3 分钟统一扫描前端与服务授权，到期风险以待办为唯一记录，首次生成时通知项目产品负责人；配置了通知组的到期通知模式还会由同一流程通知该组。其他首页风险待办每
5 分钟同步一次。用户打开或刷新风险待办时，查询接口也会先同步一次当前状态，再返回权限范围内的数据。

实时写入属于旁路提醒：业务模块只调用统一的 `WorkbenchTodoService`
，待办写入异常不能改变授权刷新、结构扫描或数据清理的原业务结果。定时扫描负责最终一致性，用于处理服务异常、历史数据、漏写事件和风险恢复后的自动关闭。

## 目标处理约束

“是否允许直接处理成功”表示是否在待办组件中显示“已处理”按钮。用户点击并确认后，接口直接把当前待办标记为已处理。

该按钮只适用于需要人工判断，或用户已经在线下完成处理但系统无法立即验证的待办。授权、任务执行、连接状态等可以由系统客观检测的风险不允许手动关闭，避免用户为了清空待办而隐藏真实问题。

所有待办统一遵循以下规则：

1. 默认不提供“已处理”按钮，只有清单中明确标记为“是”的事件类型允许调用人工处理接口。
2. 人工处理只允许逐条操作，不提供批量处理；必须记录 `handled_by` 和 `handled_at`，处理说明 `handle_note` 可选。
3. 对于不允许人工处理的待办，真实业务动作成功后重新检测状态，再由系统自动关闭。
4. 人工处理后的同一风险不能被定时扫描立即重新打开；只有事件键或结构差异指纹发生变化时才重新打开。数据模型结构待确认使用结构差异指纹区分原风险和新风险。
5. 同一风险使用稳定的 `event_key` 去重。
6. 风险解除后自动关闭；同一风险再次出现时自动重新打开。
7. 超级管理员查看全部，普通用户按项目产品权限查看。
8. 负责人优先取业务对象负责人，其次取项目产品下测试对象负责人。
9. 单次、瞬时且无需人工操作的失败只进入消息中心，不生成待办。

## 数据工厂清理失败明细

| 失败场景        | 待办需要展示的内容                                       |
|-------------|-------------------------------------------------|
| 清理 SQL 执行失败 | 执行编号、数据源、环境、表名、明细别名、错误摘要和失败时间                   |
| 部分数据清理失败    | 清理明细总数、成功数、失败数和跳过数                              |
| 清理事务回滚      | 回滚错误摘要和涉及的场景模板、表名或明细别名                          |
| 数据源连接失败     | 数据源、环境和连接错误摘要                                   |
| 清理任务超时      | 清理过程抛出超时异常并落为失败时，展示超时错误摘要和失败时间；当前不单独计算执行时长或超时阈值 |
| 重试仍然失败      | 每次重试失败按最新清理时间生成新风险，展示最近一次错误；当前不维护累计重试次数         |

数据工厂清理失败使用“执行记录 + 本次清理时间”组成事件键。同一次失败被人工确认后不会被定时扫描重新打开；后续重试再次失败会生成新的风险。下一次清理成功或执行记录删除后，系统自动关闭待办。

清理失败邮件不再随待办立即发送。待办及失败审计仍实时保留，首次创建待办后缓冲 5 分钟，由既有每 5 分钟运行的待办巡检复核发送（通常在失败后 5～10 分钟，调度延迟另计）。发送前重新读取执行当前清理状态及失败事件键；已恢复、正在重试、已处理或已被新事件替代的旧失败不发送。持续失败才通知，同一事件成功发送后不重复；邮件发送失败保留后续重试机会。通知状态保存在既有 `details.cleanup_notification_sent_at`（ISO 时间字符串），更新来源快照时保留该标记，不新增表或字段。

恢复巡检排除已完成清理的执行；对遗留顶层失败或进行中记录，先在执行锁内核对所有明细及 SQL/ES 证明，证据完整才收敛清理状态，不改业务结果、不重新删除资源。报告明细删除或批次变化不能覆盖已核验的资源成功；真正未完成或证据不足的资源继续保留恢复责任。待办创建和延迟发送前复用同一完成判定（包含补偿授权匹配及未知请求结算），全部已核验时不生成/发送清理失败告警，旧待办由巡检关闭。不以“明细状态全成功”替代资源证明；执行级异常但无失败明细时明确提示缺少完整验证及执行错误，不发送“失败0项、成功140项”的矛盾摘要。无需新增表或字段。

本规则只延迟邮件，不延迟待办、不修改 Case 结果，也不自动重跑业务请求。清理仍使用原有精确目标、归属/版本核验和完整观察窗口；超过缓冲期尚未恢复的失败不能静默隐藏。邮件已发送后无法撤回，发送后发生的恢复仍保留审计记录。SMTP 与数据库之间不具备分布式事务，进程在邮件发送后、发送标记落库前中断仍可能重复通知。

## 新增待办类型检查项

新增一个待办类型时，至少同步检查：

- `WorkbenchTodoSourceTypeEnum` 和 `WorkbenchTodoEventTypeEnum`。
- 稳定的事件去重键及重新打开规则。
- 生成条件、自动关闭条件和误关闭保护。
- 项目产品权限过滤与负责人来源。
- 列表序列化中的标题、摘要、环境和详情字段。
- “去处理”路由；若允许人工处理，还需增加带权限校验的“已处理”接口与按钮。
- 定时任务扫描入口和实时业务事件入口。
- Service、接口权限和自动关闭测试。

## 摘要

自动化测试真正变难，通常不是因为第一条脚本写不出来，而是环境、数据、任务、报告和多人协作逐渐失去统一边界。本文以开源项目芒果测试平台为例，介绍如何把 API、UI、Pytest、测试数据工厂、任务调度、执行器、测试报告和 MCP 串成一条可追踪链路，以及平台化建设的适用范围和成本。

## 正文

很多团队的自动化都从一组脚本开始。

脚本数量少时，代码仓库加 CI 已经足够。随着产品、测试环境和参与者增加，问题往往从“怎么写断言”变成下面这些：

- 环境地址、账号和请求头在多处重复维护；
- 用例依赖的数据需要人工准备，执行后还要手工清理；
- API、UI 和 Pytest 资产分散，执行入口和报告格式不统一；
- 定时任务失败后，只能在日志、截图和请求响应之间来回寻找原因；
- 新成员很难快速理解已有资产、依赖关系和历史结果；
- AI 能生成代码，却不知道团队已经有哪些用例和最近为什么失败。

芒果测试平台想解决的，是这些脚本进入团队协作阶段之后的工程问题。

### 一、先统一资产，而不是先统一技术栈

平台没有要求所有测试都改造成同一种形态。

API 和 UI 的常规流程可以在页面中配置，已有 Pytest 项目则继续保留代码表达能力，再接入统一的任务、执行器和报告体系。项目、产品、模块和测试环境成为共同的组织维度，解决的是资产归属与可发现性，而不是强行抹平不同测试类型的差异。

这也意味着“低代码”不是“永远不用写代码”。复杂协议、自定义生成规则和特殊运行环境仍然需要扩展；平台负责把这些扩展放进有边界、可追踪的执行链路。

> 配图建议 1：最新版首页或测试资产导航。不得出现真实人员、项目名、业务域名和通知内容。

### 二、把测试数据当成一等资产

编辑、删除、审批、状态流转等自动化场景，往往要求执行前已经存在一条满足特定条件的数据。如果每条用例各写一段前置 SQL，会很快遇到复制、环境硬编码、表结构耦合和清理遗漏。

数据工厂将这件事拆成一条可复用链路：

```text
逻辑数据源
  → 测试环境绑定
  → 业务实体与字段生成规则
  → 表达业务状态的模板
  → 执行前造数
  → 用例引用生成结果
  → 执行后按策略清理
```

用例只描述“需要什么状态的数据”，实际数据库连接由环境解析。生成结果可以写入变量缓存，供后续请求和断言引用；执行记录则保留创建和清理状态，便于审计与排查。

> 配图建议 2：状态模板或执行记录。表名、字段名和示例数据统一使用 `example`、`demo_user` 等虚构内容。

### 三、执行服务与 Web 请求解耦

平台将配置、调度和执行拆成不同职责：

```text
Web 控制台
  → Core API：配置、权限与状态查询
  → Scheduler：定时触发与任务分发
  → API Worker：执行接口自动化任务
  → Actuator：运行 UI、Pytest 等环境相关任务
  → MCP Service：向 AI 客户端提供受控工具
```

这样做的目的不是增加服务数量，而是避免耗时任务占用 Web 请求进程，并让 API Worker 或执行器能够按需要独立部署。每次执行都应能够回答：谁触发、在哪个环境运行、当前状态是什么、失败发生在哪一步、留下了哪些诊断信息。

### 四、报告是排查入口，不只是通过率

只有“通过 / 失败”的结果很难支持工程排查。平台会围绕执行链路保存步骤状态、请求响应、变量提取、断言、错误信息、日志和 UI 失败截图。

报告的价值是把一次失败还原成可以继续行动的信息：

- 请求是否按预期构造；
- 认证与环境配置是否正确；
- 数据准备是否成功；
- 断言是否合理；
- 被测服务是否返回了业务异常；
- UI 元素是否发生变化。

> 配图建议 3：一条完全脱敏的失败报告，保留结构和状态，不保留 Token、Cookie、真实 URL、SQL 与用户信息。

### 五、MCP 让 AI 连接真实测试资产

如果模型只能读取一段临时提示词，它生成的脚本很容易成为新的孤岛。平台通过 MCP 提供结构化工具，让支持 MCP 的 AI 助手在权限范围内查询项目上下文、测试资产、任务和报告。

一个更实用的 AI 任务是：

```text
查询演示项目最近一次失败的 API 自动化报告，汇总失败步骤，
并判断问题更可能来自请求构造、断言、测试数据还是被测服务。
```

这里的重点不是让 AI 绕过平台直接访问数据库，而是让它沿用已有权限、工具和执行记录。创建、修改、执行、清理等写操作仍需要明确的风险边界和审计。

### 六、什么时候值得平台化

以下情况更适合引入芒果测试平台：

- 已有一定数量的 API、UI 或 Pytest 资产；
- 多人协作，并且需要统一管理环境、任务和报告；
- 测试数据准备复杂，重复 SQL 和人工造数较多；
- 需要定时回归、远程执行或历史结果追踪；
- 有私有部署和二次开发需求；
- 希望让 AI 理解并使用真实测试资产。

如果只是临时调试几个接口，轻量接口工具更直接；如果只有少量稳定脚本，Pytest 加 CI 也可能是更低成本的选择。平台化带来治理能力，也意味着部署、升级和权限管理成本。

### 七、欢迎用真实问题验证项目

芒果测试平台仍在持续迭代。比单纯的功能数量更重要的是：部署是否顺畅、资产迁移是否可控、数据工厂能否覆盖真实业务状态、失败报告能否缩短排查时间。

欢迎体验后通过 Issue 提交具体问题。建议附上版本、部署方式、复现步骤和脱敏日志，不要提交密码、Token、Authorization、真实业务域名或生产数据。

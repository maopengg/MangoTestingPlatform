## 为什么要做一个测试平台

很多团队的自动化都是从个人脚本开始的。

刚开始时，脚本能够执行、能够断言、能够生成报告，已经解决了主要问题。但随着项目、环境和用例数量增加，新的问题会逐渐出现：

- API、UI 和 Pytest 资产分散在不同仓库或个人电脑中。
- 环境地址、账号、请求头和数据库配置被重复维护。
- 用例执行前需要手工准备数据，执行后还要人工清理。
- 定时任务失败后，只知道“失败了”，不知道问题发生在哪个环节。
- 报告、日志、截图和请求响应分散，排查链路比较长。
- AI 可以生成代码，却不了解团队已有的测试资产和执行结果。

所以芒果测试平台想解决的并不只是“如何执行一个自动化脚本”，而是如何让自动化资产能够被团队持续维护、执行、追踪和复用。

## 平台目前包含什么

### API 自动化

平台支持接口定义、请求参数、请求头、请求体、文件参数、场景参数、执行步骤、响应提取和多种断言方式。

用例可以配置前置与后置操作，也可以通过变量引用环境配置、缓存结果和数据工厂输出。执行后会保留请求、响应、断言和失败信息，便于定位问题。

### UI 自动化

UI 自动化按照页面、元素、步骤和用例组织资产，支持 Web、Android 和 PC 桌面场景。任务可以交给独立执行器运行，并回传日志、状态和失败截图。

### Pytest 接入

对于已经使用 Pytest 的团队，平台提供测试文件与用例管理、执行调度和结果收集能力，不要求所有测试都重新改造成页面配置。

### 任务调度与测试报告

平台支持用例集、定时任务、远程执行和执行状态跟踪。报告用于查看通过率、失败步骤、断言结果、请求响应、日志和截图，而不只是展示一个最终状态。

## 最近重点建设的数据工厂

真实业务自动化中，一个经常被低估的问题是测试数据。

例如编辑、删除、审批和状态流转类接口，都要求执行前已经存在符合特定状态的数据。如果每个用例都手写前置 SQL，会出现几个问题：

- SQL 和业务表结构强耦合。
- 同一段造数逻辑被多次复制。
- 不同环境的数据库配置容易写死。
- 创建了哪些数据、是否清理成功缺少统一记录。

芒果测试平台的数据工厂将这部分拆成了几层：

```text
逻辑数据源
  → 不同环境的真实数据库绑定
  → 业务实体与字段生成规则
  → 表示业务状态的数据模板
  → 用例执行前自动造数
  → 在请求和断言中引用结果
  → 执行结束后按策略清理
```

这样，同一份数据模板可以在不同测试环境中解析到不同数据库，用例只关心“需要什么状态的数据”，不需要反复编写具体 SQL。

## 为什么增加 MCP 与 AI 能力

AI 很擅长生成代码，但如果它不了解平台中的项目、模块、环境、已有接口、用例、变量和历史报告，生成结果很容易变成新的孤立资产。

因此，平台通过 MCP 将一部分测试能力以结构化工具开放出来，让支持 MCP 的 AI 助手可以在权限范围内完成例如这些工作：

- 查询项目、模块、环境和已有测试资产。
- 创建或维护 API 自动化用例、场景、断言和提取规则。
- 查询数据工厂实体、模板和执行记录。
- 触发测试执行并读取报告。
- 汇总失败信息，辅助判断是认证、请求构造、断言、测试数据还是业务服务问题。

我希望 AI 在这里扮演的是测试工程助手，而不是一个绕过平台和权限直接操作数据的黑盒。

## 执行架构

平台目前将不同职责拆分为独立服务：

```text
Web 控制台
  → Core API：配置、权限、页面请求和状态查询
  → Scheduler：定时触发与任务分发
  → API Worker：领取并执行 API 自动化任务
  → MCP Service：向 AI 提供平台能力
  → Actuator：执行 UI、Pytest 等需要特定运行环境的任务
```

这种拆分的目标不是为了追求服务数量，而是避免 Web 请求、定时调度和耗时执行互相影响，也方便根据实际负载扩展 Worker 或执行器。

## 适合哪些团队

这个平台更适合以下场景：

- 已经有一定自动化积累，希望从个人脚本转向团队管理。
- 同时维护 API、UI 或 Pytest，需要统一任务和报告入口。
- 测试数据准备复杂，希望减少重复 SQL 和人工造数。
- 有私有部署、环境隔离或二次开发需求。
- 正在探索 AI Agent 如何真正接入质量工程流程。

如果团队只需要临时调试几个接口，使用轻量接口工具可能更合适；如果只需要运行少量稳定脚本，直接使用 Pytest 和 CI 也足够。平台化会带来部署和维护成本，它更适合测试资产已经达到一定规模的团队。

## 当前仍在改进的地方

项目已经可以部署和使用，但还在持续完善：

- 降低首次部署和初始化配置成本。
- 补充更完整的示例项目和演示数据。
- 完善系统健康状态、任务链路和故障诊断。
- 继续优化大规模执行和报告数据的存储方式。
- 让 MCP 权限、风险分级和审计更加清晰。

## 最新版正在扩展什么

在现有自动化主链路之上，最新版已经开始连接更完整的研发质量过程：

- 以迭代、需求、开发设计、功能用例、测试计划和缺陷形成研发协同闭环；
- 通过 API 模块覆盖、版本管理和 Mock 服务完善接口测试治理；
- 通过实时工作台、智能定位和可审查的自愈流程降低 UI 维护成本；
- 增加性能场景、测试计划、运行历史和执行器容量管理；
- 从执行报告继续扩展质量效能、风险待办和来源可追溯的指标；
- 统一 SQL 执行审计，以及前端、服务端和执行器的异常记录。

这些能力可以提前交流设计思路，代码、演示数据与帮助文档会按版本逐步开放。完整预告见仓库 `docs/promotion/release-7.1.1.md`。
